# D01：交互式是什么 —— 四道防线防的是「盲等」，不是「输入」

> 议题 ①｜覆盖：交互式的定义、S004 边界的判据｜**依赖：S003 D01/D05 的四道防线**
>
> 状态：🟡 初步收敛（待评审）

## 一、问题：我们要给「交互式」下一个能落地的定义

S003 的工具描述里写死了一句话（`terminal.ts` 的 `description`）：

> This is a non-interactive environment: commands needing tty or user input will fail; use flags like -y or --no-input.

这句话把「交互式命令」整体推给了 S004。但「交互式」是个模糊词，直接照它做工具会失焦。本节要先把它**拆成可判定的东西**。

## 二、先看清 S003 那四道防线到底在防什么

S003 D01/D05 立了四道防线（[S003 D03 §5.5.8](../../../2026-08-26/e02-s003-terminal/decisions/D03-long-running-skip-and-background.md)、[non-interactive-execution-env 笔记](../../../2026-08-26/e02-s003-terminal/notes/non-interactive-execution-env.md)），对应四条独立的输入通道：

| 防线 | 手段 | 挡住的 |
|---|---|---|
| ① | `stdio[0]='ignore'` | 命令读 stdin → 立即 EOF，不会卡在 `read()` |
| ② | 不挂 pty（`isatty()` 恒 false） | 命令走「检测到终端才提问」的分支时，走非交互分支 |
| ③ | env 注入（`GIT_TERMINAL_PROMPT=0` / `GIT_ASKPASS=''` / `DISPLAY=''` 等） | 命令绕过 stdin 直接开凭据弹窗 / `/dev/tty` |
| ④ | 超时 / 跳过 / 取消兜底 | 以上都失效时的最后一道 |

⚠️ **关键观察：四道防线防的从来不是「输入」这个动作，而是「盲等一个永远不会来的输入」。**

`terminal("python")` 在 S003 下不是「不能交互」——它是**立即拿到 stdin 的 EOF 然后退出**（或报错）。防线①做的是「把无限等待变成立即失败」。这跟「支持交互」不是对立面，是**同一根光谱的两端**：

```
盲等（挂死）          立即 EOF（S003）          可回答的请求（S004 目标）
     ✗ 最差              ○ 安全但无能                ● 安全且有能
```

→ **S004 的定义因此可以精确下来**：

> **交互式支持 = 把「盲等一个不会来的输入」升级为「一个可以被回答的、有边界的请求」。**

不是「取消四道防线」，是**只把防线①打开一条缝**（`ignore` → `pipe`），并为这条缝配一套新的兜底（②③④保持不动，见 D04/D05）。

## 三、判据「要不要人输入」往下还要拆一层：**谁持有答案**

[S003 D03 §五](../../../2026-08-26/e02-s003-terminal/decisions/D03-long-running-skip-and-background.md) 把 S003/S004 的线定为「**要不要人输入**」。这条判据是对的，但它到了 S004 内部**必须再拆一层**，否则会把两类完全不同的问题当成一件事。

问一个更细的问题：**这个输入，答案在谁手里？**

| 类别 | 例子 | 答案在谁手里 | S004 怎么处理 |
|---|---|---|---|
| **A：模型能答** | `python`/`node` REPL 里求值、`git add -p` 的 `y/n`、`npm init` 的项目名、bash `read` 一个选项、`[y/N]` 确认 | **模型**（它有上下文，知道意图） | ✅ **本章主战场**：给模型一条写 stdin 的通道 |
| **B：只有人能答** | `sudo` 密码、`ssh` 口令、`gh auth login` 的 2FA、"真的要删库吗"这种需要人担责的确认 | **人**（模型不该知道，知道了也不该由它决定） | ❌ 不让模型写；划给**审批层（Epic 3）** / 拒绝并引导非交互替代 |

⚠️ **这一拆是本章最重要的判断**。因为：

1. **A 类是能力问题**：模型有答案，只是缺一条通道。补通道即可，纯工程。
2. **B 类是边界问题**：模型没有（也不该有）答案。给它通道等于逼它编一个密码，或把从别处拿到的凭据吐进上下文。**这不是"做不做得到"，是"该不该做"。**

→ **同一条判据「要不要人输入」，往下一层分叉成「工程」和「安全」两个完全不同的问题。** 这正是把它们分给两章的理由：S004 做 A（stdin 通道），Epic 3 做 B（谁有权提供只有人能答的输入）。

## 四、竞品的两个相反答案，本质是「控制权归属」

「谁写 stdin」在竞品里有两个针锋相对的实现（[codex.md §G](../../../researches/terminal/codex.md)、[aider.md §B/§G](../../../researches/terminal/aider.md)）：

| 竞品 | 谁写 stdin | 形状 | 前提 |
|---|---|---|---|
| **Codex** | **模型** | `write_stdin(session_id, chars)` 工具，模型自己续写（`shell_spec.rs:113-155`） | 全自动 Agent，模型闭环 |
| **Aider** | **人** | `child.interact()` 把终端控制权直接交给用户（`run_cmd.py:120`），shell 以 `-i` 启动 | 人在环内的结对工具 |

Aider 调研里那句话点破了本质（[aider.md 核心洞察](../../../researches/terminal/aider.md)）：

> 最本质的差别不是协议形式，而是**控制权归属**。Aider 里模型只有「建议权」……tool-calling 的 terminal 工具则把三件事交给模型闭环。

→ **zero2agent 是自主 Agent（tool-calling 架构），控制权在模型手里。** 所以 A 类输入选 **Codex 路线（模型写 stdin）**，否决 Aider 路线（人接管终端）。理由不是 Aider 做得不好，而是**它服务的是另一种产品形态** —— 把终端交给人，只在「人就坐在 TTY 前」时成立，而 Agent 可能跑在桌面 App、服务、CI 里（这正是 S003 D05 反复强调的前提差异）。

⚠️ 但注意：**否决「人接管终端」不等于「人完全不能介入」**。TUI 侧完全可以让人也往一个会话里敲字（就像 S003 的 Ctrl-X/Ctrl-S 按键）——那是**呈现层**的事，走既有事件通道，不改变「模型是主要输入者」这个架构定位。详见 D03。

| # | 决策 | 类型 |
|---|---|---|
| D01-1 | 交互式支持定义为「**把盲等升级为可回答的请求**」，即只把防线①（`stdio[0]`）打开一条缝，②③④不动 | 定义 |
| D01-2 | 判据「要不要人输入」在 S004 内部**再拆「谁持有答案」**：A（模型能答）/ B（只有人能答） | 边界 |

| D01-5 | A 类输入由**模型**写（Codex 路线），**否决 Aider 的「人接管终端」**——控制权归属决定，非优劣 | 架构 |

## 六、教学价值

1. **一道「防线」防的往往不是它字面挡住的东西** —— 四道防线防的是「盲等」不是「输入」。看清这一点，S004 就从「推翻 S003」变成「把一道防线开一条缝」，尺度完全不同。
2. **一个看似单一的判据，往下一层会分叉** —— 「要不要人输入」是对的划线，但到 S004 内部必须再拆「谁持有答案」，否则会把「补个通道」（工程）和「谁能提供密码」（安全）当成一件事做。
3. **同一个功能，选哪条路取决于产品形态而非技术优劣** —— Codex（模型写）和 Aider（人接管）都对，因为它们是不同的产品。抄之前先问「我是哪一种」。
4. **「不该做」和「做不到」是两回事** —— 让模型写密码，技术上完全做得到（就是往 stdin 写几个字节），但它是边界问题不是能力问题。**能力问题补通道，边界问题只能靠不给。**（这条判据 S003 D04-8 用过一次：不给模型 list 工具。）

## 七、向议题 ② 的顺延

答案会很反直觉 —— **观测不到**。见 D02。
