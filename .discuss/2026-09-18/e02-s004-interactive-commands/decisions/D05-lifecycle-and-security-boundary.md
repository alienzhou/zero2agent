# D05：生命周期与安全边界 —— 会话复用三道防线 + 空闲兜底；「只有人能答」的推给审批专章

> 议题 ⑤｜覆盖：会话生命周期、上限、空闲超时、安全边界｜**依赖：D03（会话表）、D04（无 pty 缺口）、S003 D04（三道防线）**
>
> 状态：🟡 初步收敛（待评审）

## 一、问题

一个交互会话是「活着、我们攥着 live handle 和可写 stdin、还在反复读写」的进程。它比 S003 的后台进程更「黏」——后台进程是「放它走」，会话是「一直连着」。三个收尾问题：

1. 会话什么时候、由谁结束？空闲了怎么办？
2. 会话数要不要设上限？
3. D01 划出去的「只有人能答」（密码/确认）到底归谁做？

## 二、生命周期：会话是「可以被写的跳过进程」，三道防线基本能复用

S003 D04 为后台进程建了[三道防线对应三种死法](../../../2026-08-26/e02-s003-terminal/decisions/D04-process-lifecycle.md)。会话在这三种死法上和后台进程**没有区别**，所以直接复用：

| S003 防线 | 对交互会话是否适用 | 说明 |
|---|---|---|
| ① 退出钩子（Agent 正常退出 → 遍历杀） | ✅ 适用 | 会话表也要挂进退出钩子；退出时**列出活会话并询问**（同 D04-10 的 `(y/N)`） |
| ② watcher 包装（Agent 被强杀 → 子进程自杀） | ✅ 适用 | 会话进程同样要包 [D04-5 的 watcher](../../../2026-08-26/e02-s003-terminal/decisions/D04-process-lifecycle.md)（`>/dev/null 2>&1` 必须带，血的教训 D04-6） |
| ③ 读取侧 2 秒 drain 超时（进程不退 → 强行 resolve） | ✅ 适用 | 会话每次 `write_stdin` 后的收输出，同样要有 drain 超时防 `setsid` 曾孙挂死 |
| Ctrl-X 取消（全程） | ✅ 复用 | 「取消整个会话」= killpg + 从会话表摘除 |

⚠️ **但有一处不能照抄**：S003 跳过时会 `child.unref()` + detach（`terminal.ts` 的 skip 分支）。**交互会话绝不能 unref/detach** —— 它必须一直连着才能写 stdin（D03 决策四已记）。→ 会话进入的是「保持连接」分支，不是 S003 的「跳过→后台」分支。

## 三、新增防线：会话空闲超时（防"开了会话就忘"的新挂死）

D03 把 `stdio[0]` 开成 `'pipe'`，**重新引入了一种挂死**：模型开了交互会话，但之后再没调 `write_stdin`（推理跑偏 / 忘了），而命令还在 `read(stdin)` 等着。这是 S004 自己制造的新问题，**必须自己收口**（同 S003 D04 §6.6.1「自己制造的问题不能留给下一章」的判据）。

**新增第四道兜底：会话空闲超时。**

- 会话超过一个空闲阈值没有任何 `write_stdin`（也没新输出）→ 自动给它 EOF（关 stdin 写端）/ 或 killpg，并在下一次相关回执里告知模型「会话 X 因空闲已关闭」。
- ⚠️ **阈值不能照抄 S003 的 10 秒**（P5）：交互会话里「模型读完输出→思考下一步写什么」本身可能 >10 秒，10 秒会误杀正常会话。倾向取显著更长的值（如 60–120 秒），待实测。**关 stdin（发 EOF）比 killpg 更温和**，很多命令收到 EOF 会自己优雅退出，优先走 EOF，killpg 留给「EOF 后仍不退」。

## 四、会话数上限：软上限 + LRU，教学项目取小值

模型可能开一串会话忘了关。借 Codex 的[会话池思路](../../../researches/terminal/codex.md)（`process_manager.rs:1346-1385`），但数值教学化：

| | Codex | zero2agent（倾向） |
|---|---|---|
| 上限 | 64（`mod.rs:73`） | **8 左右**（P6，教学项目不需要大池） |
| 淘汰策略 | LRU，优先淘汰已退出的 | 同 |
| 不变式 | **正被 write 的不淘汰**（软上限，宁可临时超限也不误杀活会话） | **照搬** —— 这条不变式很反直觉但很对 |

⚠️ Codex 那条「软上限：正确性优先于上限，宁可临时超过也不误杀正在交互的会话」（[codex.md §G.4](../../../researches/terminal/codex.md)）是本条最值得学的。硬性 LRU 会在并发下杀掉模型正在用的会话。

## 五、安全边界：S004 只做「输入通道」，不做「该不该输入」

D01 把「只有人能答」（密码/2FA/真·危险确认）划成 B 类，D04 说无 pty 顺手堵住了大部分密码提示。这里把边界**正式钉死**：

> **S004 做的是「stdin 输入通道」这个机制；「谁有权提供只有人能答的输入」「哪些交互该拦下来问人」是策略，归审批专章（Epic 3）。**

这与 S003 完全同构 —— [S003 D01 §九](../../../2026-08-26/e02-s003-terminal/decisions/D01-tool-baseline.md) 把「命令解析 / 黑白名单」整体推给安全专章，S004 把「交互输入的授权」推给同一章。**机制在这一章，策略在安全章。**

一条可以直接搬进 Epic 3 的输入（[aider.md §F](../../../researches/terminal/aider.md)）：

> Aider 的 `explicit_yes_required`（`io.py:866-867`）：**即使用户全局开了 `--yes` 自动同意，模型建议的 shell 命令依然被拒。**

→ 到 Epic 3 做交互输入的审批时，「有些输入（如代表模型的危险确认、代表人的密码）不允许被 auto-approve 覆盖」是现成的分级思路。**S004 只需保证：这些 B 类输入在本章是"够不着 / 不给写"的状态，而不是"默默替模型答了"。**

## 七、教学价值

1. **交互会话是「可以被写的跳过进程」** —— 生命周期上它和 S003 的后台进程共享三种死法，所以三道防线直接复用；唯一的差别是「连着 vs detach」。**识别"新东西其实是旧东西的一个变体"，能省掉一整套重复设计。**
2. **打开一道防线，就要为它新配一道兜底** —— D03 开了 stdin 管道（拆防线①），本章就必须补「会话空闲超时」，否则「开了会话就忘」是一种全新的挂死。**这是 S003 D04 §6.6.1「自己制造的问题不能留给下一章」的又一次应用。**
3. **软上限：正确性优先于资源上限** —— 宁可临时超过会话数上限，也不淘汰模型正在交互的会话。**大多数资源池是硬上限，但当"误杀"的代价远大于"临时超限"，就该把上限做软。**
4. **机制与策略分层** —— S004 做「stdin 通道」（机制），Epic 3 做「谁有权输入 / 哪些要拦」（策略）。与 S003「执行机制在这章、命令安全在安全章」同构。**把机制和策略切开，两章都更干净。**
5. **温和的收尾优先于强杀** —— 空闲超时先发 EOF（很多命令会自己优雅退出），killpg 留给不听话的。**能让对方自己退，就别动刀** —— 与 S003「取消才 killpg、跳过一个信号都不发」同源的克制。

## 八、S004 讨论至此闭环

五个议题走完，交互式命令的形状封闭：

```
① 交互式是什么         →  把盲等升级为可回答的请求；拆"谁持有答案"
② 怎么知道在等         →  不检测，靠模型声明 + 静默兜底
③ 用什么形状喂输入     →  新工具 write_stdin + 会话表（持有 live handle）
④ 无 pty 能覆盖多少    →  只覆盖"读 stdin"那类；isatty 门控 / 密码记缺口
⑤ 怎么收尾、谁管安全   →  复用三道防线 + 空闲兜底；密码类推给审批专章
```

⚠️ 贯穿五条的主线是一句话：**S004 = 把 S003 的防线①开一条可控的缝，并为这条缝配齐兜底与边界。** 它不是推翻 S003，是**在 S003 立好的四道防线之上，精确地、只对声明的会话、开一个口子**。
