# D01 - Glob 底层技术选型

> 状态：✅ 已确认 — 采纳方案 1（rg `--files` + `--glob`）

## 背景

E01-S003 要给 Agent 加上「按名字/路径模式找文件」的能力。在设计 Agent 工具之前，先确定底层用什么技术来执行 glob 匹配。

本文档沿用 S002 的五维评估框架，对四个候选方案做横向对比。

---

## 候选方案

| # | 方案 | 调研中的使用者 |
|---|------|--------------|
| 1 | ripgrep `--files` + `--glob` | OpenCode, Codex（shell 内） |
| 2 | fd（专用文件搜索工具） | Pi |
| 3 | npm `glob` 包（纯 Node） | Gemini CLI |
| 4 | Node.js 内置 `fs.glob`（Node 22+） | 无（新 API） |

---

## 评估维度

### 1. 工具本身的能力

对 glob / 按名找文件这个场景，「能力」主要看：

- glob 语法支持程度（`**`、`{a,b}`、`[!...]`、negation）
- 是否默认尊重 `.gitignore`
- 是否能搜索隐藏文件（dotfiles）
- 是否能跟踪符号链接
- 是否支持搜索深度限制

| 能力 | rg `--files` | fd | npm `glob` | Node `fs.glob` |
|------|-------------|-----|-----------|----------------|
| `**` globstar | ✅ | ✅ | ✅ | ✅ |
| `{a,b}` brace | ✅ | ✅ | ✅ | ✅ |
| `[!...]` 字符类 | ✅ | ✅ | ✅ | ✅ |
| negation (`!pattern`) | ✅（`--glob=!xxx`） | ✅（`-E` exclude） | ✅（ignore 选项） | ✅（exclude 选项，v22.2+） |
| `.gitignore` 默认尊重 | ✅ 自动 | ✅ 自动 | ❌ 需手动 | ❌ 无此概念 |
| 隐藏文件 | `--hidden` 开启 | `--hidden` 开启 | `dot: true` | 需手动处理 |
| 符号链接 | `--follow` | `--follow` | `follow: true` | 未明确支持 |
| 深度限制 | `--max-depth` | `--max-depth` | 无内置 | 无内置 |
| 大小写控制 | 无直接参数 | `-i` / `-s` | `nocase: true` | 无内置 |
| 纯文件（排除目录） | 默认只列文件 | `--type f` | `nodir: true` | 无内置（issue #52752 讨论中） |

**小结：** rg 和 fd 在工程场景最实用——自动 gitignore、隐藏文件/深度/符号链接都有开关。npm `glob` 功能全但需要自己配 ignore。Node `fs.glob` 最弱，功能还在补齐中。

### 2. 性能表现

文件搜索是 IO 密集型任务（遍历文件系统元数据），和 grep 的 CPU 密集不同。

| 维度 | rg `--files` | fd | npm `glob` | Node `fs.glob` |
|------|-------------|-----|-----------|----------------|
| 实现语言 | Rust | Rust | JavaScript | C++/JavaScript |
| 并行遍历 | ✅ 多线程 | ✅ 多线程（核心优势） | ❌ 单线程 | ❌ 单线程 |
| 大仓性能（~100 万文件） | 快（亚秒级） | 最快（专为此优化） | 慢（秒级） | 中等（待验证） |
| 内存占用 | 低 | 低 | 中（JS 对象开销） | 低到中 |
| 启动开销 | 中（spawn 子进程） | 中（spawn 子进程） | 低（同进程） | 低（同进程） |

**关键数据点：**
- fd 在 ~100 万文件上默认配置下 **123ms**，比 `find` 快约 58 倍（多线程并行遍历是核心原因）
- 外部 CLI 工具（rg/fd）比所有 Node.js glob 包显著快，在大型 TypeScript 仓库中 Agent 循环可加速 2-3 倍
- npm `glob` 包是「最正确但第二慢」的 Node 实现；`fdir`（更快的 Node 替代）100 万文件 < 1 秒

**小结：** 纯性能看 fd > rg `--files` > Node 方案。但对 Agent 场景（通常几千到几万文件的项目），四个方案都够快，性能不是决定性因素。

| 维度 | rg `--files` | fd | npm `glob` | Node `fs.glob` |

| GitHub Stars | ~50k | ~35k | ~8k（glob 包） | N/A（Node 内置） |

**小结：** rg 生态最强（S002 已验证），npm `glob` 下载量最高（但主要靠 legacy 依赖）。Node `fs.glob` 太新，AI 几乎没见过，Agent 场景风险最大。

### 4. 错误反馈机制

| 维度 | rg `--files` | fd | npm `glob` | Node `fs.glob` |
|------|-------------|-----|-----------|----------------|
| 无效 pattern | stderr 清晰报错 | stderr 清晰报错 | 抛异常，信息中等 | 抛异常，信息简略 |
| 目录不存在 | exit code 2 + 消息 | exit code 1 + 消息 | 返回空数组（静默） | 回调 Error |
| 权限不足 | 跳过 + 可选警告 | 跳过 + 可选警告 | 抛异常 | 抛异常 |
| 错误可直接给 Agent | ✅（stderr 文本即可） | ✅（stderr 文本即可） | 需要 catch + 格式化 | 需要 catch + 格式化 |

**小结：** rg 和 fd 的错误反馈最适合 Agent 场景——文本格式的 stderr 可以直接返回给模型自行修正。

### 5. 跨平台兼容性

| 维度 | rg `--files` | fd | npm `glob` | Node `fs.glob` |
|------|-------------|-----|-----------|----------------|
| macOS | ✅ | ✅ | ✅ | ✅ |
| Linux | ✅ | ✅ | ✅ | ✅ |
| Windows | ✅ | ✅ | ✅ | ✅ |
| 需要外部二进制 | ✅（已有下载机制） | ✅（需新增下载） | ❌ | ❌ |
| 行为一致性 | 高 | 高 | 高 | 中（新 API，可能有平台差异） |
| 路径分隔符处理 | rg 统一处理 | fd 统一处理 | 需 `posix: true` 或手动 | 需手动处理 |

**小结：** rg 的跨平台分发在 S002 中已经解决（OpenCode 的六平台下载逻辑我们已调研过）。fd 需要额外一套下载机制。npm `glob` 和 `fs.glob` 天然免安装。

## 分析与倾向

**方案 1（rg `--files`）的核心优势：零额外成本。**

S002 已经接入了 ripgrep——二进制下载、进程管理、跨平台分发全部做过了。用 `rg --files --glob=<pattern>` 只是**换一组参数**，不需要引入新的二进制、新的下载逻辑、新的 npm 依赖。这对一个教学项目来说意义很大：**学生不需要理解第二套工具链**。

**方案 2（fd）虽然性能最强，但引入了额外复杂度。** 需要新增一套 fd 二进制的下载/缓存/跨平台逻辑。Pi 选它有道理（Pi 没有先做 rg），但我们已有 rg，再加 fd 是增量成本。

**方案 3（npm `glob`）最大的问题是没有 gitignore 感知。** 这意味着要么自己实现 gitignore 解析（如 Gemini CLI 的两层过滤），要么接受 `node_modules/` 等目录的噪音。对教学项目来说过于复杂。

**方案 4（Node `fs.glob`）不推荐。** API 太新、文档不全、AI 训练语料几乎没有、功能还在补齐中。

---

## 结论

- [x] 采纳方案 1（rg `--files` + `--glob`）作为底层技术
- 核心理由：S002 已接入 rg，零增量成本；五维评估综合最优；OpenCode / Codex 验证可行
- Benchmark 已在另外的对话中完成，性能数据支持此结论
