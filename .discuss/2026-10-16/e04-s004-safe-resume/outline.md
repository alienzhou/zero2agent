源码依据：`Session.snapshot()` 只允许空闲状态；`runTurn()` 在 finally 提交本轮工作副本。`Conversations.perform()` 在执行前保存旧快照和 pending，执行后保存新快照；`load()` 遇到死亡进程目前只恢复上次结算历史。`CheckpointStore.capture()` 已持久保存工具关联身份、写入前状态和 pending，再捕获写入后状态。`executeTools()` 已有当前权限、文件保护和结果存储顺序，但还没有等待完成的逐工具恢复存储接口。

## 第一版交付建议

1. **逐工具持久执行记录。** 先保存本轮输入和完整的模型响应，再在实际执行边界保存记录；工具结算后保存真实回执。记录关联 session、turn、tool call、诊断 operation 和 checkpoint。存储失败必须沿等待完成的控制接口阻止后续工作，不能仅靠展示事件通知。
2. **恢复与核对。** 已结算记录恢复为配对的历史；能证明尚未进入执行边界的调用标为未执行；已进入执行边界却缺少结果的调用标为效果未知。对受控文件展示已有 checkpoint 和当前文件比较。内容相同只能说明核对时的文件状态，不能单独证明旧工具成功。
3. **明确的继续入口。** 复用会话恢复入口，先展示“已完成 / 未执行 / 待核对”。用户选择继续、保留中断状态或使用已有文件回退；具体命令名在交互设计阶段确定。加载、查看记录都不执行旧工具。后续调用使用当前模型、权限、工作区和新的授权判断。
4. **接住已有边界。** 保存或可靠重建 S003 未解决读取、显式产物契约及完成阶段状态；保留原运行的预算与停止证据。恢复已有任务不能暗中重置额度；若显式开始新一轮，界面说明新预算与旧轮已停止的事实。无法完整恢复的状态应保守阻止自动继续。

范围限于单机、单宿主会话和内置受控文件工具；其他工具已结算的回执可恢复为历史。普通 shell 的未知文件、后台进程和外部系统效果需要人工核对，不自动重启进程或重放命令。通用工作流调度、多主机协调、外部系统恰好一次执行、Worker 隔离列入后续工作。

## 实施顺序与设计待定项

先做确定性崩溃复现：同一个文件修改任务在指定边界结束子进程，由新进程恢复；记录文件字节、调用次数、磁盘记录和下一次 SDK 请求。先证明当前缺口，再确定存储协议。

设计必须回答：

- 持久执行记录、结果正文、checkpoint 和整轮快照如何排序发布与关联；采用快照、追加日志或组合的依据是什么。
- 完整响应内多个工具如何处理部分结算；缺失回执如何表达真实的不确定性并保持消息协议有效，不能伪造成功回执。
- 崩溃后重复恢复如何去重，整轮快照吸收记录后怎样避免再次追加。
- 未结算记录和所引用正文如何阻止提前清理；磁盘满、半写、损坏、版本不支持与另一进程占用怎样明确失败。
- S003 的回合内检查及 S001 预算状态如何保存、重建或安全终止；不能以恢复为由静默绕过检查。

随后按“存储与 Core 执行边界 → 恢复重建 → CLI/TUI 入口 → 验收 → 跟练和课程”实施。先形成具体 Spec 与故障矩阵，再开始生产代码；这份课前安排不宣称这些设计已完成。

## 验收先冻结

| 故障或恢复场景 | 必须观察到的结果 |
| --- | --- |
| 写入执行标记之前退出 | 只有持久协议能够证明未开始时才报告未执行，文件效果为零 |
| 执行标记已发布、工具尚未调用时退出 | 不能从缺少结果推断未执行；保守报告未知 |
| 文件已改变、结果尚未持久化时退出 | 恢复不再次写入；展示待核对状态与文件证据 |
| 工具结果已持久化、整轮快照尚未保存时退出 | 恢复调用与真实结果，保持配对，副作用次数不增加 |
| 一个响应内部分工具完成 | 已完成结果保留，剩余调用状态准确，不重放整个批次 |
| 恢复后再次崩溃或反复加载 | 已吸收记录不重复追加，不重复执行 |
| 人工已修改文件、读取权限改变、旧进程仍存活 | 不覆盖人工修改，不沿用旧审批，不抢占旧进程 |
| 存储满、半写、损坏、引用缺失 | 说明证据缺口，保留可恢复数据，不能伪装恢复成功 |
| 原轮预算已耗尽或完成检查未解决 | 恢复保留停止事实；不能通过重启获得隐含重试额度或完成状态 |

主要门槛由可重复的真实子进程故障测试判定；真实 CLI/PTY 验证恢复交互。再用少量固定真实模型任务验证集成，分开报告结果，不能把模型一句“已完成”当作恢复成功。进程被终止的验证不等于断电、网络文件系统或所有平台的持久性保证。
