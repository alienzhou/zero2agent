# D01：E03 课程顺序与边界

## 状态

Confirmed，2026-10-01。用户认可六节课建议并要求写入仓库。

## 决策

采用 [Epic 3 课表](../../../../specs/E03-product-foundations/README.md)：S001 多轮会话 → S002 权限与 Approval → S003 TUI → S004 会话恢复 → S005 日志 → S006 文件 Checkpoint。

这替代了[早期 D05](../../../2026-03-14/zero2agent-course-roadmap/decisions/D05-stage3-to-stage5-preview.md)中先落 TUI 的方向性安排。旧决策保留为历史，不改写原始讨论。Epic 4、Epic 5 的分工不变。

## 为什么这样排序

1. 现有 CLI 连续接受输入，但 `runLoop()` 每次重新构造消息数组。先补最小多轮会话，让后续 UI 有实际会话状态可展示。
2. E02 已具备写、删、执行能力，应尽早统一授权入口。审批协议先由简单终端承载，不必等待完整 TUI。
3. 现有 Core 已有事件回调，解耦应随状态展示、审批与控制需求补齐，不另开无交付目标的架构课。
4. 进程内对话与持久化拆开，避免首课同时承担文件格式、恢复和界面管理。基础错误边界仍由各课处理，复杂异常恢复留到 Epic 4。
5. 会话历史服务于继续对话，运行日志服务于排障，文件快照服务于回退。分课讲清职责，避免一份记录承担三种互不相同的保证。

## 不在本次确认的内容

不确定 TUI 框架、存储格式、权限规则语法、日志字段或 Checkpoint 存储方案；这些在对应 Story 的需求讨论和技术设计阶段确定。本次不生成六套占位 Spec，不实现会话分叉、沙箱或外部副作用回滚。
