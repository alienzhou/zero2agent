# E03-S003：让运行过程看得见、控得住

用户最新指令：“继续推进下一课程呢，是什么主题？”根据既定 Epic 3 顺序，下一课为运行状态与 TUI。本文开始需求讨论，不将规划写成已经实现。

## 承接点

S001 提供多轮会话、请求预算和压缩；S002 提供执行前权限、一次 Approval 和配对结果。工程从 `E03-S002-permissions-approval` 开始，固定生产与测试候选 `73ecdbc`。S002 已交付工程 PR #17 和本地图文，待人工审阅与合并。

当前 UI 使用 readline 和 stdout。Core 的 onText、onToolStart/onToolEnd/onToolError、onPermission、onCompaction 已具备部分展示能力；requestApproval 独立返回用户响应。工具展示回调尚未携带稳定调用 ID，onText 混有运行提示，现有 cancelPendingApprovals 和 cancelCompaction 都不是完整 Turn 取消接口。这些是下一课设计需要明确的事实。

## 读者将遇到的情景

1. 模型请求尚未返回时，界面持续显示运行阶段；文本流、工具进度和上下文压缩能区分来源。
2. 模型提议写文件时，展示同一次调用的工具、参数、工作目录与授权理由；回答仅控制这一审批。
3. 工具完成、拒绝、失败或取消后，状态与配对结果一致；重复工具调用靠稳定 ID 关联。
4. 用户编辑输入、等待审批、人工 PTY 接管之间只有一个输入持有者；终端尺寸变化和退出能恢复显示与终端状态。

## 第一版范围

梳理 Core→UI 的带身份事件，以及 UI→Core 的独立控制接口；定义状态转换；实现基础终端界面和审批交互；保留已有一问一答 CLI 与非 TTY 语义；用确定性流和真实 PTY 验证事件顺序、焦点、取消范围、尺寸变化与清理。

是否支持完整取消当前 Turn，需要先设计请求中断、工具执行与消息证据的共同契约。不能把停止 spinner 或取消 Approval 当作完整取消，也不能删除已经产生的工具副作用证据。

## 竞品调研与方案问题

比较 Claude Code、Codex、Gemini CLI 和 OpenCode 的状态/工具/审批呈现、取消手势、输入焦点及 PTY 交接，分别记录官方文档、可固定源码与可复现的交互证据。选择实现方案前验证已有代码的控制接口与终端能力，再评估 TUI 组件库和原生终端方案；不先以框架决定事件契约。
