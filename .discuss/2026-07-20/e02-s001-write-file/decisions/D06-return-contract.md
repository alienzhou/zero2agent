# D06：返回结果契约 —— 沿用 string 回执，携带路径与语义信息

## 状态
✅ Confirmed

## 决策

`write_file` 与 `delete` **沿用现有工具的 `Promise<string>` 回执**，不引入结构化返回类型。回执内容要携带足够信息量：

### write_file 成功回执

- **区分新建 vs 覆盖**，让模型无需再读文件确认：
  - 新建：`已创建文件 <path>（写入 N 字节）`
  - 覆盖：`已覆盖文件 <path>（写入 N 字节）`

### delete 成功/部分失败回执（呼应 D05）

- 逐条汇总，例如：
  `已删除：a.txt, c.txt；失败：b.txt（文件不存在）`

### 错误回执

- 沿用现有 `Error: ...` 字符串前缀（非抛异常）。
- 文本区分常见错因：`文件不存在` / `是目录` / `超出工作区` / `权限不足` 等，但**不引入错误类型枚举**。

## 竞品对照

- **pi-mono**：`Successfully wrote N bytes to path` —— 最贴合 zero2agent 现有 string 风格，字节数直接采纳。
- **Gemini**：回执明确区分 `created` vs `overwrote` —— 零成本、对模型有用，采纳。
- **OpenCode**：回执拼接 LSP 诊断；**Gemini**：附完整 diff —— 太重，S001 **不做**。
- **Gemini** 还把错误细分为 `ToolErrorType` 枚举 —— S001 用文本区分即可，不上枚举。

## 理由

1. **一致性**：现有 4 个只读工具都返回 string、错误用 `Error:` 前缀。写工具沿用，读者不必学新契约。
2. **信息量恰到好处**：字节数 + 新建/覆盖标识 + 逐条删除结果，足够 Agent 判断结果，又不像 LSP/diff 那样重。
3. **结构化返回留给未来**：若日后要传 diff、诊断等富信息，再评估升级返回类型，S001 不提前设计。
