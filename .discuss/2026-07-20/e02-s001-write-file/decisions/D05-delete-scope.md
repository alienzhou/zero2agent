# D05：delete 的范围 —— 支持多文件（数组），不递归，尽力删 + 逐条汇总

## 状态
✅ Confirmed

## 决策

`delete` 工具的能力边界：

- **支持一次删除多个文件**：参数为路径数组（如 `delete({ paths: ["a.txt", "b.txt"] })`）。
- **只删文件，不递归删目录**：目标是目录时返回错误，不做 `rm -r`。
- **部分失败语义 = 方案 B「尽力删 + 逐条汇总」**：
  - 对数组里每个路径都尝试删除，不因某个失败而中断；
  - 每个路径都要先过 D03 的 cwd 边界校验；
  - 最终回执逐条汇总成功与失败，例如：
    `已删除：a.txt, c.txt；失败：b.txt（文件不存在）`
- **删不存在的目标 = 失败项**：如实报告 `文件不存在`，不做幂等静默。

## 竞品对照

竞品都用 shell `rm`（可递归、可批量、可通配），没有独立 delete 工具可直接对标。数组 + 不递归是 zero2agent 的自主设计：批量删临时/中间文件是真实场景，而递归删目录破坏性过强，应等 Epic 3 有 Checkpoint / 确认机制再放开。

## 为什么选方案 B（尽力删 + 逐条汇总）

三种部分失败处理方式对比：

| 方案 | 行为 | 问题 |
|------|------|------|
| A. 全成功才算成功 | 遇错即停，已删的不回滚 | 语义模糊（a 删了 b 没删），状态不清 |
| **B. 尽力删 + 逐条汇总** ✅ | 每个都试，汇总结果 | —— |
| C. 先全校验，全过才删 | 任一越界/不存在就整体拒绝 | 更安全但对批量删的便利打折 |

选 B 的理由：

1. **对 Agent 最友好**：Agent 能从回执明确知道哪些成了、哪些没成，自主决定是否重试，无需猜测整体状态。
2. **契合现有 string 回执风格**：一条汇总字符串即可，不必引入结构化返回（呼应 D06）。
3. **教学价值**：让读者直面「批量操作要处理部分失败」这个真实工程问题，是很好的教学点。

## 范围约束（进 Spec 定稿）

- 不支持通配符 / glob（保持路径显式）。
- 不递归删目录：目标为目录 → 该项失败，回执写明「是目录，不支持删除目录」。
