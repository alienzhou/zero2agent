# 选题池：terminal 这一章有哪些值得单独写成文章的设计点

> 筛选标准只有一条：**读完能改变读者已有的判断**。
> 只是「介绍某个 API 怎么用」「罗列 N 家怎么做」的，不入选。

---

## A 级（有反直觉结论 + 有多方证据 + 有可复用判据）

### A1. 让 CLI 不问你问题，要同时封住四条通道

**反直觉点**：绝大多数人以为「非交互」是一个开关（加个 `-y`、设个 `NONINTERACTIVE=1`）。
实际上一个 CLI 判断「该不该问用户」有四条独立通道，任缺一条都能挂死：

1. stdin 是否可读 → `stdio[0]='ignore'` → 立即 EOF
2. 是否有 tty → 不挂 pty → `isatty()` 恒 false
3. 能否绕过 stdin 直接开 `/dev/tty` → env 关掉凭据助手 / askpass
4. 以上都失效 → 超时 + 杀进程组

**最强论据**：两个互不相关的团队（一个为守 daemon 环境保真，一个为防 shell 工具挂死）
**独立收敛到同一份 env 清单**。独立收敛比任何单家做法都可信。

**可复用判据**：「不做 pty」不是省功能的妥协，而是**主动关掉防线 #2**。
这个视角切换本身就是文章的钩子。

---

### A2. 「保持和用户终端一致」是一句必须拆成两半的话

**反直觉点**：「Agent 执行环境要和用户终端一致」听起来天经地义，但它混淆了两类东西：

| | 该不该一致 | 做法 |
|---|---|---|
| **能力**（PATH、语言版本管理器、代理、凭据） | **必须一致** | 继承 `process.env` |
| **呈现与交互**（TERM、PAGER、EDITOR、askpass） | **必须刻意不同** | 定向覆盖 |

→ 一条可直接用的原则：**继承为默认，覆盖为例外**。

**加分论据**：为什么 `bash -c` 不读 rc 文件却不是问题 —— 因为 Agent 进程本身是从用户
终端启动的，rc 的成果早已在 `process.env` 里。而一旦这个前提失效（跑在服务管理器 / CI
下），就要做 login shell env 采集，那条路上有 4 个非直觉的坑（`-i` 让 zsh 忽略 SIGTERM、
rc 里读 stdin 的脚本会 hang、shell 主题的 ANSI 污染解析、超时得用 SIGKILL）。

**这篇文章的结构天然完整**：一个看似正确的说法 → 拆成两类 → 给出原则 → 给出前提失效
时的升级路径与它的四个坑。

---

### A3. 解析命令文本来做安全，是一条已被三方证伪的路

**反直觉点**：几乎所有人的第一反应都是「加个命令白名单/黑名单解析器」。三份独立证据说不行：

- 一家写了近 300 行 tree-sitter 解析，遇到 `$(...)` 动态展开时**放弃解析、命令照跑** —— 安全感剧场
- 一家检测到 `$(`/反引号**直接拒绝执行** —— 诚实，但误伤大量合法命令
- 一个生产产品写到 700+ 行（递归剥 `sudo`、剥 `env VAR=`、剥 shell wrapper 含 `-lc`
  这类组合 flag、按 `&&;||` 切复合命令、对子命令再查一层 wrapper、另挖 `$()`）——
  代码注释写着「宁可误切也不漏放」，**最终仍然要靠人工审批兜底**

**最锋利的一句**（来自那个生产产品被 DISABLED 掉的设计）：

> 原设计让模型自己标 `requires_approval` 来触发弹窗。
> **当前决策：不以模型自身的安全判断作为权限依据。**

同向证据：Aider 的 `explicit_yes_required` —— 即使用户开了全局 `--yes`，
模型建议的 shell 命令依然被拒。

**可复用判据**：走到最远的那个团队的结论是**换维度**（人工审批 + 平台沙箱），
而不是继续加码解析。遇到「解析不完」的问题，正确动作是**换边界层**，不是加解析。

## B 级（结论扎实，但更适合作为 A 级文章里的一节，或短文）

### B1. 同一个工具，「杀进程」有两条相反正确的路径

- **单命令超时**：目标是确保死透 → SIGTERM → 宽限 → SIGKILL
- **停机回收**：目标是不拖住关键路径 → **只发 SIGTERM**，剩下交 OS

一个真实产品曾**主动移除 SIGKILL 兜底**，理由是「停机不因回收被拖住」。
抄代码时不看目标只看形状，就会抄错方向。

附赠一个进程回收的演进故事：从「扫进程树」改成「env marker 标记」——
因为主进程被杀后孙进程会 **reparent 到 pid 1**，进程树断了扫不到（漏杀），
同时会误扫到自身的其他子进程（误杀）。marker 方案的三个防事故细节：
随机 UUID 而非固定串（否则多实例互杀）、列进程必须禁用宽度截断（否则 marker 被裁掉
→ 静默漏杀）、跳过自身 pid 防自杀。

### B2. 回执只能有一个出口

一家产品把 exit code 挂在 `metadata` 上，而序列化进模型的只有 `output` 字段 ——
**模型永远看不到退出码**。同一个提交里的新版本已经改成在文本末尾显式追加
`Command exited with code N.`。

另一处同病：跨层翻译时丢了「是否被截断」的结构化信号，只能从输出文本里**嗅探字符串**。

同一个病：**信息在出口分叉处静默丢失。**
→ 所以工具签名保持 `execute(...) => Promise<string>` 的单出口，是一种架构上的防御。

### B3. prompt 是执行环境的一部分，不是文档

三个同向例子：把返回契约写进工具描述、把超时阈值写进工具描述、
以及一个更极端的 —— Windows 编码问题在工程层修不干净（旧命令解释器用 OEM 代码页输出，
切代码页也修不了管道解码），于是**注入一条 system prompt 规则**引导模型改用等价命令。

结论：当工程层的修复有残留，提示词是一个**正当的兜底层**，不是偷懒。

### B4. 截断应该保尾，而且要能被挖回来

- **保尾弃头**：因为错误信息在输出末尾
- **告诉模型被截断了**：否则它会基于残缺输出下结论
- **全文落盘**：模型可以用已有的 `read_file` / `grep_search` 把丢掉的部分挖回来 ——
  成本是一次 `writeFile`，收益是展示「工具集的组合能力 > 单个工具的完备性」

## C 级（有意思但独立性不足）

- 「纯执行逻辑不到 100 行，剩下 3900 行都是 UI/流式/取消/编码」—— 一个关于
  「复杂度到底长在哪」的观察，适合作为开篇引子而非独立文章
- 把踩坑写成**独立档案**，再被代码注释与技术方案风险表**双向引用** —— 元层面的工程习惯，
  适合写进「团队知识沉淀」类文章，与 terminal 主题关系不大

---

## 建议的写作顺序

1. **A1**（四通道防挂死）—— 最具体、最容易验证、读者最容易立刻用上
2. **A2**（一致性拆两半）—— 承接 A1 的 env 部分，把它升格为原则
3. **A3**（解析式安全的证伪）—— 最有观点、也最容易引发讨论，放在有了前两篇的信任基础之后

B 级各点分散嵌入这三篇，或攒成一篇「抄代码时最容易抄错的几个地方」。
