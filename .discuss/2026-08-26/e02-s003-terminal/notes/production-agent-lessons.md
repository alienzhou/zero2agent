# 笔记：第六样本 —— 一个生产级桌面 Agent 产品的终端实现踩坑

> 调研日期：2026-08-29 ｜ 服务对象：E02-S003（terminal）
>
> **来源说明**：本篇材料来自一个**闭源的生产级桌面 Agent 产品**（下称「样本 F」）的内部实践，
> 已做匿名化处理 —— 不含产品名、仓库路径、提交号与内部平台信息，只保留可独立复述的
> 工程结论与推理链。凡涉及开源竞品的 `文件:行号` 均可公开核对。
>
> 与 [researches/terminal/](../../../../researches/terminal/README.md) 五竞品调研的关系：
> 那五家是**开源 CLI Agent**；样本 F 是一个**跨 macOS/Windows 分发的桌面 Agent 产品**，
> 架构上是「桌面壳 + 常驻本机服务进程（daemon）+ 多 Agent 后端适配」。
>
> 它的价值不是「再多一家竞品」，而是**验证哪些坑是结构性的、哪些只是分发环境带来的**。

## 一、先做归因：哪些坑 zero2agent 会碰到

样本 F 的坑几乎全部可归到**四个分发维度**：

1. daemon 由系统服务管理器 / 桌面壳启动 —— **不是从用户终端启动**
2. 跨 Windows 分发
3. 长驻进程 + 高频后台探测
4. 多 Agent 后端适配（同一套工具契约要翻译给若干不同后端）

zero2agent 在这四个维度上取值完全不同，所以大部分坑是**结构性不存在**，而非「暂时不做」。

| 样本 F 的坑 | 根因维度 | zero2agent 是否触发 |
|---|---|---|
| login shell env 采集（`-lc` + 脚本内 `source rc < /dev/null` + 去 ANSI + 超时用 SIGKILL） | ① 非终端启动 | ❌ 结构性不触发 —— 但**前提必须写进 spec** |
| Windows 上改用 PowerShell + Base64 编码传命令 + 强制 UTF-8 输出 | ② 跨 Win 分发 | ❌ 非目标 |
| 「后台探测」与「命令执行」必须分离的硬约束 | ③ 高频探测 | ❌ 无探测路径 |
| 用 env marker 精确标记并回收后代进程 | ③ 长驻、多实例、孙进程 reparent | ⚠️ **降级触发**：进程组够用 |
| 原生 PTY 模块的打包 / 跨平台预编译产物缺失 / 惰性加载 | 原生模块分发 | ❌ 不做 pty（T07 已定） |
| shim 注入时 PATH 变量名大小写与分隔符跨平台差异 | ② 跨平台 | ❌ |
| 命令解析式权限门禁膨胀到 700+ 行 | 真实审批产品需求 | ⚠️ Epic 3，但**负面结论要提前吸收** |
| 「输出是否被截断」拿不到结构化信号，只能从文本里嗅探 | ④ 多后端翻译 | ❌ 单实现 —— 但**反向是教学点** |
| `Promise.race` 竞出后未 `clearTimeout`，定时器泄漏 + 悬空 promise | 通用并发 | ✅ **必然触发**，S003 就要写超时 |
| `GIT_EDITOR=true` / `PAGER=cat` / `GIT_TERMINAL_PROMPT=0` 一类 env 注入 | 通用非交互 | ✅ **必然触发** |

### 最强的一条证据在最后两行

样本 F 与 Gemini CLI 是**不同团队、不同动机**（一个为 daemon 环境保真，一个为 shell 工具
防挂死），却**独立收敛到同一份 env 清单**。

这类**独立收敛项**的置信度远高于任何单家做法 —— 属于「不必再讨论，直接抄」。

## 二、三条五竞品调研里没有的新结论

### 结论 1：「杀进程」有两条完全不同的路径，抄错会出事

样本 F 有一次提交是**主动移除 SIGKILL 兜底**，理由写在代码注释里：「停机不因回收被拖住」。
而五竞品清一色是 SIGTERM→SIGKILL 升级。

**这不是矛盾，是两个场景**：

| 场景 | 目标 | 正确做法 |
|---|---|---|
| **单命令超时**（S003 要做的） | 必须确保这条命令死透，否则污染后续命令 | SIGTERM → 宽限期 → SIGKILL |
| **进程回收 / 停机**（样本 F 那条） | 不能拖住关键路径 | 只发 SIGTERM，剩下交 OS |

→ **S003 取前者。** 样本 F 那条结论不适用，但知道它存在，能防止将来 S004 做后台任务
清理时抄错方向。

**补充（S004 可直接参考）**：样本 F 的进程回收从「扫进程树」重写成「env marker 标记」。
旧方案两个致命缺陷 —— 主进程被杀后孙进程 **reparent 到 pid 1**，进程树断了扫不到（漏杀）；
同时会把 daemon 自身的其他子进程扫进来（误杀）。新方案是往子进程 env 注入一个 marker，
靠 env 继承自动传播，回收时按 marker 匹配。三个防事故细节：

- marker 值用**随机 UUID**，不是固定字符串 —— 否则同账号开两个实例，A 停机会杀掉 B 的进程
- 列进程时必须**禁用宽度截断**（`ps` 的 `-ww`）—— 否则长 env 里的 marker 被裁掉 → 静默漏杀
- **防自杀**：跳过自身 pid

### 结论 2：exit code 泄漏与 truncated 嗅探是同一个病 —— 「回执有两个出口」

- OpenCode V1 漏 exit code，根因是 `metadata` 与 `output` **两条路**，只有 `output`
  进模型（`shell.ts:585-593` + `message-v2.ts:292-295`）
- 样本 F 的「是否截断」靠字符串嗅探，根因是**跨层翻译**丢了结构化信号

同一个病：**信息在「出口分叉」处静默丢失。**

zero2agent 现有签名恰好只有一个出口：

```
// packages/core/src/tools/types.ts:21
execute: (input: Record<string, unknown>, ctx: ToolContext) => Promise<string>;
```

**这是现有架构的隐性优势，应该在 spec 里点明并守住。**

→ **T13 建议：不扩展返回侧。** 如需超时配置，只在**入参侧**（`ToolContext` 加可选
`defaultTimeoutMs`）；**坚决不加流式回调 / metadata 通道**。一旦回执有第二个出口，
OpenCode 那个 bug 在 zero2agent 就有了生存土壤。这条比「少写点代码」重要得多。

### 结论 3：「解析命令文本来做安全」是一条已被三方证伪的路

三份独立证据指向同一个负面结论：

- **OpenCode**：近 300 行 tree-sitter 抽路径，遇到 `$(...)` 动态展开时**放弃解析、
  命令照跑** → 安全感剧场
- **Gemini CLI**：检测到 `$(` / 反引号**直接拒绝不 spawn**（`shell.ts:468-478`）→
  诚实，但误伤大量合法命令
- **样本 F**：700+ 行权限门禁层层加码 —— 递归剥 `sudo` → 剥 `env VAR=value` 前缀 →
  剥 shell wrapper（含 `-lc` / `-xec` 这类组合 flag，`c` 在末尾）→ 按 `&& ; || |`
  切分复合命令 → 对每个子命令**再查一层 wrapper**（处理 `cmd1 && sh -c "cmd2"`）→
  另挖 `$()` 与反引号里的命令替换。代码注释自己写「**宁可误切也不漏放**」，
  **而最终仍然要靠人工审批兜底**

样本 F 花了 700+ 行走到最远，结论却是**换维度**而非继续加码 —— 命令黑名单只保留为
「穿透沙箱的最后一层硬门禁」（未命中就交回后端原生策略；即使用户开了完全放行模式，
黑名单依然生效），真正的边界是**人工审批 + 平台沙箱**。

加上它另一条决策（写在代码里的 DISABLED 注释）：

> 原设计：模型在命令调用中设置 `requires_approval=true` 表示该命令可能有风险，
> 即使用户配置了自动运行也应强制弹窗。
> **当前决策：不以模型自身的安全判断作为权限依据。**

**不把模型的自我风险评估当权限依据** —— 这句话在 Agent 安全这个话题上比任何解析器都重要。
（同向证据：Aider 的 `explicit_yes_required`，`io.py:866-867` —— 即使用户全局开了
`--yes`，模型建议的 shell 命令依然被拒。）

→ **T11/T12 建议：S003 一行命令解析都不写。** spec 里如实写「物理边界在此第一次失效」，
并把三方证据作为**为什么不补救**的论证。这比写 50 行半吊子解析有教育意义得多，也符合
前 7 个工具「边界要么真守住、要么明说守不住」的一贯诚实度。

## 三、对 S003 现有结论的补强

### 3.1 env 策略：样本 F 反证了「继承为默认」

[non-interactive-execution-env.md](./non-interactive-execution-env.md) 第二节已推出
「继承为默认，覆盖为例外」。样本 F 提供反向补强：它**确实构造过「清理型」env**
（显式删掉几个宿主环境注入的变量），但那纯粹因为它跑在桌面壳进程里、env 已被污染 ——
恰好反证「继承 + 定向覆盖」是对的，**只有被污染的宿主才需要额外删除**。

### 3.2 「用户终端启动」这个前提要升格为显式假设

建议 spec 原文写：

> 前提：Agent 由用户终端启动，`process.env` 已含 rc 成果。若跑在系统服务管理器 / CI 下
> 此前提失效 —— 那时需要「login shell env 采集」方案，含 4 个非直觉坑：
> ①用 `-i` 拿交互式环境会让 zsh **ignore SIGTERM**，采集超时后杀不掉；
> ②rc 里有读 stdin 的脚本（凭据代理、终端集成）会 **hang 死**，须 `source rc < /dev/null`；
> ③shell 主题输出的 **ANSI 序列污染 env 解析**，须去 ANSI + 分隔符夹住 env 区段；
> ④超时须用 **SIGKILL** 才杀得掉。

这一句把「简化」变成「**有条件的简化 + 已知的升级路径**」，是教学项目该有的姿态。

### 3.3 prompt 是执行环境的一部分

样本 F 有一条独有做法：Windows 编码问题**工程层修不干净**（旧式命令解释器用 OEM 代码页
输出，切换代码页也修不了管道解码），于是**注入一条 system prompt 规则**引导模型改用
不受影响的等价命令。

这与调研洞察 7（Gemini 把返回契约写进描述、OpenCode 把超时阈值写进描述）是同一原理的两面：

> **prompt 是执行环境的一部分，不是文档。**
> 当工程层的修复有残留时，提示词是一个正当的兜底层。

→ 工具描述必须写：默认超时值、截断阈值、`workdir` 替代 `cd`、降噪建议（`--no-pager`）、
以及「非交互环境，需要 tty 的命令会失败」。

### 3.4 落盘的独立论证（T05）

不必只靠「OpenCode / pi-mono 都做了」。zero2agent 已经有 `read_file` 和 `grep_search`
—— 落盘后模型能用**现有工具**把丢掉的部分挖回来。这是**工具正交组合的复利**，
成本一次 `writeFile`，教学价值是展示「工具集 > 单个工具」。

## 四、元层面：一个值得抄的做法

样本 F 里最值得抄的不是任何一段代码，而是这个：

它把一次线上事故写成了一份**独立的踩坑档案**，然后这份档案被**代码注释**（解释「为什么
这个平台上我们不做这件事」）和**技术方案的风险表**（列为已知风险 + 对策）**双向引用**。

踩过的坑不留在人脑里，而是变成一个可被 grep 到、被多处引用的锚点。

zero2agent 是教学项目 —— **这个做法本身就是可以教的内容**，而且 `.discuss/` + `specs/`
+ `retros/` 三层结构已经是它的雏形。
