# D04：生命周期 —— 常驻服务与孤儿进程

> 状态：✅ **已收敛**（14 项决策，6 个权衡点全部拍板）
>
> **前置**：③ 让进程可以留在后台继续活着（D03-12 的 Ctrl-S 跳过）。
> 本文回答紧接着的问题：**它什么时候死、由谁杀，以及 Agent 自己死的时候怎么办。**

## 一、问题：Agent 的视野边界

```
Agent 视野内                      Agent 视野外
─────────────────────────────    ──────────────────────────
terminal("npm run dev")
  └─ bash -c                     ← 我们 spawn 的，pid 已知
       └─ npm                    ← 孙进程
            └─ vite dev server   ← 曾孙，可能自己换了进程组
                 └─ esbuild      ← 曾曾孙

Ctrl-S 跳过 → Agent 继续干别的活
Agent 退出  → 这一串谁来收？
```

`terminal` 是**第一个会在自己返回之后仍然留下活物**的工具。前 7 个工具都是「调用—返回—结束」，
唯独它可能在回执写完之后，还有一整棵进程树在系统里跑着。

## 二、实证：四条逃逸路径，只有一条真逃

D01-4 定的 `detached: true` + `kill(-pid)` 打一遍（`/tmp/o2.mjs`）：

| 命令 | 孙进程 pgid | killpg 结果 |
|---|---|---|
| `sleep 30 &`（普通孙进程） | = 父 pgid | ✅ 已死 |
| `nohup sleep 30 &` | = 父 pgid | ✅ 已死 |
| `sleep 30 & disown` | = 父 pgid | ✅ 已死 |
| **`setsid sleep 30 &`** | **自成一组** | ❌ **逃逸**（`killpg` 报 ESRCH） |

⚠️ **反直觉结论：`nohup` 和 `disown` 都杀得掉。**

大家凭直觉以为 `nohup` 是「逃逸符」，但它改的是 **SIGHUP 的处置方式**；
`disown` 改的是 **shell 的 job 表**。两者**都不改进程组**，所以 `killpg` 照样打得到。

真正能逃的只有 `setsid` —— 它调 `setsid(2)`，把自己变成**新 session 的组长**，
从此不在我们那个进程组里。

> 📌 **教学点：「后台」这个词在 shell 里至少有四种不同的实现，它们的可杀性完全不同。**
> 不实测一遍，凭词感会把 `nohup` 当成最危险的那个 —— 实际上它最无害。

## 三、更狠的：同一个 `setsid` 还会让 Agent 挂死

这是 Codex 调研里那个被标为「本次调研最有价值的单点发现」的坑
（`core/src/exec.rs:82-89`、`researches/terminal/codex.md:702`）。**本机复现了：**

| 场景 | killpg 后 `stdout` 的 `end` 事件 | `child` 的 `close` 事件 |
|---|---|---|
| 孙进程继承 stdout | ✅ 触发 | ✅ 触发 |
| 孙进程重定向 `/dev/null` | ✅ 触发 | ✅ 触发 |
| **`setsid` 且继承 stdout** | ❌ **永不触发** | ❌ **永不触发** |

**「进程杀了 ≠ 管道关了」。** 那个逃逸的曾孙攥着继承来的 stdout 写端，于是：

```
     我们 kill(-pid)
          │
          ├─→ bash 死了
          └─→ setsid 出去的曾孙活着，还握着 stdout 写端
                          │
                    管道永不 EOF
                          │
              child.on('close') 永不触发
                          │
            execute() 的 Promise 永不 resolve
                          │
                  ⚠️ 整个 Agent loop 挂死
```

⚠️ **同一个 `setsid` 同时捅穿两道防线**：既逃了 `killpg`，又挂死了 loop。

而 D01-5 定的单出口 `Promise<string>` 在这里显出它的**代价**：它不 resolve，整条链就停在那儿。
→ **单出口是个好约束，但它要求「一定要有出口」这件事必须由我们自己保证**（见 §5.4 防线③）。

## 五、方案：三道防线

### 5.1 三道防线对应三种死法

```
                     Agent 正常退出            Agent 被 SIGKILL           Agent 还活着
                     （用户 Ctrl-C / 跑完）    （kill -9 / OOM / 崩溃）   （进程自己不退）
                            │                        │                        │
   防线①  退出钩子      ✅ 遍历登记表逐个杀       ❌ 钩子根本不执行         ——
          (exit hook)
                            │                        │                        │
   防线②  watcher      ——                      ✅ 轮询发现父没了 → 自杀    ——
          (方案 D)                                 ⚠️ 有 1 秒延迟窗口
                            │                        │                        │
   防线③  读取侧超时    ——                      ——                      ✅ 2 秒排空后强行 resolve
          (I/O drain)                                                        防 setsid 挂死
```

⚠️ **三道防线不是「重复保险」，是各自覆盖一种 Agent 无法预期的死法。**

- ① 管不了被强杀 —— 因为进程已经没机会执行任何代码了
- ② 管不了曾孙 —— 它只覆盖我们直接 spawn 的那个 bash 及其进程组
- ③ 管的**根本不是杀进程**，而是「别让自己挂住」

> 📌 **教学点：防线要按「失败模式」分类，不是按「措施」分类。**
> 三个措施看起来都在「收拾进程」，但只要问一句「Agent 是怎么死的」，
> 就会发现它们互相**完全不能替代**。

### 5.2 防线①：进程登记表 + 退出钩子

```
┌─────────────────────────────────────────────┐
│  registry: Map<pid, entry>                  │
│  ┌────────┬──────────┬─────────┬─────────┐  │
│  │  pid   │ command  │ logPath │ startAt │  │
│  ├────────┼──────────┼─────────┼─────────┤  │
│  │ 12345  │ npm run… │ /tmp/…  │ 21:04   │  │  ← ③ 的 Ctrl-S 跳过时登记
│  └────────┴──────────┴─────────┴─────────┘  │
└─────────────────────────────────────────────┘
        │                          │
   进程自然退出 → 摘除          Agent 退出 → 询问 → killpg
```

**只有被 Ctrl-S 跳过的才进表。** 正常跑完的命令进程已经没了，登记它没有意义。
→ 登记表的大小 = 用户按过多少次 Ctrl-S，通常是 0 或 1。**这不是一个需要考虑规模的数据结构。**

### 5.3 防线②：watcher 包装（决策 1 = 方案 D）

Codex 用 Rust 直接调 `prctl(PR_SET_PDEATHSIG)`。
**Node 的 `child_process.spawn` 没有这个 option**（实测确认：`/usr/include/linux/prctl.h:9`
定义了 `PR_SET_PDEATHSIG`，但 Node API 不暴露）。

四个选项及取舍：

| 选项 | 代价 |
|---|---|
| A. 不做 | Agent 被 `kill -9` 时留下孤儿 —— **这是个真漏洞** |
| B. 装 native 依赖 | 教学项目引入编译期依赖，`npm install` 可能失败 —— **违背零依赖基调** |
| C. `bash -c 'prctl…'` | 需要 `prctl` 命令行工具，不是所有发行版都有 |
| **D. 纯 JS 变通（定案）** | 子 shell 里跑 watcher 轮询父 pid，没了就自杀。零依赖，代价是**污染用户命令** |

**定案的 wrapper 形状：**

```bash
( while kill -0 $AGENT_PID 2>/dev/null; do sleep 1; done; kill -- -$$ 2>/dev/null ) >/dev/null 2>&1 &
_w=$!
<用户命令>
__code=$?
kill $_w 2>/dev/null
exit $__code
```

**实测验证（`/tmp/w3.mjs`）：**

```
=== A. 退出码 / 输出保真 ===
  echo hi                          code=0    ✅ out="hi"
  exit 42                          code=42   ✅
  nosuchcmd_xyz                    code=127  ✅ out="bash: line 2: nosuchcmd..."
  echo out; echo err >&2; exit 3   code=3    ✅ out="out\nerr"

=== B. kill -9 假 agent 之后 ===
  孙进程存活=false  ✅ watcher 收掉了
```

#### 5.3.1 ⚠️ 一个必须记录的坑：watcher 自己会挂死 loop

**第一版 wrapper 直接把测试跑成了 2 分钟超时。**

```
watcher 继承 stdout        → close 事件 TIMEOUT   ❌ 挂住了
watcher 重定向 /dev/null   → close code=42        ✅
```

原因**正是 §三那个坑**：watcher 是个后台子 shell，它攥着继承来的 stdout fd，
用户命令退出了它还活着 → 管道永不 EOF → `close` 永不触发。

→ **`>/dev/null 2>&1` 不是「顺手加的」，是必需的。**

> 📌 **教学点：防御措施自己成了故障源。**
> 我们为了防孤儿进程加了 watcher，而这个 watcher 第一时间踩了我们自己刚记录下来的坑。
> ⚠️ **凡是「我们注入进用户命令里的东西」，都要按「一个可能逃逸的孙进程」来审视。**

#### 5.3.2 wrapper 的三个已知代价（如实记录）

| 代价 | 说明 |
|---|---|
| **1 秒延迟窗口** | 轮询间隔 1 秒，Agent 被强杀后最长 1 秒内孤儿仍存活。可接受 —— 它最终会死 |
| **行号偏移** | `nosuchcmd_xyz` 的报错从 `bash: line 1:` 变成 `line 2:`（wrapper 占了第一行）。→ **D01-11「错误消息不泄漏内部包装」要跟着处理行号** |
| **污染用户命令** | 与 Gemini 的 `_bgpids_file` wrapper 同类问题。Gemini 的对策是 `result.error.message.replaceAll(commandToExecute, params.command)`（`shell.ts:807-808`），我们照做 |

### 5.4 防线③：读取侧超时

```
  close 事件与 2 秒计时器竞速
      │
      ├── 等 close 事件 ────────┐
      │                        │  正常情况 <10ms
      └── 同时起 2 秒计时器 ────┤
                               ▼
                    先到者胜（Promise.race）
                               │
              ┌────────────────┴────────────────┐
              │                                 │
        close 先到                        2 秒先到
        （99.9%）                    （有 setsid 曾孙攥着 fd）
              │                                 │
        正常组装回执                 强行 resolve + 回执加一行：
                                    ⚠️ Note: a descendant process may
                                       still be holding the output pipe.
                                       Output may be incomplete.
```

⚠️ **那一行必须写进回执**：否则模型收到一份「看起来正常」的输出，
不知道后面可能还有内容 —— 这正是 D01-7 那条「不能让模型 debug 一个不存在的问题」的同类。

## 六、六个权衡点的拍板

### 6.1 决策 1：PDEATHSIG → **方案 D（watcher 包装）**

见 §5.3。选 D 而非 A（认漏洞）的理由：**「Agent 被 kill -9」不是罕见场景** ——
OOM、用户不耐烦、CI 超时都会走到那儿。而代价（1 秒窗口 + 命令包装）都是可控且可如实说明的。

### 6.2 决策 2：**不给模型 list 工具**

Codex / Gemini 都不给，理由是「怕诱导 poll」。**我们不给，但理由更硬：**

| 问 | 答 |
|---|---|
| 模型什么时候需要「有哪些后台任务」？ | 它自己起的那几个，**pid 已经在回执里了**（D03 §5.5.4） |
| 那 list 能给它什么**新**信息？ | **只有「别人起的」** —— 上一轮会话、另一个 Agent 实例起的 |
| 模型该管别人起的进程吗？ | ❌ **不该。** 它没有那个上下文，杀错了后果由人承担 |

→ **list 的唯一增量信息，恰好是模型不该碰的那部分。**

⚠️ 这比「怕它 poll」硬得多：**poll 是行为问题**（可以用 prompt 约束），
**越权是能力边界问题**（只能用不给来约束）。

⚠️ **但「有哪些后台任务」是人的关切**，所以 TUI 侧要能看到 ——
走 `LoopEventHandlers` 事件通道（同 D03-5），**能力做，只对人开放**。
→ 与两家殊途同归，但推理路径不同，这个差异本身值得写进教学。

### 6.3 决策 3：Agent 退出时 **询问，不默认杀**

这条最纠结，因为**跳过的语义本来就是「让它继续跑」**。

| 选项 | 后果 |
|---|---|
| A. 一律杀 | 用户跳过 `npm run dev` 是想让 dev server 起着，退出 Agent 就杀掉 —— **违背跳过的初衷** |
| B. 一律不杀 | 孤儿满地。跑十次测试留十个 orphan |
| **C. 退出时问一句（定案）** | 多一次交互，但**语义最诚实** |

```
还有 2 个后台命令在运行：
  [12345] npm run dev      （已运行 4m12s）
  [12389] tail -f app.log  （已运行 1m03s）
要一并结束吗？(y/N)
```

→ **判据与 ③ 同源：「该不该活下去」这个判断只有人能做。**
③ 里「要不要继续等」交给人，④ 里「要不要留下来」同样交给人。

⚠️ **非 TTY 下退化为 B（不杀）。** 理由：非 TTY 环境（CI）里默认杀更危险 ——
CI 脚本可能故意留一个服务给后续步骤用。**不杀会留孤儿，但杀错会破坏流程**，
两害相权取其轻，且 CI 本来就该在外层做进程清理（同 D03 §5.5.8 的立场）。

### 6.4 决策 4：落盘文件 **不清理**，交 `/tmp` 系统回收

D03-4b 留的那个缺口（`yes` 类命令让 `/tmp` 无限增长）。三个选项：

| 选项 | 代价 |
|---|---|
| A. 落盘设上限（如 100MB） | 输出不完整 —— **且与 ② 的「不截断」立论产生张力，要额外解释** |
| B. Agent 退出时删掉所有落盘文件 | 用户事后想看日志就没了；且跳过的命令**可能还在写** |
| **C. 不管，交 `/tmp` 系统回收（定案）** | 单次会话内理论上可能撑爆磁盘 |

**定案 C。** 理由：
1. 这是 `/tmp` 这个目录**本来就该负责的事** —— 所有主流系统都有 tmp 清理策略
2. 触发条件极端（要故意跑 `yes` 类无限输出命令）
3. **A 会引入一个需要长篇解释的例外**（「磁盘上限不算截断」），教学成本高于它防住的风险

⚠️ **如实记录这是个已知风险，不是已解决的问题。** 与 D02-10（二进制嗅探）同样的处理方式：
**明示缺口 > 假装解决。**

### 6.5 决策 5：完成通知 **搭 `terminal` 回执的便车**

三个选项各有死穴：

| 选项 | 死穴 |
|---|---|
| A. 完全不通知 | 模型如果忘了自己跳过过命令，那个结果**永久丢失** |
| B. 注入系统消息 | 要改 loop 的消息组装 —— **动 Epic 1 地基**，且会打断模型当前推理链 |
| C. 只给人看 | 同 A 的问题，只是人能兜 |

**定案：C + 一条补丁 —— 把「已完成的后台任务」写进下一次 `terminal` 调用的回执尾部。**

```text
Exit code: 0
Output:
...

---
Note: 1 earlier background command has finished.
  npm run build (pid 12345) → exit 0, 340 lines at /tmp/zero2agent-a3f9c1b2.log
```

四个理由：

| 理由 | 说明 |
|---|---|
| **不动地基** | 只是 `terminal` 自己的回执多一段，`execute` 仍是 `Promise<string>` 单出口（D01-5 不破） |
| **不打断推理链** | 模型正在调 `terminal`，说明它正在「做事」，这时接收执行类信息是自然的 |
| **不会漏** | 只要模型还在用 `terminal`，迟早看到 |
| **零额外成本** | 不需要新通道、新工具、新事件 |

⚠️ **代价**：模型跳过命令后若再也不调 `terminal`，这条通知同样丢失。
但那种情况下**它本来也不关心** —— 而人在 TUI 里看得到。

> 📌 **可复用判据：新信息优先搭已有通道的便车，而不是开新通道。**
> 这与 D03-5（跳过提示走既有 `LoopEventHandlers`）、D03-3（回读走既有 `read_file`）
> 是同一条判据的第三次应用。

### 6.6 决策 6：**全部放 S003**

⚠️ **这推翻了 D03-7**（③ 刚把「进程登记表 / 完成通知」划给 S004）。

S003 的最终范围：

| 内容 | 原划归 | 现划归 |
|---|---|---|
| 防线① 退出钩子 + 退出询问 | —— | **S003** |
| 防线② watcher 包装 | —— | **S003** |
| 防线③ 读取侧 2 秒超时 | —— | **S003** |
| 进程登记表 | S004（D03-7） | **S003** |

→ **S004 只剩「交互式」**（stdin 续写、pty），判据回到 D03 §五那句

#### 6.6.1 ⚠️ 这是第二次重画 S003/S004 的线，而且两次方向相同

| 时点 | 动作 |
|---|---|
| roadmap D04 原划 | S003 只做短命令，长时间 / 阻塞 / 交互全给 S004 |
| D03 §五 第一次重画 | **慢命令从 S004 拉进 S003**（判据换成「要不要人输入」） |
| D04 §6.6 第二次重画 | **生命周期从 S004 拉进 S003**（本节） |

为什么两次都往里拉、而不是往外推：

> **因为「一个问题该放哪一章」的判据不是工作量，是它和已有内容的耦合度。**
> 生命周期问题**完全由 ③ 的「让进程活下来」制造出来** ——
> 把它推给 S004，读者读完 ③ 会立刻问「那它什么时候死」，而书里没有答案。
> ⚠️ **一个自己制造的问题，不能留给下一章。**

反过来，「交互式」不是 S003 制造的 —— 它是一类**独立存在的命令**，
不学 S003 也存在。**这条线才是真的。**

## 八、教学价值

1. **「后台」在 shell 里有四种实现，可杀性完全不同** —— 实测 `nohup` / `disown` 都杀得掉，
   只有 `setsid` 能逃（§二）。⚠️ **凭词感会把最无害的当成最危险的。**
2. **「进程杀了 ≠ 管道关了」** —— 逃逸的曾孙攥着继承来的 stdout fd，
   `close` 事件永不触发，Promise 永不 resolve，**整个 Agent 挂死**（§三）。
   这是终端工具最隐蔽的坑，Codex 专门为它加了 `IO_DRAIN_TIMEOUT_MS`。
3. **单出口约束的代价在这里第一次显形** —— D01-5 的 `Promise<string>` 很干净，
   但它要求「**一定要有出口**」由我们自己保证。→ **好的约束不会自动成立，它需要被守卫。**
4. **防线要按「失败模式」分类，不是按「措施」分类** —— 三道防线看起来都在收拾进程，
   但问一句「Agent 是怎么死的」（正常退出 / 被强杀 / 没死），
   就会发现它们**互相完全不能替代**（§5.1）。
5. **防御措施自己成了故障源** —— 为防孤儿加的 watcher，第一时间踩了我们自己刚记录的坑
   （§5.3.1）。⚠️ **凡是注入进用户命令的东西，都要按「一个可能逃逸的孙进程」来审视。**
6. **「不给模型某个能力」要区分行为问题和边界问题** —— 竞品不给 list 是怕 poll（行为，
   可用 prompt 约束）；我们不给是因为 list 的增量信息恰好是**模型不该碰的别人的进程**
   （边界，只能靠不给）。⚠️ **同一个结论，理由的硬度可以差很远。**
7. **「该不该活下去」只有人能判断** —— ③ 把「要不要继续等」交给人，
   ④ 把「要不要留下来」交给人（§6.3）。**同一条判据在两个议题里各用一次。**
8. **新信息优先搭已有通道的便车** —— 完成通知搭 `terminal` 回执，
   而不是开新事件 / 新工具 / 改 loop（§6.5）。这是该判据的第三次应用
   （前两次：D03-5 走既有事件通道、D03-3 走既有 `read_file`）。
9. **「这个问题该放哪一章」的判据是耦合度，不是工作量** —— 生命周期问题
   **完全由 ③ 自己制造出来**，推给下一章会让读者读完 ③ 就卡住（§6.6.1）。
   ⚠️ **一个自己制造的问题，不能留给下一章。** 而「交互式」不是 S003 制造的，
   它独立存在 —— **那条线才是真的。**
10. **明示缺口 > 假装解决** —— `setsid` 逃逸（D04-2）、磁盘撑爆（D04-11）
    都选择如实记录而非勉强修补。⚠️ 判据是**修补的复杂度与教学价值不成比例**：
    递归扫 `/proc` 找逃逸进程能写，但它会让这一章的重点从「理解生命周期」
    变成「一个大工程」。

## 九、S003 至此闭环

五个议题走完四个，`terminal` 的完整生命周期已经封闭：

```
①  起进程、定回执           →  信息进上下文的规则
②  输出太多怎么办           →  落盘 + 渐进式披露
③  时间太久怎么办           →  跳过/取消 + 后台化
④  进程活下来之后怎么办      →  三道防线 + 登记 + 退出询问
⑤  这一切跑在什么环境里      →  能力继承 + 呈现覆盖（见 D05）
```

⚠️ ①→④ 讲的都是「**Agent 与一个它不写的程序之间的边界**」，
⑤ 换一个角度：**这个程序跑在什么环境里，以及那个环境和用户自己的终端有什么不同。**
