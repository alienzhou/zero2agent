# D05：执行环境 —— 子进程跑在什么世界里

> 议题 ⑤｜覆盖：T06（env 规格化）、T07（不做 pty）、T03 关联项｜**S003 最后一个议题**
>
> 状态：✅ **已收敛**（12 项决策，6 个权衡点全部拍板）
>
> **前置**：①—④ 讲的都是「Agent 与一个它不写的程序之间的边界」。
> 本文换一个角度：**那个程序跑在什么环境里，以及那个环境和用户自己的终端有什么不同。**

## 一、问题：两个「不同」，方向相反

用户在自己终端里敲 `npm run build` 能跑通，Agent 调 `terminal("npm run build")` 却报
`npm: command not found` —— 这是**能力不一致**，是 bug。

反过来，用户敲 `git log` 看到彩色分页，Agent 调 `terminal("git log")` 如果也拿到分页器
和 ANSI 色码，那是**呈现不一致的缺失**，同样是 bug。

```
                    用户的终端                Agent 的子进程
                    ─────────                ──────────────
 能力（PATH / 版本管理器 / locale）   ●━━━━━━━━━━━━━●   必须一致  ← 不一致就是 bug
 呈现（颜色 / 分页 / 凭据弹窗）        ●             ○   必须不同  ← 一致才是 bug
```

⚠️ **「和用户终端保持一致」这句话本身是错的**，它把两件方向相反的事说成了一件。
正确的表述是：

> **能力必须一致（继承），呈现必须不同（覆盖）。**

这是本议题的总纲，后面所有决策都是它的推论。

> 📌 **教学点：需求里出现「保持一致」时，先问「一致的是哪个维度」。**
> 这四个字在本议题里同时是**目标**和**反目标**，取决于说的是能力还是呈现。

## 二、能力一致：`process.env` 靠不住

### 2.1 一条被自己证伪的推理

`outline.md` 的 T03 条目里原本写着（**本轮推翻**）：

> `bash -c` 是 non-login non-interactive，不读 `.bashrc` / `.zshrc`。
> **但 Agent 进程通常由用户终端启动，`process.env` 已含 rc 处理后的 `PATH`**，
> 所以继承 env 即可，无需加载 rc。

前半句对，后半句错。「Agent 进程通常由用户终端启动」这个前提**在下列场景全部不成立**：

| 启动方式 | 父进程是谁 | rc 读过吗 |
|---|---|---|
| 桌面 App 双击图标 | Finder / launchd / Explorer | ❌ |
| 系统服务 | systemd / launchd | ❌ |
| CI 作业 | runner daemon | ❌ |
| 定时任务 | cron（PATH 通常只有 `/usr/bin:/bin`） | ❌ |
| 用户终端里敲命令 | 用户的 shell | ✅ |

**五种里只有一种成立。**

### 2.2 实测：差多少

模拟一个非 login 的父进程，PATH 只有系统最小集（`/tmp/h1.sh`）：

```
env -i PATH=/usr/bin:/bin bash -c 'bash -c  "echo $PATH"'
  → PATH=/usr/bin:/bin

env -i PATH=/usr/bin:/bin bash -c 'bash -lc "echo $PATH"'
  → PATH=/home/…/.npm-global/bin:/home/…/.local/bin:/usr/bin:/bin
```

差的正是**用户自己装的一切** —— 全局 npm 包、`~/.local/bin`、版本管理器。
在这种环境下 Agent 连 `node` 都可能找不到。

> 📌 **教学点：一条推理错了，往往不是逻辑错，是它的前提被默认成了普遍情况。**
> 「Agent 由终端启动」在写代码的人身上是 100% 成立的 —— 因为他一直在终端里 `npm run dev`。
> ⚠️ **自己的开发环境是最容易被误当成普遍情况的那个前提。**

### 2.3 做法：起一次 login shell，把 env 捞回来

```
   Agent 启动
       │
       ▼
  spawn( $SHELL, ['-lc', 'echo -n DELIM; command env; echo -n DELIM'] )
       │                    ── 它会读 .profile / .zprofile / .zlogin ──
       ▼
  按 DELIM 切出中段 → 解析成 Map → 模块级缓存（进程内一次）
       │
       ▼
  之后每次 terminal 调用：spawn('bash', ['-c', cmd], { env: 缓存 + 覆盖项 })
```

⚠️ **注意 spawn 的仍然是 `bash -c`，不是 `bash -lc`。**
`-l` 只在**采集那一次**用；执行用户命令时依然是 non-login non-interactive（D01-1 不破）。

→ **「读 rc」和「执行命令」被拆成了两件事。**
这样每条命令不必重复付 rc 的启动开销，也不会被 rc 的副作用（`cd`、`alias`、欢迎语）污染。

### 2.4 三个必踩的坑（实测）

#### 坑 1：rc 会往 stdout 打字，把 `env` 输出污染掉

```
.profile 里写了 echo "欢迎回来！今天天气不错"
  ↓
bash -lc 'command env' 的输出：
  欢迎回来！今天天气不错     ← 混进来了
  MYVAR=ok
  PWD=/home/…
```

`echo "Welcome"`、`neofetch`、`fortune`、各种 shell 框架的启动横幅都会干这个。
**解法：前后各打一个分隔符，只取中段。**

```javascript
const D = '__Z2A_ENV__';
const out = execFileSync(shell, ['-lc', `echo -n "${D}"; command env; echo -n "${D}"`], …);
const body = out.split(D)[1];   // ← 欢迎语留在 [0] 里，被丢掉
```

实测验证（`/tmp/*.mjs`）：

```
解析出的变量: MYVAR, PWD, HOME, SHLVL, PATH, HISTIGNORE, _
被丢掉的段  : "欢迎回来！今天天气不错"      ✅
```

⚠️ 用 `command env` 而不是 `env` —— 前者绕过用户可能定义的 `env` 函数/别名。

#### 坑 2：rc 里有 `read`，采集会永久挂住

```
.profile 里有一行 read x
  ↓
stdin 是永不 EOF 的管道  → timeout 3 秒后 exit=124   ⚠️ 挂死
stdin 接 /dev/null       → 立刻拿到 EOF，正常返回     ✅
```

⚠️ **这与 D01-2「`stdin: 'ignore'`」是同一条防线的第二次应用** ——
只不过那次防的是**用户命令**，这次防的是**用户的 rc 文件**。

> 📌 **教学点：我们注入进流程的每一步，都要按「用户命令」的标准来防。**
> 这是 D04-6（watcher 必须重定向）之后，同一条判据的第二次兑现。

#### 坑 3：采集本身要有超时

rc 里可能有网络请求（检查更新、拉配置）。采集是**启动路径**，卡住等于 Agent 起不来。

```javascript
execFileSync(shell, ['-lc', cmd], {
  timeout: 5000,
  killSignal: 'SIGKILL',   // ← 不是 SIGTERM
  stdio: ['ignore', 'pipe', 'ignore'],
})
```

⚠️ **`killSignal: 'SIGKILL'` 不是保守起见。** 交互式 zsh 会忽略 SIGTERM
（这正是 D01-1 拒绝 `-i` 的理由之一），超时了却杀不掉，就从「慢」变成了「挂死」。

### 2.5 简化版的诚实代价：zsh 用户的 `.zshrc` 读不到

这是本章**最需要如实交代**的一处。zsh 的启动文件矩阵实测（`/tmp/*.sh`）：

| 文件 | `zsh -lc` | `zsh -c` |
|---|---|---|
| `.zshenv` | ✅ | ✅ |
| `.zprofile` | ✅ | ❌ |
| **`.zshrc`** | ❌ | ❌ |
| `.zlogin` | ✅ | ❌ |

⚠️ **`.zshrc` 是唯一两种都读不到的**，而它恰恰是**用户实际写东西的那个文件**。
本机 `.zshrc` 第 106–108 行就有 nvm 的初始化。

bash 侧看起来没事，但那是**运气**：

```
裸 .bashrc                     → bash -lc 读不到    ❌
.profile 里有 . ~/.bashrc      → 读到了              ✅
```

Debian/Ubuntu 的默认 `.profile` 自带这行转发，所以大部分 Linux 用户碰不到。
**macOS 的默认 zsh 没有对应的转发。**

**补救一行就够：**

```javascript
const rc = shell.includes('zsh') ? '~/.zshrc' : '~/.bashrc';
const cmd = `[ -f ${rc} ] && source ${rc} < /dev/null; echo -n "${D}"; command env; echo -n "${D}"`;
```

实测 `source ~/.zshrc < /dev/null` 后 `.zshrc` 里的变量出现了。
⚠️ 那个 `< /dev/null` 就是坑 2 的第三次兑现 —— **单独给 source 再关一次 stdin**，
因为 rc 可能自己重开输入。

**仍然不覆盖的（明示缺口，不实现）：**

| 缺口 | 真实产品要做什么 |
|---|---|
| rc 输出带 ANSI 色码 | 解析前 strip ANSI |
| shell 框架自动更新阻塞 | 注入框架特定的禁用变量（更新提示、tmux 自启等） |
| Windows PowerShell | 完全另一条代码路径 + 编码处理 |
| 多字节/换行值的 env | `env -0` 用 NUL 分隔 |

> 📌 **教学点：一个「简化实现」合格的标准，是它把没做的部分写清楚。**
> ⚠️ 这与 D02-10（二进制嗅探）、D04-2（`setsid` 逃逸）、D04-11（磁盘）
> 是**同一条原则的第四次应用**：**明示缺口 > 假装解决。**

### 2.6 采集失败怎么办

| 做法 | 问题 |
|---|---|
| 静默回退 `process.env` | 模型撞上 `command not found` 会去 debug 一个**不存在的问题** |
| 启动时报错退出 | 太激进 —— 很多环境下裸 `process.env` 完全够用 |
| **回退 + 首次回执告知（定案）** | 模型知道「工具链可能不全」，能自己调整策略 |

```text
Exit code: 127
Output:
bash: line 1: pnpm: command not found

Note: could not load your shell profile; PATH may be incomplete.
```

⚠️ 关键在于**这条信息必须让模型看见**。写进日志、`process.emitWarning`
都只有开发者能看到 —— 而需要据此改变行为的是模型。

→ 判据来自 **D01-7「不能让模型 debug 一个不存在的问题」**，这是第三次应用
（前两次：exit code 无条件写、signal 如实透传）。

## 三、呈现不同：定向覆盖

### 3.1 四道防线里 env 是第三道

D01 已经定下防卡死的四道防线，env 注入是其中第三道：

```
① stdin: 'ignore'   → 从 stdin 读的程序立刻拿到 EOF
② 不给 pty          → isatty() === false，程序普遍自动降级
③ env 注入          → 拦住绕过 stdin 直接开 /dev/tty 的（git/ssh 凭据）  ← 本节
④ 超时兜底          → 前三道漏掉的最终保险
```

⚠️ **第③道存在的理由，正是第①道拦不住的那类程序。**
`git` 要密码时不读 stdin，它直接 `open("/dev/tty")` —— 关 stdin 对它毫无作用。

### 3.2 覆盖清单

| 变量 | 值 | 防什么 |
|---|---|---|
| `PAGER` / `GIT_PAGER` | `cat` | less 等分页器占住终端 |
| `GIT_TERMINAL_PROMPT` | `0` | git 凭据交互 |
| `GIT_EDITOR` | `true` | `git commit` 拉起 vim |
| `GIT_ASKPASS` / `SSH_ASKPASS` | `''` | 图形凭据弹窗 |
| `DISPLAY` | `''` | 兜底断掉图形程序的显示目标 |
| **`TERM`** | **`dumb`** | 见 §3.3 |

竞品实证：Gemini 的同类清单在
`services/shellExecutionService.ts:490-492, 512-521`（`TERM=xterm-256color`、
`PAGER=cat`、`GIT_PAGER=cat`、`GIT_TERMINAL_PROMPT=0`、`GIT_ASKPASS=''`、
`SSH_ASKPASS=''`、`GH_PROMPT_DISABLED=1`、`GCM_INTERACTIVE=never`、
`DISPLAY=''`、`DBUS_SESSION_BUS_ADDRESS=''`）。

⚠️ 注意 `GIT_EDITOR=true` 的巧妙之处：`true` 是个**立刻成功退出的命令**。
git 以为编辑器正常返回了，于是用默认 commit message 继续 —— 不报错、不卡住。

### 3.3 `TERM` 设成什么：唯一和竞品分道的一条

**实测三种取值（`/tmp/term.sh`）：**

| `TERM` | `tput cols` | `tput setaf 1` | `clear` | |
|---|---|---|---|---|
| **`dumb`** | 80 | （空） | （空） | ✅ 干净降级 |
| `xterm-256color` | 80 | `^[[31m` | `^[[H^[[2J^[[3J` | ⚠️ 吐转义序列 |
| **未设置** | ❌ 报错 | ❌ 报错 | ❌ 报错 | ❌ **命令直接失败** |

**三条结论，按重要性排序：**

1. ⚠️ **「不设」是最差的选项，而它恰好是「什么都不做」的结果。**
   `tput` / `clear` 直接失败 —— 这不是「少了点颜色」，是**命令执行不成功**。
   → **这一条本身就让 `TERM` 从「可选优化」变成了「必须处理」。**

2. `dumb` 优于 `xterm-256color`：让 terminfo 层面就查不到这些能力，
   比事后过滤转义序列干净。

3. **Gemini 用 `xterm-256color` 的理由在我们这儿不成立** ——
   它走 node-pty，内部挂了一个 headless 终端模拟器
   （`services/shellExecutionService.ts:977-983`），**需要一个真终端类型来驱动那个 emulator**。
   我们 T07 明确不做 pty，那个前提没有了。

#### 3.3.1 但必须写清 `TERM` 防不住什么

```
git -c color.ui=always log --oneline -1
  TERM=dumb            → ^[[33m55196b3^[[m    ← 照样上色
  TERM=xterm-256color  → ^[[33m55196b3^[[m
```

**TERM 拦不住铁了心要上色的程序。** 真正在起作用的是第②道防线
（`isatty() === false`，程序自己降级），`TERM` 只是补充。

对照实测：`git log`、`git status`、`git diff --stat`、`ls --color=auto`
在两种 `TERM` 下**输出完全相同** —— 因为它们看的是 TTY，不是 `TERM`。

> 📌 **教学点：一个措施要说清它防住了什么、防不住什么。**
> 只写「我们设了 `TERM=dumb` 来避免色码」是不诚实的 ——
> 它真正解决的是 `tput`/`clear` 报错，色码那部分主要是第②道防线的功劳。
> ⚠️ 这与 D03 §6.4 拆解「兜底」是同一种动作：**把一个笼统的措施拆到能追责为止。**

### 3.4 不做 `NO_COLOR`

`NO_COLOR=1` 看起来该加，但**不加**：

- 第②道防线（非 TTY）已经让绝大多数程序不上色了
- 它是个**约定**而非标准，遵守程度参差
- 而铁了心上色的（`color.ui=always`）它同样拦不住

→ **一个既非必要、又不充分的措施，加了只会让人以为色码问题解决了。**

## 四、第三类变量：宿主污染（不实现，但要讲）

前面两类问的都是**「这个变量有没有用」**。第三类问的是另一个问题：

> **它是谁塞进来的？**

宿主进程 —— 桌面应用外壳、systemd、CI runner —— 会往环境里塞自己需要的东西。
那些东西**对宿主是必需的，对子进程是有害的**：

| 典型 | 危害 |
|---|---|
| 桌面外壳注入的 node 行为开关 | 子进程里的 `node` 行为异常 |
| 容器/服务管理器的运行时目录 | 权限不匹配，程序报莫名其妙的错 |
| CI runner 的内部变量 | 泄漏进用户命令，或干扰工具链判断 |

⚠️ **这类变量有一个共同特征：它们不在用户的 rc 里，也不是我们注入的 ——
它们凭空存在，且只在特定分发形态下存在。**

**zero2agent 不实现它。** 因为它是 CLI 启动的，压根不会遇到。做了就是屠龙之技。

**但这个判据要讲**，因为它是三类里唯一一个**不看变量本身、只看来源**的：

```
第一类  能力  →  问「有没有用」   →  继承
第二类  呈现  →  问「有没有用」   →  覆盖
第三类  污染  →  问「谁塞的」     →  删除     ← 判据换了个维度
```

> 📌 **教学点：当你把 Agent 装进一个壳里（桌面 App、服务、CI），
> 你继承的就不再只是"用户的环境"，还有"壳自己的环境"。**
> 读者以后真的做这件事，会立刻想起这一节。

## 五、六个权衡点的拍板

### 5.1 决策 1：**做采集，但只做简化版**

不做（A）不行 —— 这是本议题唯一一个**不做就真的会坏**的问题（§2.2 实测）。

照抄生产实现（B）也不行 —— 那份实现 300+ 行，处理 zsh 交互模式、SIGTERM 忽略、
stdin 挂死、框架自动更新阻塞、Windows 编码……**代码量超过 `terminal` 工具本身**，
会让读者以为这一章讲的是 shell 兼容性。

**定案 C+：`$SHELL -lc` + 显式 `source rc` + 分隔符 + 超时，约 25 行；
没覆盖的部分在 §2.5 逐条列出。**

→ 这正是本教学项目的标准形态：**实现最小可用，认知给完整。**

### 5.2 决策 2：**`TERM=dumb`** —— 见 §3.3

### 5.3 决策 3：**回退 + 回执告知一次** —— 见 §2.6

### 5.4 决策 4：宿主污染**不实现，文档单列一节** —— 见 §四

### 5.5 决策 5：**采集一次，进程内缓存，不提供刷新**

与 D01-13（不加配置）同一条判据：**没有真实消费者要求它可刷新。**

用户改了 `.zshrc` 想生效 → 重启 Agent。这个心智模型和「改了配置重启服务」
完全一致，**不需要教**。

⚠️ 但要写明**为什么可以缓存**：采集的是「用户的环境」，而用户的环境在一次会话内
**几乎不变**。这是个基于场景的判断，不是「懒得做」。

实测采集耗时 3ms（本机 bash），即便不缓存也不贵 —— **缓存的理由是语义确定性，不是性能。**

### 5.6 决策 6：`ToolContext` **第四次不扩展**，用模块级缓存

| 问 | 答 |
|---|---|
| 采集到的 env 有别的工具要用吗？ | ❌ **只有 `terminal`**。前 7 个工具不 spawn 进程 |
| 它会随调用变化吗？ | ❌ 进程生命周期内恒定 |
| 那放 `ToolContext` 图什么？ | 只图「看起来更正规」 |

→ **一个只有单一消费者、且生命周期与进程相同的东西，模块级缓存就是它正确的位置。**

⚠️ **`ToolContext` 连续四次没扩展（S001-D07 / S002-D07 / D01-13 / 本条），这不是巧合。**
「上下文对象」是最容易被滥用的结构 —— 任何东西都能塞进去，而且塞进去看着都合理。
每次都要问一句「**谁还需要它**」，问四次都是「没人」。

| # | 决策 | 类型 |
|---|---|---|
| D05-1 | **「和用户终端一致」必须拆成能力（继承）与呈现（覆盖）两个方向相反的要求** | 架构（总纲） |
| D05-2 | ⚠️ **推翻 T03 原推理**：「Agent 由用户终端启动」在桌面 App / 服务 / CI / cron 下全不成立，`process.env` 靠不住 | 技术（自我证伪） |
| D05-3 | 启动时用 `$SHELL -lc` **采集一次 login shell env**；执行用户命令仍是 `bash -c`（D01-1 不破） | 技术（解权衡 1） |
| D05-4 | 采集必须用**前后分隔符切中段** —— rc 会往 stdout 打欢迎语（实测 §2.4） | 技术 |
| D05-5 | 采集必须 `stdin: 'ignore'` —— rc 里的 `read` 会永久挂住（实测；D01-2 的第二次应用） | 技术 |
| D05-6 | 采集必须带 **5 秒超时 + `killSignal: 'SIGKILL'`** —— SIGTERM 可能被忽略 | 技术 |
| D05-7 | 显式 `source ~/.zshrc < /dev/null` 补 zsh 缺口；**`.zshrc` 是 `-lc` 唯一读不到的文件**（实测矩阵 §2.5） | 技术 |
| D05-8 | 简化版**未覆盖项如实列出**（ANSI / 框架阻塞 / Windows / 多字节 env）——「明示缺口」第四次应用 | 产品（诚实度） |
| D05-9 | 采集失败 → 回退 `process.env` + **在回执里告诉模型一次**（D01-7 第三次应用） | 产品（解权衡 3） |
| D05-10 | **`TERM=dumb`**；⚠️ 「不设」最差（`tput`/`clear` 直接报错）；不跟 Gemini 的 `xterm-256color`，因为它的理由是 pty，我们不做 pty | 产品（解权衡 2） |
| D05-11 | **不加 `NO_COLOR`** —— 既非必要（非 TTY 已覆盖）又不充分（拦不住 `color.ui=always`） | 产品 |
| D05-12 | env 采集结果**模块级缓存、不刷新**；`ToolContext` **第四次不扩展** | 架构（解权衡 5 + 6） |

## 七、教学价值

1. **「保持一致」是个必须拆维度的需求** —— 同样四个字，在能力上是目标、
   在呈现上是反目标（§一）。⚠️ **需求里出现"一致"时，先问"哪个维度"。**
2. **一条推理错了，往往不是逻辑错，是前提被默认成了普遍情况**（§2.2）——
   「Agent 由终端启动」在写代码的人身上永远成立，因为他一直在终端里。
   ⚠️ **自己的开发环境是最容易被误当成普遍情况的那个前提。**
3. **「读 rc」和「执行命令」要拆成两件事** —— `-l` 只用在采集那一次，
   执行仍是 non-login。这样既拿到能力，又不被 rc 的副作用污染，还不必每条命令重复付开销。
4. **我们注入进流程的每一步，都要按「用户命令」的标准来防** ——
   rc 里的 `read` 会挂死采集，正如用户命令里的 `read` 会挂死执行（§2.4 坑 2）。
   这是 D04-6（watcher 必须重定向）之后同一判据的第二次兑现。
5. **`.zshrc` 是 zsh 启动文件里唯一 login 和非 login 都读不到的**，
   而它恰恰是用户实际写东西的那个（§2.5 实测矩阵）。
   ⚠️ **bash 侧看起来没事是运气** —— 靠的是发行版默认 `.profile` 里那行转发。
6. **「简化实现」合格的标准，是它把没做的部分写清楚**（§2.5）——
   「明示缺口 > 假装解决」的第四次应用（前三次：D02-10 / D04-2 / D04-11）。
7. **一个措施要说清它防住了什么、防不住什么** —— `TERM=dumb` 真正解决的是
   `tput`/`clear` 报错，色码那部分主要是「非 TTY」的功劳（§3.3.1 实测）。
   ⚠️ **把笼统的措施拆到能追责为止**（同 D03 §6.4）。
8. **「什么都不做」也是一种选择，而且它可能是最差的那个** ——
   不设 `TERM` 让 `tput` 直接报错，比设错还糟（§3.3）。
9. **竞品的做法要连着它的前提一起抄** —— Gemini 用 `xterm-256color` 是因为它走 pty，
   把值抄过来而不抄前提，就抄到了一个对我们有害的配置（§3.3 结论 3）。
10. **第三类环境变量的判据不看变量本身，只看来源**（§四）——
    前两类问「有没有用」，第三类问「谁塞的」。
    ⚠️ **把 Agent 装进壳里，你继承的就不只是用户的环境，还有壳自己的环境。**
11. **`ToolContext` 四次都没扩展，不是巧合**（§5.6）——「上下文对象」是最容易被滥用的结构，
    因为任何东西塞进去看着都合理。判据是**「谁还需要它」**，问四次都是「没人」。

## 八、S003 五议题闭环

```
①  起进程、定回执           →  信息进上下文的规则
②  输出太多怎么办           →  落盘 + 渐进式披露
③  时间太久怎么办           →  跳过/取消 + 后台化
④  进程活下来之后怎么办      →  三道防线 + 登记 + 退出询问
⑤  这一切跑在什么环境里      →  能力继承 + 呈现覆盖 + 采集的三个坑
```

①—④ 讲的是「Agent 与一个它不写的程序之间的**边界**」，
⑤ 讲的是「那个程序**脚下的地面**」。

⚠️ 而 ⑤ 有一点和前四个不同：**前四个的问题都是被命令的行为触发的**
（输出多、跑得久、留下进程），**⑤ 的问题在第一条命令执行之前就已经存在了。**
→ 这也是为什么它放在最后讲，却必须在最前面做。
