# 核心原理：程序还在运行，Agent 也能继续决策

> 讨论前置导读草稿。说明实现持续交互所需的基本机制，不预先决定本章的工具接口、兼容范围或人机分工；S004 尚未实现。

[讨论大纲](../outline.md) | [下一篇：为什么需要持续交互](./01-problem-value.md) | [调研证据](../../../../researches/interactive-commands/README.md)

## 1. 先区分程序与工具调用

程序是操作系统中实际运行的进程。工具调用则是 Agent 请求 Harness 执行一次操作，并接收这次操作的回执。二者不必同时结束。

简单执行通常表现为：模型请求执行命令，Harness 启动程序，等待完成，再把结果交给模型。S003 已支持人工取消、跳过后后台运行和输出回读，但没有模型向原进程续写输入的入口。

当程序需要根据运行中的情况继续接收输入时，如果工具坚持等它退出才返回，就可能出现相互等待：程序等下一次输入，模型却还在等工具结果，没有机会决定输入什么。

持续交互首先要改变的是这种等待关系：**一次工具调用可以先交回已有信息，程序仍由 Harness 持有。** 这不是暂停程序，也不是把尚未完成的执行说成成功。

## 2. Harness 在两次调用之间持有运行会话

模型不会自己保留一个操作系统进程，也不会直接接住它的输入输出流。Harness 需要在工具调用结束后，继续管理足够的运行状态，让后续操作能找到同一个程序。

这里称它为“运行会话”：它关联仍可操作的程序、输入输出通道，以及必要的状态与归属信息。它不是聊天历史，也不意味着必须维护一个永不退出的 shell。

会话至少让三件事成为可能：

- **保留执行现场**：程序走到哪一步、解释器中的变量等不会因为一次工具返回就重新开始。
- **继续观察**：后续操作可以取得程序新产生的输出，而不是只能读第一次的结果。
- **继续输入**：把新的回答或指令送给原来的程序，而不是重新启动一份命令。

会话如何命名、由哪个模块保存，以及保留到什么时候，是后续设计问题。关键是它的存活期可以超过某一次工具调用。

## 3. 让中间反馈回到决策者

以模型参与输入为例，完整回路可以分成六步。这里描述职责，不规定要拆成六个工具。

| 步骤 | 发生什么 | 必须分清的含义 |
|---|---|---|
| 1. 发起 | 模型请求启动一项需要持续参与的工作，Harness 建立运行会话 | 创建程序不等于完成任务 |
| 2. 观察并返回 | Harness 收集一段输出，在合适的边界返回中间回执，告知工作尚未结束及如何继续关联它 | 工具返回不等于程序退出 |
| 3. 再次决策 | 模型获得这些信息，判断继续输入、继续观察、结束或请求人参与 | 仅在界面展示输出，不等于模型已获得决策机会 |
| 4. 继续操作 | Harness 将下一次操作交给同一会话；需要输入时写入原进程的输入通道 | 续写原进程不同于重跑命令 |
| 5. 重复往返 | 程序继续处理，产生新的反馈；按需要重复观察和操作 | 模型可再次决定时，程序也可能仍在计算或等待 |
| 6. 结束或移交 | 根据明确的规则确认结果、释放资源，或把继续运行的工作移交给明确的所有者 | 对话结束不自动证明所有工作已经结束 |

原有 ReAct 循环本来就会根据工具结果决定下一步。这里不是新增一种模型推理能力，而是让一个尚未结束的程序，也能提供下一轮决策所需的反馈，并接受后续行动。

初次调用何时交回控制权，可以根据时间窗口、程序协议或其他观察依据决定；它不必先“可靠检测到正在等输入”。具体选择留在 Q3 讨论。

## 4. 输入输出通道解决什么，PTY 又解决什么

普通程序可以从标准输入接收数据，并通过标准输出、标准错误返回信息。Harness 用管道连接这些通道，就能对支持这种运行方式的程序读写。能写入数据，还需要配合前面的中间回执和决策回路，才形成模型持续交互。

有些程序还要求终端环境：它们根据是否连接终端来决定显示提示、缓冲输出、回显输入或处理按键。这时可以用伪终端（PTY）提供相应的终端语义。

**管道或 PTY 解决连接和兼容问题；运行会话与决策回路解决如何持续推进工作的问题。** 分配了 PTY，不意味着模型已经能观察、判断并继续输入；使用管道，也不意味着所有程序都能按照预期交互。

因此本节先解释二者的职责，不决定本章必须使用哪一种。控制字符、EOF 和取消也不是同一操作，细节在讨论所需能力后再展开。

## 5. 用一个小例子理解“同一个程序”

在已有的 Python/Node 实验中，控制器先让解释器建立 `value=42` 并返回结果；控制器读取到 42 后，再请求原解释器执行 `value += 42`，得到 84。

第二步同时依赖两件事：控制器知道首轮输出，解释器保留了首轮变量。只重新启动一个空解释器，或只让人看到输出但不给决策者反馈，都不能完成这个回路。

这个实验的决策者是确定性控制器，不是实际运行的 LLM；它验证通道、跨轮状态和退出行为，为原理提供证据，不代表某款 Agent 产品的端到端效果。真实任务的价值仍要由 Q1 选定的场景说明。

## 6. 原理明确后，仍有哪些事需要决定

上述机制使“持续参与”成为可能，但没有替产品作出决定：

- 哪些任务值得为此保留运行现场？这是 Q1。
- 哪些输入由模型决定，哪些要交给人？这是 Q2；通道可写不等于已经获得授权。
- 哪些反馈足以支持下一步行动？这是 Q3。
- 中止、放弃或结束后，谁负责尚未结束的程序？这是 Q4。
- 本章承诺覆盖哪些程序与行为？这是 Q5。

读完本节，应能解释这句话：**Harness 把持续运行的程序与一次次工具调用连接起来，使执行中的反馈可以再次进入 Agent 的决策过程。**
