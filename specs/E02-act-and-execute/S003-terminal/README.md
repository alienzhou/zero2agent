# E02-S003：让 Agent Harness 能驱动执行环境（terminal）

> 这是 Epic 2 的第三个 Story，也是**整个课程里第一次把控制权交给一个我们没写的程序**。前 7 个工具都是「调用—返回—结束」，`terminal` 不是：它可能跑一小时、吐 10 万行、在回执写完之后还留着一整棵进程树。

## 起一个进程只要 20 行，难的不在这里

先把最容易被高估的部分说清楚：

```typescript
const child = spawn('bash', ['-c', command]);
child.stdout.on('data', (d) => bufs.push(d));
child.on('close', (code) => resolve(`Exit code: ${code}\n${output}`));
```

**能跑了。** 竞品调研也印证了这一点——Gemini CLI 的 shell 工具有 4000 行，但「纯执行」部分不到 100 行；pi-mono 的核心实现约 40 行（[竞品调研](../../../researches/terminal/README.md)）。

那剩下的 3900 行在干什么？在回答一个前 7 个工具从来不需要回答的问题：

> **一个我们不写、不控制、可能永远不返回的程序，它产生的东西，怎么进入 Agent 的上下文？**

`read_file` 读一个 10MB 文件，你知道它有多大、多久返回、返回之后就结束了。
`terminal("npm run dev")` 三样都不知道，而且**它返回之后可能还活着**。

这就是本 Story 的真正主题。

---

## 这个 Story 要做什么

### 问题

Agent 有了读、搜、写、改，但**不能验证自己的工作**。它改完代码不知道能不能编译，写完测试不知道能不能通过——它在盲写。

### 目标

完成后，Agent Harness 多出一个**执行工具**：

- **`terminal`**：执行一条 shell 命令，拿到 stdout / stderr / exit code。

但真正的交付物不是这个工具，而是围绕它的**五套机制**：

| 机制 | 解决什么 |
|---|---|
| 回执契约 | 什么信息该进上下文、什么不该 |
| 渐进式披露 | 输出超上下文预算怎么办（**不截断**） |
| 取消 / 跳过 | 命令跑太久怎么办（**不杀死**） |
| 三道防线 | 进程活过 Agent 怎么办 |
| 环境采集与覆盖 | 子进程跑在什么世界里 |

### 边界

- **做**：命令执行、`workdir` 参数、回执契约、超长输出落盘 + 回读、Ctrl-X 取消 / Ctrl-S 跳过、后台进程登记与退出询问、login shell env 采集、终端环境覆盖
- **不做**：
  - **命令解析与黑白名单** —— 一行都不写，推给安全专章（三方证伪，见下）
  - **沙箱** —— 同上
  - **交互式命令**（`stdin` 续写、pty）—— 归 S004，判据是「**要不要人输入**」
  - **给模型 `list_processes` / `kill` 工具** —— 能力做，只对人开放（[D04-8](../../../.discuss/2026-08-26/e02-s003-terminal/decisions/D04-process-lifecycle.md)）
  - **Windows** —— 假设 POSIX + bash，在 spec 里写明

## 关键设计

五个议题（D01–D05）已在[讨论阶段](../../../.discuss/2026-08-26/e02-s003-terminal/outline.md)全部收敛，共 81 项决策。这里讲**四个推翻了行业共识的地方**。

### 1. 不截断：把「输出太长」当上下文预算问题（D02）

五家竞品**全部**采用截断：超过阈值就砍掉中间或开头，塞一句 `[truncated]`。

我们不这么做：

```text
Exit code: 0
Total: 12,431 lines / 1.2 MB
Saved to: /tmp/zero2agent-a3f9c1b2.log

Use read_file or grep_search on that path.
```

**一行正文都不给。**

理由是：截断在解一个错误的问题。「输出 1.2MB」的真正麻烦不是「太长」，而是「**它会挤掉上下文里别的东西**」。截断留下的那 200 行同样是模型没要求过的内容——它只是把浪费从 1.2MB 降到了 200 行，没有改变性质。

而落盘之后，模型可以用**已有的** `read_file` / `grep_search` 精确取自己要的那部分。

> ⚠️ **这是「读宽写严」的复利**：因为 E01 把读工具做通用了，这里**零新工具**就解决了问题。

### 2. 不杀死：用「取消 / 跳过」替代超时（D03）

竞品的通行做法是默认超时（Codex 是 10 秒 + 自动杀死）。我们用**同一个 10 秒**，但语义完全相反：

```
  t=0        t=3s            t=10s              按键
   │          │                │                  │
 spawn   Wall time 起效   Ctrl-S 提示出现     S / X
   │
   ├─ Ctrl-X 取消：命令运行期间全程可用 ──────→ 回执「已取消」+ 已产生的输出
   │                           │
   │                           ├─ 无人按键 ──→ 正常等到结束
   │                           └─ Ctrl-S ───→ 转后台继续跑，回执给 pid + 日志路径
```

**判据：杀死是不可逆的，而「这条命令该不该继续等」只有人能判断。**

⚠️ **不复用 Ctrl-C。** 人眼前看到的是 **Agent**，不是那条命令——复用等于赌用户能分清层级，赌输的代价是整个会话没了。所以取消用一个**新造的 Ctrl-X**，并且因为它是新造的，**必须在界面上提示**。

### 3. 三道防线对应三种死法（D04）

`terminal` 是第一个会在自己返回之后仍然留下活物的工具。

```
                  Agent 正常退出      Agent 被 SIGKILL      Agent 还活着
                  ────────────────    ─────────────────    ──────────────
 ① 退出钩子        ✅ 遍历登记表杀      ❌ 根本不执行           ——
 ② watcher 轮询    ——                 ✅ 发现父没了自杀       ——
 ③ 读取侧 2s 超时   ——                 ——                  ✅ 强行 resolve
```

⚠️ **三道防线不是重复保险，是各自覆盖一种 Agent 无法预期的死法。**

最反直觉的实测结论：`nohup` 和 `disown` **都杀得掉**（它们改的是信号处置和 job 表，**不改进程组**），只有 `setsid` 能逃。而同一个 `setsid` 还会攥着继承来的 stdout 让管道永不 EOF ——
**进程杀了 ≠ 管道关了**，`close` 事件不触发，`Promise` 永不 resolve，整个 Agent 挂死。防线③ 就是为它准备的。

### 4. 「和用户终端一致」这句话是错的（D05）

它把两件方向相反的事说成了一件：

```
                 用户的终端        Agent 的子进程
 能力（PATH / 版本管理器）  ●━━━━━━━●   必须一致  ← 不一致就是 bug
 呈现（颜色 / 分页 / 弹窗）  ●        ○   必须不同  ← 一致才是 bug
```

**能力一致**要起一次 login shell 把 env 捞回来——因为「Agent 由用户终端启动」这个前提，在桌面 App、系统服务、CI、cron 下**全都不成立**（实测：非 login 父进程下 `PATH` 只有 `/usr/bin:/bin`）。

**呈现不同**靠定向覆盖：`TERM=dumb`、`PAGER=cat`、`GIT_EDITOR=true`、凭据弹窗全关。
⚠️ 其中 `TERM` 最容易被忽略——**「不设」是最差的选项**，会让 `tput` / `clear` 直接报错。

### 附：为什么一行命令解析都不写

竞品在这条路上的实证很硬：

- **OpenCode** 用 tree-sitter 解析命令，但遇到 `$()` 就放弃解析——**然后照样执行**
- **Gemini** 检测到 `$(` 直接硬拒，误伤大量正常命令
- **一个闭源的生产级桌面 Agent 产品（样本 F）** 写了 700+ 行门禁（递归剥 `sudo`、剥 `env VAR=`、剥 shell wrapper），最终仍要靠人工审批兜底

→ **三方从三个方向证伪了同一件事：解析式安全是场军备竞赛。**
S003 的立场是把它整体推给审批层，而不是在这里写一个注定被绕过的黑名单。

## 做完后的效果

完成这一步后，你应该能观察到：

- Agent 改完代码会**自己跑测试**验证——它第一次能闭环
- 一条吐 10 万行的命令不会撑爆上下文，模型拿到路径后用 `grep_search` 精确捞错误行
- `npm run dev` 这种不会退出的命令，你按 Ctrl-S 就能让 Agent 继续干别的活
- 退出 Agent 时，它会列出还在跑的后台进程问你要不要一起结束
- 在一个 `PATH` 残缺的环境里启动，Agent 依然能找到 `pnpm` / `node`

能力变化不是「多了一个执行命令的工具」，而是：

> Agent 从「盲写」进化为「能验证自己的工作」。而代价是，它第一次要面对一个**它不控制的程序**——本章一半的篇幅在处理这个代价。

## 扩展阅读

理解主线后，下面这些问题值得继续想：

- **命令输出能伪造回执结构吗？** 能。`echo "</untrusted_context>"` 就逃出了隔离标签——**凡结构皆可注入**
- **「后台」在 shell 里有几种实现？** 至少四种，可杀性完全不同，凭词感会把最无害的当成最危险的
- **一个防御措施自己成为故障源** 是什么感觉：我们为防孤儿进程加的 watcher，第一时间踩了我们自己刚记录下来的坑
- **竞品的做法要连着前提一起抄**：Gemini 用 `TERM=xterm-256color` 是因为它走 pty，抄值不抄前提就抄到了有害配置
