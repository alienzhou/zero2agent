# 日志缺了一行，为什么不能直接重试工具

[本课](../README.md) | [Backlog](../details/04-backlog.md)

假设日志中最后一条是 write_file/running，后面的结果缺失。可能是文件没有写完，也可能是文件写完后进程被杀，或者只是不再能写日志。三个情况对应不同动作；同一份缺失记录分不出来。

## 两条提交路径

```text
工具：检查 → 修改文件 → 返回结果
日志：排队 → 写完整行 → flush
```

本课没有把两条路径绑成一个事务。日志失败会降级，工具不会回滚。S004 的 pending 也只是「本轮未结算」，不是「工具尚未发生」。你应先检查工作区和会话工具回执，再决定怎么继续。

即便同步写了 running 并 fsync，也不能用它判断工具是否已经执行完。那只能证明开始记录先进入了持久存储，无法填补副作用与结束记录之间的空隙。

## 什么时候可以重试

| 操作 | 重试前需要什么 |
| --- | --- |
| 读文件 | 确认当前读取目标与问题仍相同 |
| 写入确定的完整内容 | 检查当前版本，避免覆盖其他人的后续修改 |
| 追加一条记录 | 唯一业务身份和去重机制，防止重复追加 |
| 启动命令或外部请求 | 可查询状态、幂等键或补偿流程 |

日志里的 UUID 是关联身份，不会让外部动作自动具有幂等性。toolCallId 甚至可能在不同请求中重复，所以本课还保留 requestId 与 operationId。

## WAL 与普通运行日志

事务的 write-ahead log 要参与提交与恢复协议。普通运行日志用于解释发生过什么，可以采样或在故障时丢失。本课采用后者：写队列有界、失败可见、任务继续；没有从 JSONL 自动恢复工具的入口。

下一课文件 Checkpoint 能回到某个文件版本，也不能自动撤销外部服务、已发送消息或仍在运行的进程。把这些边界分清楚，才能避免用「日志完整」替代实际验证。
