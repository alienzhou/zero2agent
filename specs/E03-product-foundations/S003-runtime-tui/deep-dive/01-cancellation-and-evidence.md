# 为什么取消后还要等待

[课程](../README.md) | [设计](../details/01-technical-design.md) | [后续问题](../details/04-backlog.md)

## Promise 结束不代表工作结束

假设 writeReport() 花五秒写文件，你用 Promise.race([writeReport(), abortPromise]) 实现取消。第一秒 abortPromise 返回了，但 writeReport() 仍会在第五秒完成写入。如果第一秒就开放下一轮，新任务看到的是一个仍在变化的工作区。

Promise.race 只决定调用方先收到哪个结果，不提供停止原始任务的能力。能够中止的工作需要具体机制：HTTP 请求的 AbortSignal、子进程的信号与进程组清理、文件操作的协作检查，或独立 Worker/进程的生命周期控制。

## 三个时刻不能合并

| 时刻 | 已知事实 | 界面应该表达什么 |
|---|---|---|
| 用户请求取消 | 使用者希望停止当前工作 | 正在取消 |
| 中断已经送达 | 控制信号到达请求或工具 | 继续等待收尾 |
| 已启动工作全部结束 | 不会再从这一轮启动新的工作 | 已取消，可以继续 |

正常退出、失败和取消都需要释放资源。为了尽快回到输入框而跳过等待，可能遗留仍会写文件的工具；为了保留证据而永远等待，又可能被不协作工具拖住。当前实现选择协作取消并保留互斥，明确显示收尾状态。若要给任意工具提供强制期限，需要把它放进可终止的执行容器，这是运行架构的改变。

## 已发生的事实不能从历史里抹掉

模型同批提出 A、B 两个工具。A 已写入文件，B 尚未启动时用户取消。正确历史包含 A 的实际结果与 B 的未执行回执；如果只保留一条“任务取消”，下一轮就无法判断 A 是否执行过。

工具运行后抛错也不证明它没有副作用。例如写入成功后读取校验失败，最终回执是错误，文件却已改变。因此错误与取消说明需要提示重新检查工作区，不能声称自动回滚。

模型流式输出还有另一层边界：屏幕上已经出现几个字，不代表已经得到可提交的完整 assistant 消息。半个工具 JSON 不能进入下一次模型请求。显示记录与已提交会话分别维护，正是为了不把视觉上的部分进展误当协议中的完整消息。

## 事件不天然是日志

UI 事件为了即时展示，可以合并文字片段、丢弃旧显示记录，并忽略结束后到达的旧状态。永久审计日志则需要稳定格式、持久化、跨进程顺序和隐私策略。把界面事件直接写进文件，并不能自动解决这些问题。

本课使用 turnId 与 seq 处理单次运行的身份和顺序；S005 再定义可追查日志。现有人工终端的私密正文也不会因为引入日志就自动成为采集对象。

## 取消与回滚何时结合

回滚需要知道哪些资源改变、旧值是什么、有没有并发修改，以及外部系统是否支持补偿。取消只阻止更多工作；回滚尝试恢复先前状态。二者可以由产品流程组合，但不能用同一个按钮文案掩盖不同保证。

本项目将文件 Checkpoint 与回退留给 S006。HTTP 请求、已发消息、后台服务或任意 shell 外部副作用不属于文件回退的承诺范围。先让取消准确，再让回滚有证据，两个能力才有可靠的边界。
