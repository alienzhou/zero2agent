# 快照与追加日志：保存多少，才能恢复多少

[返回本课](../README.md)

全量快照把某个时刻的状态写成一个完整文件。恢复时不需要重放事件，先校验数据，再把 raw history 和摘要交给 Session。缺点是重复：若每轮消息量相近，第 n 轮的快照约含 n 轮历史，保留所有快照时，总量随 1+2+…+n 增长。本课每轮还先写一份 pending，因此需要明确后续的保留策略。

追加日志只写新增记录，通常更适合长会话，但读取需要处理半行、顺序、版本演进、压缩和索引。日志存在不代表恢复安全：如果 write_file 完成后进程就退出，工具副作用和记录追加之间仍然存在空窗。要进一步缩小这个窗口，需要逐工具意图/结果日志、幂等键或事务性工具，而不是单纯把 JSON 改成 JSONL。

## 原子可见和断电持久性是不同问题

临时文件写完后再发布，解决读取者不应看到半截 JSON 的问题。独占创建目标 revision 进一步解决并发覆盖：两个写入者都持有 r4，只能有一个发布 r5。本课使用同文件系统 hard link，目标已存在就失败，不覆盖。

文件 fsync 把文件数据交给文件系统的同步机制；目录 fsync 用于同步名字变更。本课目录同步尽力执行，不能据此承诺所有文件系统、网络卷或断电场景都安全。所有已发布 revision 保留，读取最高版本失败时明确报错。静默降级到 r4 看似“恢复成功”，却可能抹掉用户对 r5 已发生效果的认识。

## 恢复的是观察，不是执行计划

历史里的 tool_use 说明模型当时提出过什么；tool_result 说明宿主记下了什么结果。恢复时二者一起进入消息历史，不调用 execute。下一轮模型可以根据这些观察提出新动作，但必须重新经过当前权限控制。

pending 的含义更弱：只能确定本轮尚无已发布的结算快照。它不告诉我们哪些工具完成，更不能说明文件未变。所以中断恢复明确加入 Harness 提醒，让模型与使用者重新检查工作区。逐工具恢复、旧进程监督和自动重试属于后续可靠性课程。

## 为什么保留原史和摘要

摘要是当前请求的节省方案，不是审计级原始证据。保存 raw messages 可以在预算变化、临时文件消失后重新组织上下文；保存已采用 summary/through 又避免重启后重复压缩同一段历史。没有采用的后台摘要作业不进入快照，防止一个迟到的任务覆盖新会话。

本课的验证直接检查恢复后的 HTTP 请求正文，既确认摘要出现，也确认被覆盖的旧助手正文没有再次整段发送。界面能看见旧消息与模型收到压缩上下文，可以同时成立。
