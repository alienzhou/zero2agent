# 1. 为什么回滚消息不等于回滚世界

假设 Agent 已把配置文件里的端口从 3000 改为 4000，下一次模型请求却断网了。你删除本轮消息，再对模型说“继续”，它看到的历史就像文件从未改过。但磁盘上的端口已经是 4000。

问题不只是丢失一次回复，而是模型的行动依据和真实环境出现了偏差。

## 消息可以删除，副作用未必能撤销

| 状态 | 能否靠删除历史回退 |
|---|---|
| 尚未发送的用户输入 | 可以从内存移除 |
| 尚未完成的流式文本 | 可以不提交为正式历史，但终端可能已显示 |
| 已写入的文件 | 不可以，需要文件快照或明确的逆操作 |
| 已启动的进程 | 不可以，需要进程所有权与清理机制 |
| 已发送的外部请求 | 通常不可以，必须依赖外部系统的补偿能力 |

因此，本课把“完成的工具结果”当作必须保留的观察证据。失败只意味着这一轮没有正常结束，不意味着之前的工具没执行。

## 为什么不能直接把流式文本也保存下来

流式界面追求及时显示，正式历史追求完整结构。屏幕可能已经显示“准备修改”，但下一段 tool_use 参数还没收完。如果把这个半截结构当作可继续的消息，下次请求可能不合法，或者更糟：执行了缺少关键字段的指令。

本课以 finalMessage 为完整响应边界；max_tokens 即使返回了可解析的工具参数，也不执行。模型随后可根据错误结果重新提出完整调用，但宿主不会代它自动重跑。

## 压缩的是工作上下文，不是已经发生的事实

继续上面的场景：端口修改成功的工具结果很长，下一次请求接近窗口。不能为了省空间删除“改到 4000”的证据，更不能重新执行原命令来找回输出。

本期先把大工具正文完整保存到临时文件，仅在发送视图里留下预览与按行回读引用；遇到很长的单行，还额外保存按 Unicode 码点切片的 JSONL，每行有字符偏移与文本，既有 read_file 就能分段读到末尾，而不必重跑原工具。需要进一步缩减时，再用摘要替代稳定历史前缀。`getHistory()` 仍保留原始工具结果，`getContext()` 看到的才是压缩后的消息视图。摘要与原文分开，才能检查遗漏，也避免把有损总结伪装成原始事实。

后台摘要开始后，用户可能又说“不要再改端口”。旧摘要不能覆盖这条新约束：采用时必须保留新增尾部，确认源前缀没有变化。`/new` 或取消让旧任务失效，晚到的摘要不得重新填回会话。前台请求如果已放不下，就先等待或继续压缩，而不是为了保持界面流畅跳过预算。

手动 `/compact` 同样不是撤销：它只改变模型接下来可见的工作上下文，并可能产生额外模型费用。摘要失败保留原始记录，但不代表请求一定还能发送；不可压缩的最新输入或固定指令过大时，仍需拆分输入。主模型拒绝窗口后的恢复也只重试模型请求，不重跑完成的工具。

最终验收测试候选 `3829868` 为这些边界补充了组合证据：连续两次实际恢复后第三次拒绝停止，副作用仍只执行一次；成功／失败混合工具批次经过后台 pending、新工具对追加、模型失败与前台接管后，原史与增量证据仍保留。生产代码保持 `ea498a3`，这些本地测试不证明摘要语义无损。详见[验收记录](../details/03-verification-checklist.md)。

## 原始历史、工作上下文、日志与快照不是一回事

| 记录 | 回答的问题 | 不提供的保证 |
|---|---|---|
| 原始会话历史 | 已提交哪些对话与工具证据 | 不是持久审计日志，退出不恢复 |
| 工作上下文 | 下次请求准备采用哪些消息 | 有损摘要不保证事实齐全，仍需发送前计数 |
| 运行日志 | 宿主实际发生过什么 | 不自动恢复文件或外部服务状态 |
| 文件快照 | 哪些文件内容可以恢复 | 不撤销全部外部副作用 |

本课的 `[Harness]` 中断说明与摘要标记用于区分来源，不是防伪安全边界。工具结果临时文件可能被系统清理，也不是持久化承诺。日志与 Checkpoint 分别留给 E03-S005、E03-S006；高级摘要质量评估与更复杂上下文工程留给 Epic 4。未来自动恢复仍须单独设计幂等性、重试与副作用补偿。
