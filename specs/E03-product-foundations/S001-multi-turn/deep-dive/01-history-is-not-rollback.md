# 1. 为什么回滚消息不等于回滚世界

假设 Agent 已把配置文件里的端口从 3000 改为 4000，下一次模型请求却断网了。你删除本轮消息，再对模型说“继续”，它看到的历史就像文件从未改过。但磁盘上的端口已经是 4000。

问题不只是丢失一次回复，而是模型的行动依据和真实环境出现了偏差。

## 消息可以删除，副作用未必能撤销

| 状态 | 能否靠删除历史回退 |
|---|---|
| 尚未发送的用户输入 | 可以从内存移除 |
| 尚未完成的流式文本 | 可以不提交为正式历史，但终端可能已显示 |
| 已写入的文件 | 不可以，需要文件快照或明确的逆操作 |
| 已启动的进程 | 不可以，需要进程所有权与清理机制 |
| 已发送的外部请求 | 通常不可以，必须依赖外部系统的补偿能力 |

因此，本课把“完成的工具结果”当作必须保留的观察证据。失败只意味着这一轮没有正常结束，不意味着之前的工具没执行。

## 为什么不能直接把流式文本也保存下来

流式界面追求及时显示，正式历史追求完整结构。屏幕可能已经显示“准备修改”，但下一段 tool_use 参数还没收完。如果把这个半截结构当作可继续的消息，下次请求可能不合法，或者更糟：执行了缺少关键字段的指令。

本课以 finalMessage 为完整响应边界；max_tokens 即使返回了可解析的工具参数，也不执行。模型随后可根据错误结果重新提出完整调用，但宿主不会代它自动重跑。

## 会话历史、运行日志与文件快照不是一回事

会话历史回答“下一轮模型知道什么”；日志回答“宿主实际发生过什么”；文件快照回答“哪些内容可以恢复”。三者可能记录同一个动作，却不提供同一种保证。

本课的 `[Harness]` 中断说明只是上下文中的明确标记，不是可靠的审计日志，也不是防伪安全边界。日志与 Checkpoint 分别留给 E03-S005、E03-S006；如果未来支持自动恢复，还必须单独设计幂等性、重试与副作用补偿。
