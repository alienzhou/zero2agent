# 2. 回退也是一次需要恢复的写入

[课程](../README.md) | [设计](../details/01-technical-design.md)

恢复按钮最容易制造一种错觉：原操作已经失败，所以撤销它应该更安全。但恢复会覆盖或删除当前文件，也会遇到断电、磁盘满和其他进程写入。它需要和普通写入一样严肃的协议。

## before、after、live 的不同职责

before 告诉你想回到哪里，after 告诉你原操作完成后应该是什么，live 告诉你现在是什么。若 live 不等于 after，说明中间存在未被这条记录解释的变化。无论它来自用户、另一个 Agent，还是后台命令，直接恢复 before 都可能抹掉有价值的结果。

所以正常回退采取乐观并发检查：预览比较，确认时再比较。令牌绑定清单和当前文件，不是一个可以永久重复使用的“批准”。如果你改了文件再来确认，就得重新看计划。

这不是三方自动合并。自动合并还需要语法、冲突展示和语义验证；“都修改不同的行”也不保证行为正确。本课冲突即停，保留文件原样。

## 多文件恢复为什么需要意图日志

假设 A 已恢复，B 还没恢复，进程就退出了。如果只有一个最后写入的 success 标记，下次就不知道 A 是完成了还是外部变化。恢复意图先把每个文件的来源和目标记下来，让后续判断有依据。

重启后比较 live：等于目标就跳过，等于来源才继续，既不是来源也不是目标则停止。这样不会重放模型或文件工具，也不会因为日志没结算就再执行可能已经有副作用的命令。完成后的恢复意图又能反向作为新一次 undo 的来源。

未结算的原工具比较棘手：只有 before，没有可靠 after。课程不自动猜来源，而是让用户看当前文件清单，确认接受当前状态被恢复覆盖；同时先把当前版本保存进新的恢复记录，保留撤销这次选择的机会。

## 文件系统仍有最后一个竞争窗口

Node 的普通路径接口提供了读取、rename、unlink，却没有跨任意外部进程的“只有内容仍等于这个哈希时才替换”原子操作。检查之后、实际替换之前，别的程序仍可能改文件。存储锁只能协调遵守同一协议的写入者，不能锁住文本编辑器、另一个未受控 shell 或操作系统服务。

因此路径逐层检查、禁止链接、O_NOFOLLOW、写前重验和不覆盖式新建都只是具体防护；不能合起来就称为沙箱。更强保证需要隔离工作区、平台级文件句柄协议或文件系统事务，适用性和工程成本都不同。

## 回退历史为什么不能顺便删掉

工具回执记录的是当时发生过的事。文件退回，并不让那次工具执行消失，也不会撤销网络调用、进程或用户见过的输出。原史保留，当前会话追加一次文件已恢复的事实，让下一轮重新读取磁盘。会话压缩只调整模型可见视图，不承担磁盘恢复。

工程上最有用的恢复设计，是清楚写出每个阶段还有哪些证据、已经有哪些效果，以及哪些动作必须由用户确认。一个始终显示“成功”的撤销按钮，反而无法帮助你面对真正的失败。
