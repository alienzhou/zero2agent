## 共用案例与现有基础

准备一个很小的 TypeScript 双包项目：`packages/api` 与 `packages/web`。固定任务是修复一处金额计算错误、补测试并输出 `artifacts/change-report.json`。工单资料来自本地固定夹具，不依赖真实公司系统。每节的默认跟练可以在没有模型 API key 的情况下，通过确定性模型响应和真实宿主进程验证机制。

| 已有能力 | E05 的复用方式 |
| --- | --- |
| E01 Prompt 分层、文件读写与搜索 | 增加有来源和作用域的项目指令；接入新的工具描述时同步实际能力文案 |
| E03 审批、TUI、日志、Checkpoint | 扩展来源可见；新操作使用当前权限；诊断仍只记录元信息；只对明确受控文件承诺回退 |
| E04 请求预算、结果引用、完成校验、恢复 | 扩展消耗同一轮预算；长结果按需读取；未完成检查不能被清除；未知效果不自动重放 |

规划时的基线：`AgentOptions.tools` 可以注入工具，`Tool.execute` 返回字符串；`SystemPromptOptions.instructions` 仍是未接通的预留位。`LoopEventHandlers` 是展示观察者，不能当作阻断执行的 Hook。E05 分别补齐这些连接，不另造一套权限、结果仓库或运行循环。

## E05-S001：项目指令与 AGENTS.md

**要解决的问题**：每次都在对话里重复项目约定，而且同一仓库的不同目录有不同规则。

### 具体做什么

1. 在显式工作区边界内发现根目录、启动目录祖先链和目标文件祖先链的 `AGENTS.md`。不遍历整棵仓库，不自动读取工作区之外的父目录或用户目录。规则来源、作用域、顺序及内容版本可查看。
2. 将项目规则作为独立的请求上下文提供，计入输入预算。目标目录更深的规则只覆盖该目录下的冲突约定，兄弟目录不串用；同一请求涉及多目录时保留各自作用域标签。
3. 本课程采用“宿主硬边界始终有效；明确用户任务可覆盖项目约定；同一作用域内更具体规则优先”的产品语义。自然语言规则由模型理解，不宣称能通用地自动判断语义冲突；确定性验收验证实际请求里的来源、内容与适用范围。
4. 首次操作进入新的嵌套作用域、或规则已变化时，在工具副作用前完成规则补载；需要模型重新规划时，原调用配对为明确的未执行结果，再发起有界的新请求。不能先写文件，再告诉模型该目录有规则。一次批次预检处理所有可确定的目标；不从任意 shell 文本猜测全部影响路径。
5. 提供查看当前规则及显式刷新/关闭的 CLI/TUI 入口。恢复会话时按当前文件重新构建规则；旧规则保留为历史，不能覆盖当前规则或变成新授权。根规则默认读取也必须遵守显式读取拒绝和边界策略。

**跟练**：根目录要求补测试，`api` 目录规定专用测试命令，`web` 有另一套约定。分别从仓库根和子目录启动，观察发送给模型的规则及最终修改文件。

| 必须验收的场景 | 判定依据 |
| --- | --- |
| 根目录、嵌套目录、兄弟目录与跨目录批次 | 实际请求包含正确来源和作用域；无兄弟规则误用；不会重复无限注入 |
| 首次写入尚未加载规则的子目录 | 规则在重新规划请求中可见；原批次尚未产生文件修改；调用和结果完整配对 |
| 项目约定与用户明确要求冲突 | 请求明确表达用户覆盖；项目文本要求绕过审批或写出工作区时，宿主仍阻止实际副作用 |
| 无规则、文件缺失、不可读、超限、符号链接越界 | 无规则保持原行为；缺失与拒绝可区分；必要规则读不到时不继续受影响写入，不静默截断关键内容 |
| 文件变化、会话恢复、压缩后继续 | 下一轮使用当前规则版本；旧摘要不能覆盖新规则；刷新不改写历史、不继承旧授权 |
| CLI、plain、TUI 查看/刷新 | 列出的来源与实际请求一致；仅查看不发模型请求；无交互审批时拒绝仍有效 |

**代码起点**：[Prompt](../../packages/core/src/prompt/system.ts)、[Agent](../../packages/core/src/agent.ts)、[执行循环](../../packages/core/src/loop.ts)、[权限](../../packages/core/src/permissions.ts)、[CLI](../../packages/tui/src/cli.ts)。

**本节延期**：组织级策略服务、自动改写 AGENTS.md、任意 Markdown include、不同产品全部指令文件别名、任意 shell 的目录级规则强制推断。当前仓库已有 AGENTS.md 是开发协作规范，不代表这些加载行为已经实现。

## E05-S002：Skills 的发现与按需加载

**要解决的问题**：把所有任务指南都塞进初始 Prompt，成本高，也难以复用一套可靠步骤。

### 具体做什么

1. 从项目技能目录和用户显式指定的目录发现 `SKILL.md`，校验标准的 `name`、`description` 等元数据。主线采用名称/描述目录 → 选中技能正文 → 按需读取参考文件三层加载；目录和正文分别有数量与字节限制。
2. 先实现用户明确选择技能，再支持模型根据目录选择受控的加载入口。提供已发现、已加载、被禁用及加载失败的可见状态；不承诺模型一定能自动选中所有相关技能。
3. 资源路径相对于技能根解析，建立明确的目录来源与权限。工作区外的显式技能目录也要遵守当前读取许可；路径穿越和符号链接不能借资源引用绕过限制。
4. 技能脚本仍通过已有工具和审批执行。发现或加载技能不会启动脚本；技能中的 `allowed-tools` 等声明不能自行扩权。首版不支持的权限或控制字段要明确提示，不能假装已经执行其语义。
5. 激活内容和引用计入现有上下文预算；正文读取失败不得伪装激活成功。恢复后检查当前技能身份和版本，旧会话不恢复脚本进程、隐含授权或失效资源。
6. 用 `fix-with-tests` 技能描述定位、修改、测试、报告流程；顺带检查仓库现有 CDP Skill 示例的格式。当前示例的头部不符合标准 frontmatter，实施时修正或明确保留为普通指南，不能拿它冒充标准解析验收样本。

**跟练**：同一金额修复任务，先只显示技能摘要；选择 `fix-with-tests` 后读取步骤，真正需要报告格式时才读取参考文件。用哨兵文本检查无关技能正文没有进入请求。

| 必须验收的场景 | 判定依据 |
| --- | --- |
| 发现、明确选择、模型选择、停用 | 请求与加载记录显示正确的技能身份；停用后新轮不会继续自动注入 |
| 放入多份无关技能及很大的参考文件 | 首次请求只包含允许的元数据；正文/参考按需出现；超出目录预算有明确结果，不能撑爆输入 |
| 非法 frontmatter、重名、缺失依赖、被删除技能 | 错误和来源可追查；重名不静默覆盖；失败不标记成功、不执行代码 |
| 资源越界、符号链接和外部目录拒绝 | 未获允许的正文不进入模型请求；拒绝不升级成允许 |
| 技能请求自动运行脚本或放宽权限 | 单纯发现/加载产生零脚本执行；真正调用由当前权限控制；拒绝后实际效果为零 |
| 中断、恢复与内容变更 | 旧正文只作为历史；当前版本明确，缺失资源可见；不自动重跑脚本 |

**代码起点**：S001 的有来源上下文、[工具接口](../../packages/core/src/tools/types.ts)、[结果按需读取](../../packages/core/src/tools/read-tool-result.ts)、[会话](../../packages/core/src/session.ts)。

**本节延期**：技能市场、下载更新、依赖安装器、远端技能仓库、完整产品私有 frontmatter、技能自动生成和自动评分。

## E05-S003：MCP 工具接入

**要解决的问题**：每接一个外部工具，都需要修改内置工具代码。

### 具体做什么

1. 实现一个边界明确的 MCP Client 适配器，先接本地 **stdio** 服务：初始化与能力协商、分页工具发现、参数校验、调用及关闭。选定协议版本并锁定兼容 SDK；研究参考使用 `2025-11-25` 版本文档，不追随未冻结的 draft。
2. 用稳定的 server/tool 身份映射到当前模型支持的工具名，检测长度、字符和碰撞。发现集在一轮内固定；变化要显式刷新，发生变化时旧调用不能误路由到新工具。
3. 读取配置不启动进程。用户明确启用的命令、参数和环境白名单才可启动本地服务；不能把从仓库发现的命令自动当成可信程序。服务启动与工具调用分别管理授权，清楚区分 `accept-edits`、`read-only`、显式许可等策略。
4. MCP 的自报只读/幂等等提示不直接变成可信的本地权限元数据。工具及其历史结果绑定服务身份；回读大结果也按当前外部来源权限检查，不能因落盘为本地文件就绕开许可。已有 `ResultSource` 只有路径信息，这部分需要扩展并兼容旧快照。
5. 先支持文本与结构化 JSON 结果；保留工具错误与传输错误的区别。遇到不支持的内容类型明确失败/标记不完整，不静默丢失后再声称成功；若服务声明输出 schema，纳入所选支持范围的验证。
6. 启动、发现、调用均有时限和容量门槛；工具执行计入现有预算。服务断开、取消或超时不能推断远端无效果；只做有界连接恢复，不自动重试可能已发送的业务调用。结果未知时停止当前轮并进入待核对状态，也不能由模型重新提出相同调用来自动试探；新的显式继续重新连接并使用当前配置。
7. 更新当前 Prompt 中写死的工具范围，让实际暴露的工具和说明一致。不能增加 MCP 后仍笼统写“不能访问网络”，也不能因此宣称所有外部访问都已许可。

**跟练**：启动仓库内固定版本的工单资料服务，用两个同名工具的服务验证隔离。查询固定工单与长日志，再调用内置文件工具完成修复。写入计数器仅用于验证断线后的未知效果，不连接真实业务系统。

| 必须验收的场景 | 判定依据 |
| --- | --- |
| 真实 stdio 子进程初始化、分页发现、一次调用、退出 | 协议记录、服务端调用计数、实际模型工具表一致；关闭后进程和管道释放 |
| 两服务同名、非法 schema、版本/能力不兼容 | 无碰撞误路由；不兼容服务可见地拒绝，内置工具仍可用；无静默 schema 降级 |
| 恶意只读提示、未启用服务、无交互审批 | 服务发现本身不启动未信任代码；未许可调用次数为零；许可不是服务器自己授予的 |
| 工具错误、结构化结果和长输出 | 错误保持错误；长输出可有限回读；恢复后若当前来源被禁用，历史正文回读仍拒绝 |
| 服务先产生效果再断线、取消或超时 | 观察到的效果计数不因重连而增加；记录结果未知；旧业务请求不自动重放 |
| 超大目录/输出、发现死循环、服务不退出 | 数量、字节、页数、时长都有界；停止后不再启动新调用；本地子进程清理可观察，且不宣称撤销外部效果 |

**代码起点**：[Tool 适配接口](../../packages/core/src/tools/types.ts)、[Agent 工具注入](../../packages/core/src/agent.ts)、[权限](../../packages/core/src/permissions.ts)、[结果来源](../../packages/core/src/result-store.ts)、[恢复协议](../../packages/core/src/execution-recovery.ts)、[宿主生命周期](../../packages/tui/src/cli.ts)。

**本节延期**：Streamable HTTP、OAuth、远端账号管理、MCP Prompts/Resources 专用入口、Sampling/Elicitation、异步 Tasks、多媒体完整呈现及服务市场。stdio 服务本身是本地代码，首版没有 OS 沙箱，不把权限提示说成进程隔离或通用回滚。

## E05-S004：Hooks 与扩展能力验收

**要解决的问题**：把检查要求写在项目规则或技能里，仍不能保证程序执行前后必定运行这项检查。

### 具体做什么

1. 提供三个同步检查点：工具执行前、真实回执保存后、最终完成前。名称和 JSON 契约在 Spec 冻结；首版使用 `command + argv` 执行固定程序，不将模型输出拼进 shell 命令字符串。
2. 项目配置只负责发现 Hook。用户明确启用的命令、配置版本和脚本来源才可执行；本轮绑定启用版本，配置/脚本变化不得继承失效信任。展示状态沿用事件，阻断判断使用等待完成的控制接口。
3. 执行前检查只能通过或阻止，不能批准被宿主拒绝的操作，不能悄悄改参数。参数和当前授权固定后才运行检查；因检查失败尚未执行的工具要留真实的未执行结果。
4. 后置检查失败时保留已经保存的工具回执和文件效果，停止后续工作并明确“工具已执行，检查失败”；不把工具成功改成“没有发生”，不重放工具来补跑 Hook。
5. 完成前检查与 S003 的契约/读取门槛共同决定结果。检查失败返回未完成，首版不由 Hook 自动启动模型修复循环。检查程序约定只验证；如实际文件发生变化，原产物结论必须重新校验或任务失败，不能沿用变化前的通过结论。
6. Hook 子进程有独立次数/输出/超时上限，耗时受当前 Turn 剩余时长约束；取消后等待终止和清理。隔离 stdout 控制 JSON 与 stderr 诊断，非法控制响应、超时或执行错误按失败处理。默认不传整段会话、模型凭据、人工终端内容；不在诊断日志写入脚本正文输出。
7. 将 Hook 开始/结算及未完成检查加入版本化恢复控制，区分工具事实与 Hook 事实；持久化执行意图失败时不启动 Hook。崩溃后不自动补跑未知 Hook；明确继续仍保留必要检查。用户原始任务、脚本自身副作用和失败信息都不能被隐藏。

**跟练**：执行前阻止修改夹具的只读配置；写入后检查报告 JSON；完成前运行该小项目的测试。先故意让检查失败，再由用户明确继续修复，观察“文件已经改了”与“任务尚未完成”同时成立。

| 必须验收的场景 | 判定依据 |
| --- | --- |
| 执行前通过、阻止与当前权限拒绝 | 拒绝时工具实际效果为零；Hook 不能扩权；既有文件 Checkpoint 仍先于受控写入 |
| 后置检查失败 | 原真实回执和文件内容保留，工具执行计数为一；后续调用停止，错误说明执行阶段 |
| 完成前拒绝、产物契约失败、未解决读取 | 任一必要检查失败都不能标记完成；不自动追加无限模型请求；Hook 通过不能清除原 guard |
| 无效 JSON、非零退出、卡住、超量输出、Ctrl-C | 按冻结协议失败且有界；进程与终端恢复；管道/单次模式也不会无声放行 |
| 配置由模型修改、脚本版本变化、未信任命令 | 不自动执行新命令；本轮不热切换到模型刚写的脚本；显式启用与模型文本分开 |
| Hook 前/中/后真实 SIGKILL，随后恢复 | 独立记录 Hook 阶段；已发生工具效果不重放；未知 Hook 不自动补跑；必要检查仍存在 |
| Hook 日志和递归触发 | 无模型密钥、完整会话或人工终端私密字节；Hook 自身不会再次触发同一组 Hook |

**代码起点**：[执行控制与展示事件](../../packages/core/src/loop.ts)、[文件保护](../../packages/core/src/file-mutations.ts)、[完成检查](../../packages/core/src/artifact-completion.ts)、[恢复控制](../../packages/core/src/execution-recovery.ts)、[Conversations](../../packages/tui/src/conversations.ts)。

**本节延期**：自动格式化/改写文件的后置流水线、异步 Hook、HTTP Hook、LLM 判定 Hook、任意事件总线、自动批准、参数改写、自动修复闭环。可信本地脚本有宿主进程权限，受信任并不等于沙箱；未知副作用仍需核对。

## 四课共同的交付门槛

上面各节“必须验收”表全部是交付门槛，未通过的项目不能用总体通过率掩盖。每节在实现前固定案例输入、预期效果、模型配置、预算和检查脚本；失败保留原始记录，修复后针对改动重验，不靠切模型、放宽门槛或无限重跑取成功。

| 层级 | 每节交付要求 |
| --- | --- |
| 纯逻辑与确定性集成 | 覆盖该节全部门槛；抓实际模型请求、工具调用和文件字节，断言效果次数与状态配对 |
| 实际宿主 | CLI、管道/单次、plain 和 TUI 路径；新增交互做真实 PTY 验证，检查退出、信号及 stdin 恢复 |
| 真实进程故障 | 涉及脚本或服务的课程使用真实子进程，S003 验断线/清理，S004 验 SIGKILL/恢复；不能只 mock 一个异常 |
| 真实模型集成 | 每课固定 1 个正常任务 + 1 个拒绝/失败任务，共 8 个案例；建议每例最多 8 次模型请求、12 次工具调用、120 秒，开工时核实并冻结。负例以正确停止和零额外效果为通过，保留实际模型身份和失败记录；小样本不用于宣称泛化成功率 |
| 工程回归 | build、相关类型/格式/lint 与完整既有测试；live 默认跳过要单列。不能把“关闭扩展时原行为不变”只靠肉眼判断 |
| 文档与课程 | 实现、测试、Spec、跟练、复盘、协作记录、导航同一 PR；每课含封面最多 18 页，源与产物一致，PC/H5 可读性及实际交互验收 |
| 证据 | Git 只保存源代码、必要小夹具、测试、复现脚本和精简结果。原始请求、进程日志、截图及失败附件进忽略目录和独立校验归档；保留源码 SHA，不提交大批实验文件 |

所有新增来源/配置都须测“关闭扩展”的兼容路径，以及保存、恢复、压缩后继续的行为。单文件/总字节、条目/分页、单次/整轮时间等上限，要在 Spec 中给出具体数字，并测试阈值前、阈值处、超出阈值；本规划不以空泛的“有界”代替实施验收。

## S004 的最终组合验收

固定一条全链路：根目录和 `api/AGENTS.md` 提供约定 → 激活 `fix-with-tests` → MCP 查询固定工单和长日志 → 内置工具修复文件、补测试 → 后置及完成前 Hook 验证 → 生成通过原产物契约的报告。核对规则来源、技能加载、MCP 服务身份、工具效果、检查结果和最终文件，不能只检查回答中出现了几个关键词。

另做两组故障版本：一组让 MCP 在产生效果后断线；一组在工具已写入、Hook 尚未结算时杀进程。恢复后先展示未知效果和未完成检查，经明确继续再完成必要工作；断线调用、已结算工具和未知 Hook 的自动重放计数均为零。

两个故障版本主要由确定性服务验机制；正常组合案例可复用 S004 的真实模型正例，不另开大规模实验矩阵。E05 四课全部交付后，当前五阶段主线完成；站点部署/图文发布单列，未来选题不影响本阶段收官。

## 教学形式与实施顺序

S001 用目录树和作用域对照；S002 用目录/正文/资源三层展开；S003 用客户端—服务进程时序和调用计数；S004 用执行检查点和故障恢复时间线。每课先展示一个可复现问题，再讲机制、实现和实验，不连续铺满文字卡片。

先列每课的学习目标与必要步骤，再确定篇幅，不套用固定页数模板。每页必须提供新的必要理解或操作；重复动机、机制拆解和总结能合并就合并。详细参数、完整故障矩阵与协议下沉到跟练/Spec。18 页只作上限，保持字号与留白，不把删页内容硬塞到其他页；S001 根据实际主线收敛为 10 页，其余三课各自评估。

先实施 S001，将规则来源、作用域和读取边界跑通；S002 复用这层加载；S003 复用同一条工具执行链，并完成外部来源权限建模；S004 才加入可阻断执行的 Hook 并完成四课组合验收。外部格式参考及本次源码核对记录见[讨论资料](../../.discuss/2026-10-17/e05-course-plan/outline.md)。
