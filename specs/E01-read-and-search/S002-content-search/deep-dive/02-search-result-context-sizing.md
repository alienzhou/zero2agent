# 02. 搜索结果的上下文大小应该怎么控制？

搜索工具一旦不只是返回“命中在哪”，而是开始希望“顺手多给一点上下文”，就会立刻碰到一个很真实的工程矛盾：

- 上下文给少了，Agent 很难判断这个结果值不值得继续读
- 上下文给多了，搜索结果本身又会快速吞掉上下文窗口

在 `S002` 里，这个问题只先做了最基础的处理：

- 提供可选 `context` 参数
- 给搜索结果设置 100 条上限

这足够支撑第一版工作流，但离“生产里怎样更高效地控制上下文”还差很远。

再往后走，真正值得继续讨论的，往往不是“默认给几行上下文”，而是：

> 在有限的上下文窗口里，怎样更动态、更灵活地把最有价值的搜索结果交给 Agent？

如果后续要继续深挖，这里至少可以继续追问几个问题。

## 可以继续追问的问题

### 1. 是否应该更动态地控制搜索结果数量？

第一版是固定上限，但在真实场景里，一个更自然的问题是：

- 能不能根据当前上下文窗口余量，动态决定返回多少结果
- 能不能根据单条结果的长度，动态调整总返回数量
- 能不能在“结果少”时给得更丰富，在“结果多”时主动收紧

也就是说，控制逻辑未必一定是“最多返回多少条”，而可能是“当前还能安全返回多少信息”。

### 2. 如果搜索结果特别多，能不能更快地筛掉不重要的内容？

很多生产问题不在于“搜不到”，而在于“搜出来太多”。

这时就会继续遇到几个问题：

- 能不能基于一些工程性的判断，优先保留更可能相关的结果
- 能不能基于一些经验性的规则，先快速删掉明显噪音
- 能不能结合其他技术手段，让保留下来的内容更接近真正需要读的部分

这些判断未必都要非常复杂，但一旦做得好，往往会比硬性截断更有效。

### 3. 是否应该根据结果规模，动态调整返回内容的丰俭程度？

除了“返回多少条”，还有一个同样重要的问题：

- 当结果很少时，是否应该给更多上下文，帮助 Agent 一次判断清楚
- 当结果很多时，是否应该先只给更短的摘要式结果
- 是否应该把“结果列表展示”和“深一点的内容返回”拆成两层

本质上，这也是在问：**同样的上下文预算，应该优先换更多结果，还是换更厚的单条信息？**

## 为什么这件事值得继续讲

在真实项目里，这类问题并不罕见。搜索结果远超上下文窗口、然后被硬性截断，最后导致 Agent 不能高效定位信息，这其实是很常见的一类体验问题。

所以在这一块，后面其实还有很多事情可以做。当前先把问题提出来，不急着在这里展开答案。如果后面有合适篇幅，也可以专门再把这类动态机制拆开分享。
