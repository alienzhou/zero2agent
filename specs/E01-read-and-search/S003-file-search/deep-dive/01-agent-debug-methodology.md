# Agent Debug 方法论：从静态分析到运行时调试

> 开发 Agent 或用 Agent 开发，都难免遇到 bug。掌握调试方法论，让 Agent 能完整闭环地定位和修复问题。

到了第三个 Story，我们已经用 Vibe Coding 的方式完成了若干功能。在这个过程中，bug 是不可避免的。本文探讨如何高效且准确地调试问题——不仅是人工调试，更重要的是**让 Agent 自己能调试**。

---

## 为什么要关注 Agent Debug

传统 AI 代理遇到 bug 时，最常见的行为是直接基于代码猜测修复。它会告诉你「我 100% 确信问题在这里」，然后改一通代码，结果经常是错的。为什么？因为它只能做静态分析，缺乏运行时信息。

这种「猜测-修复-再猜测」的循环效率很低。我们需要让 Agent 像优秀的人类开发者一样，**基于证据调试，而非基于猜测**。

---

## 调试能力的演进路径

调试能力可以分成四个阶段，每个阶段都比上一个更强大，但实现难度也更高。

最底层是**静态分析**——直接看代码猜问题，简单但能力有限。往上一层是**预埋日志**——开发时在关键位置埋好日志，出问题后分析日志定位原因。再往上是**动态日志**——Debug 时按需插入日志，用假设驱动的方式精准收集信息。最顶层是 **CDP 断点调试**——让 Agent 像人一样操作调试器，设断点、看变量、查调用栈。

下面逐一展开。

---

## Phase 1: 静态型分析

这是最基础的调试方式，也是大多数人和 Agent 打交道时的默认方式。

### 最简单的情况

你跟 Agent 说「点击保存按钮没反应」，它就去分析代码，猜测原因，尝试修复。这种方式的问题在于，Agent 完全不知道运行时发生了什么，只能基于代码结构做推测。

### 好一点的情况

你把终端或控制台的报错粘贴给它。比如：

```
TypeError: Cannot read property 'map' of undefined
    at UserList.render (UserList.tsx:42)
```

有了堆栈信息，Agent 能更精准地定位问题位置。这已经比「没反应」强多了。

### 更进一步

对于复杂问题，你可以帮 Agent 梳理调用链路。告诉它「用户点击按钮，然后调 API，然后更新状态，然后触发渲染，问题出在第三步」。或者让它自己先梳理链路，你来确认和补充。

但即使做到这一步，静态分析的天花板也很明显：它能处理语法错误、类型错误、简单的调用链追踪，但对运行时状态、异步时序、跨进程交互这些问题，基本无能为力。

---

## Phase 2: 动态日志调试

核心理念很简单：**让 Agent 基于运行时证据调试，而非基于猜测**。

### 预埋日志：开发时就要想好

在开发阶段，就应该在关键位置埋好日志。但这里有个取舍问题：如果每个 if 都加日志，代码会变得很脏；但如果完全不加，出问题时又无从下手。

经验上来说，这些位置值得埋日志：API 入口和返回、状态变更点、外部依赖调用、关键分支决策、异常捕获。这不是一个完整的清单，而是一个思考框架——问自己「如果这里出问题，我需要知道什么信息才能定位」。

实践中，我会让 Agent 帮忙梳理关键链路，然后在这些位置加日志。比如让它分析登录功能的调用链，它会告诉你表单提交、API 调用、Token 存储、路由跳转这几个关键节点，然后我们一起决定在哪些位置加什么日志。

### 动态日志：Debug 时按需添加

当预埋日志不够用时，就需要动态添加调试日志。这里有一套叫「Hypothesis Debug」的方法论，核心流程是：

用户描述 bug 后，Agent 不是直接猜修复方案，而是先生成 3-5 个假设。比如「可能是状态同步问题」「可能是 API 超时」「可能是边界条件没处理」。然后 Agent 在代码中插入日志埋点，每个埋点关联一个假设。用户复现问题后，Agent 读取日志，分析每个假设是被证实、被否定、还是没有足够证据。最后基于确认的假设进行修复。

这套方法的关键约束是：**禁止无证据修复**。如果日志没有明确指向问题原因，就不能动手改代码。假设被否定后，相关的代码修改要回滚。

### 日志收集的技术细节

对于浏览器环境，日志需要通过一个简单的 HTTP 服务收集到本地文件。对于 Node.js 等后端环境，可以直接写文件。日志格式推荐 NDJSON（每行一个 JSON），方便后续分析。

日志里需要包含几个关键字段：时间戳、代码位置、日志消息、上下文数据。如果是 Hypothesis Debug 模式，还需要标记这条日志关联的是哪个假设。

## Phase 3: CDP 断点调试

> 本节内容为未来展望，Zero2Agent 将实现一个最小可行版本。

日志调试虽然好用，但有一个根本限制：你只能看到埋点位置的信息。如果问题出在一个你没想到的地方，日志就帮不上忙了。

CDP（Chrome DevTools Protocol）提供了一种更强大的方式：让 Agent 像人一样操作调试器。

### 基本原理

Node.js 应用可以通过 `--inspect` 参数暴露调试端口。Agent 作为 CDP 客户端连接上去后，就能设置断点、暂停执行、读取变量值、获取调用栈。这相当于给 Agent 装上了一双能看到程序内部的眼睛。

### MVP 能力

最小可行版本只需要四个能力：设置断点、暂停和继续执行、读取变量值、获取调用栈。有了这四个能力，就能实现基本的调试循环：Agent 分析代码确定断点位置，设置断点，用户触发操作，程序暂停，Agent 读取当前状态，判断是否找到问题，如果没找到就继续下一个断点。

### 与日志调试的权衡

CDP 调试比日志调试强大得多——你可以在任意位置查看任意变量，不需要预先埋点。但它有一个硬伤：需要 `--inspect` 启动，线上环境通常不会开放这个能力。所以实际使用中，线上问题只能靠预埋日志，CDP 调试主要用于本地开发环境的疑难杂症。

---

## Phase 4: 高级调试能力

> 本节内容为更远的未来方向。

CDP 还有很多高级能力：条件断点（只在满足特定条件时暂停）、Heap 分析（定位内存泄漏）、Profile（分析性能瓶颈）。这些能力对于特定类型的问题非常有用，但实现复杂度也高得多。

---

## 实践中的思考

### 日志优先原则

我现在越来越多地会直接让 Agent 看日志去解决问题，而不是让它直接去修。不管什么样的 bug，都让它先尝试看日志。即使有些 bug 它可能不需要看日志就能快速修好，我也会让它先看。

这样做有几个好处：培养 Agent 基于证据分析的习惯；避免遗漏一些「看起来简单但其实有深层问题」的 bug；日志记录可以帮助后续复盘。

### 分层策略

遇到问题时，我的处理顺序是：先看预埋日志能不能定位；如果不够，就梳理链路、动态加日志、复现、分析；对于特别复杂的问题，才会用到 CDP 断点调试。

线上问题只能靠预埋日志，所以开发时把日志埋好非常重要。本地开发时三种手段都可以用，根据问题复杂度选择合适的方式。

---

## 小结

调试能力是 Agent 完整闭环的关键一环。从最基础的静态分析，到预埋日志，到动态日志，再到 CDP 调试，每一层都是对上一层的补充和增强。

掌握这些方法，不仅能提升用 Agent 开发的效率，还能为你自己开发的 Agent 或产品提供调试能力。毕竟，一个不会调试的 Agent，就像一个不会 debug 的程序员——能力天花板太低了。
