# Agent Debug 方法论：从静态分析到运行时调试

> 开发 Agent 或用 Agent 开发，都难免遇到 bug。掌握调试方法论，让 Agent 能完整闭环地定位和修复问题。

到了第三个 Story，我们已经用 Vibe Coding 的方式完成了若干功能。在这个过程中，bug 是不可避免的。本文探讨如何高效且准确地调试问题——不仅是人工调试，更重要的是**让 Agent 自己能调试**。

---

## 为什么要关注 Agent Debug

传统 AI 代理遇到 bug 时，常见的行为是：
- 直接基于代码猜测修复
- 声称「100% 确信」，但实际经常失败
- 缺乏运行时信息，只能做静态分析

这种「猜测-修复-猜测」的循环效率很低。我们需要让 Agent 像优秀的人类开发者一样，**基于证据调试，而非基于猜测**。

---

## 调试能力的四个阶段

### 能力金字塔

```
              ┌─────────────────┐
              │  Phase 4: CDP   │ ← 最强：实时断点、Heap、Profile
              │  高级调试能力    │
         ┌────┴─────────────────┴────┐
         │  Phase 3: CDP 简单交互     │ ← 断点、变量、调用栈
         │  (MVP)                     │
    ┌────┴───────────────────────────┴────┐
    │     Phase 2: 动态日志埋点            │ ← 按需：假设驱动、精准收集
    │     (核心能力)                       │
┌───┴─────────────────────────────────────┴───┐
│         Phase 1: 预埋日志分析                │ ← 基础：关键链路、事后分析
│         (必备基础)                           │
└─────────────────────────────────────────────┘
```

下面逐一展开每个阶段的方法和实践。

## Phase 1: 静态型分析

这是最基础的调试方式，Agent 主要依赖代码本身和少量的运行信息。

### 1.1 基础调试：描述问题

最简单的方式：直接告诉 Agent 问题现象。

```
用户: "点击保存按钮没反应"
Agent: [分析代码，猜测原因，尝试修复]
```

**局限**：Agent 只能基于代码静态分析，缺乏实际运行时的上下文。

### 1.2 进阶调试：提供报错信息

把终端或控制台的报错粘贴给 Agent。

```
用户: "运行时报了这个错：
TypeError: Cannot read property 'map' of undefined
    at UserList.render (UserList.tsx:42)
    at ..."

Agent: [根据堆栈定位代码位置，分析数据流]
```

**改进**：有了堆栈信息，Agent 能更精准地定位问题位置。

### 1.3 高级调试：梳理调用链路

对于复杂问题，需要帮 Agent 理解完整的调用链路。

**方式一：人工协助梳理**
```
用户: "这个功能的调用链路是：
1. 用户点击按钮 → onClick handler
2. 调用 API → fetchUsers()
3. 更新状态 → setUsers()
4. 触发渲染 → UserList

问题出在第 3 步，状态没更新成功"
```

**方式二：让 Agent 自己梳理**
```
用户: "请先梳理一下这个功能的调用链路，从按钮点击到数据展示"

Agent: [分析代码，输出调用链路]

用户: "第 2 步不对，实际是先检查缓存再调 API，请修正"
```

**静态分析的边界**：

| 能做到 | 做不到 |
|--------|--------|
| 语法错误定位 | 运行时状态 |
| 类型错误分析 | 异步时序问题 |
| 简单调用链追踪 | 跨进程/模块交互 |
| 明显的逻辑问题 | 边界条件触发 |

当静态分析无法解决问题时，就需要进入动态调试阶段。

## Phase 2: 动态日志调试

核心理念：**让 Agent 基于运行时证据调试，而非基于猜测**。

### 2.1 预埋日志（开发时）

在开发阶段，就应该在关键位置埋好日志。

**关键埋点位置**：

| 位置 | 埋什么 | 示例 |
|------|--------|------|
| **入口边界** | 请求参数、触发条件 | API 入口、事件处理器入口 |
| **出口边界** | 返回值、响应内容 | 函数返回、响应发送 |
| **状态变更** | before/after | 状态机转换、关键变量修改 |
| **分支决策** | 走了哪个分支、条件值 | 关键 if/else、switch |
| **外部依赖** | 请求/响应、错误 | API 调用、数据库操作 |
| **异常捕获** | 错误信息、上下文 | catch 块 |

**取舍原则**：
- ✅ 关键链路必埋
- ✅ 状态变更点必埋
- ✅ 外部依赖必埋
- ❌ 不是每个 if 都埋
- ❌ 不是每个函数都埋

**实践建议**：让 Agent 帮忙梳理关键链路，然后在这些位置加日志：

```
用户: "请梳理用户登录的关键链路，并建议在哪些位置加日志"

Agent: "登录链路如下：
1. 表单提交 → 建议日志：表单数据（脱敏）
2. 调用登录 API → 建议日志：请求参数、响应状态
3. Token 存储 → 建议日志：存储成功/失败
4. 路由跳转 → 建议日志：目标路由
..."
```

### 2.2 动态日志（Debug 时）

当预埋日志不够用时，需要动态添加调试日志。

**Hypothesis Debug 流程**：

```
┌──────────────────────────────────────────────────────────┐
│  1. 用户描述 Bug                                          │
│     ↓                                                    │
│  2. Agent 生成 3-5 个假设                                 │
│     "H1: 可能是状态同步问题"                               │
│     "H2: 可能是 API 超时"                                 │
│     "H3: 可能是边界条件"                                  │
│     ↓                                                    │
│  3. Agent 在代码中插入日志埋点                             │
│     每个埋点关联一个假设（H1, H2...）                      │
│     ↓                                                    │
│  4. 用户复现问题                                          │
│     ↓                                                    │
│  5. Agent 读取日志，分析每个假设                          │
│     H1: ❌ REJECTED（日志显示状态一致）                    │
│     H2: ✅ CONFIRMED（日志显示请求耗时 5200ms）            │
│     H3: ⚠️ INCONCLUSIVE（未触发该路径）                   │
│     ↓                                                    │
│  6. 基于确认的假设进行修复                                │
│     ↓                                                    │
│  7. 用户验证修复                                          │
│     ↓                                                    │
│  8. 成功后清理所有调试埋点                                │
└──────────────────────────────────────────────────────────┘
```

**日志格式规范**（NDJSON）：

```json
{
  "hypothesisId": "H2",
  "runId": "run-1",
  "location": "api/login.ts:42",
  "message": "API response received",
  "data": {
    "status": 200,
    "duration": 5200
  },
  "timestamp": 1712505576000
}
```

**关键约束**：
- ❌ 禁止无证据修复
- ❌ 禁止在验证成功前移除埋点
- ✅ 修复必须基于日志证据
- ✅ 假设被否定后要回滚相关代码

### 2.3 日志收集架构

对于浏览器环境，需要一个简单的日志收集服务：

```
浏览器代码                    Log Server              日志文件
    │                            │                       │
    │  fetch POST (JSON)         │                       │
    │ ─────────────────────────► │                       │
    │                            │   append to file      │
    │                            │ ────────────────────► │
    │                            │                       │
                                 │                       │
                                 │  ~/.codeflicker/      │
                                 │  debug.log            │
```

对于 Node.js 等后端环境，可以直接写文件。

## Phase 3: CDP 断点调试（MVP）

> 本节内容为未来展望，Zero2Agent 将实现一个最小可行版本。

CDP (Chrome DevTools Protocol) 让 Agent 能像人一样使用调试器。

### 3.1 基本原理

Node.js 应用可以通过 `--inspect` 暴露调试端口：

```bash
node --inspect=9229 app.js
```

Agent 作为 CDP 客户端连接：

```
┌──────────────┐     CDP (WebSocket)     ┌─────────────────┐
│    Agent     │ ◄─────────────────────► │   Node.js App   │
│ (CDP Client) │                         │ --inspect=9229  │
└──────────────┘                         └─────────────────┘
```

### 3.2 MVP 能力范围

| 能力 | 说明 |
|------|------|
| 设置断点 | `Debugger.setBreakpointByUrl` |
| 暂停/继续 | `Debugger.pause` / `resume` |
| 读取变量 | `Runtime.evaluate` / `getProperties` |
| 获取调用栈 | `Debugger.getStackTrace` |

### 3.3 调试循环

```
┌─────────────────────────────────────────────────────────┐
│  1. Agent 分析代码，确定断点位置                          │
│     ↓                                                   │
│  2. 设置断点                                             │
│     ↓                                                   │
│  3. 用户触发操作 → 程序在断点处暂停                       │
│     ↓                                                   │
│  4. Agent 读取当前作用域的变量值                          │
│     ↓                                                   │
│  5. Agent 读取调用栈                                     │
│     ↓                                                   │
│  6. 分析是否找到问题原因                                 │
│     ├─ 是 → 结束调试，提出修复方案                       │
│     └─ 否 → Resume，设置下一个断点，回到步骤 3           │
└─────────────────────────────────────────────────────────┘
```

### 3.4 与日志调试的对比

| 维度 | 日志调试 | CDP 调试 |
|------|---------|---------|
| 变量值 | 只有埋点位置 | 任意位置实时查看 |
| 调用栈 | 需要预埋 | 实时获取 |
| 执行流控制 | 无法暂停 | 可以 step in/out/over |
| 条件断点 | 需要 if + log | 原生支持 |
| 迭代效率 | 改代码 → 重跑 → 看日志 | 直接断点 → 看值 → 继续 |
| 环境要求 | 较低 | 需要 --inspect |
| 线上可用 | ✅ | ❌ |

## Phase 4: 高级调试能力（展望）

> 本节内容为未来方向，不在当前版本范围内。

### 4.1 高级 CDP 能力

- **条件断点**：只在满足特定条件时暂停
- **Heap 分析**：内存泄漏定位
- **Profile**：性能瓶颈分析
- **Source Map**：TypeScript 断点映射

### 4.2 智能调试 Agent

- 自动识别问题模式，选择合适的调试策略
- 根据历史修复经验，优化假设生成
- 跨会话的调试知识积累

## 实践建议

### 日志优先原则

> "越来越多地会直接让 Agent 看日志去解决问题，而不是直接去解。不管什么样的 bug，都让他先尝试看日志。"

即使是简单的 bug，也建议先让 Agent 查看日志。这有几个好处：

1. **培养好习惯**：Agent 会逐渐学会基于证据分析
2. **避免遗漏**：有时候「看起来简单」的 bug 背后有更深层的问题
3. **留下痕迹**：日志记录可以帮助后续的复盘和优化

### 分层调试策略

```
问题出现
    │
    ├─ 先看预埋日志
    │      └─ 能定位 → 修复
    │
    ├─ 预埋日志不够
    │      └─ 梳理链路 → 动态加日志 → 复现 → 分析
    │
    └─ 复杂疑难问题
           └─ CDP 断点调试（本地开发环境）
```

### 线上 vs 本地

| 场景 | 可用手段 |
|------|---------|
| 线上问题 | 预埋日志分析（唯一选择） |
| 本地开发 | 预埋日志 + 动态日志 + CDP 调试 |

---

## 小结

调试能力是 Agent 完整闭环的关键一环。本文介绍的四阶段方法论：

1. **静态分析**：基础但有局限
2. **预埋日志**：开发时埋好，线上线下通用
3. **动态日志**：假设驱动，精准定位
4. **CDP 调试**：终极能力，适用于本地开发

掌握这些方法，不仅能提升 Vibe Coding 的效率，还能为你自己开发的 Agent 或产品提供调试能力。
