# 02. Agent Debug 方法论：从静态分析到运行时调试

> 开发 Agent 或用 Agent 开发，都难免遇到 bug。掌握调试方法论，让 Agent 能完整闭环地定位和修复问题。

到了第三个 Story，我们已经用 Vibe Coding 的方式完成了若干功能。在这个过程中，bug 是不可避免的。本文探讨如何高效且准确地调试问题：人工调试的经验会写进来作对照，但笔墨会更多落在**让 Agent 自己能调试**这条线上。

---

## 为什么要关注 Agent Debug

传统 AI 代理遇到 bug 时，最常见的行为是直接基于代码猜测修复。它会告诉你「我 100% 确信问题在这里」，然后改一通代码，结果经常是错的。为什么？因为它只能做静态分析，缺乏运行时信息。

这种「猜测-修复-再猜测」的循环效率很低。我们需要让 Agent 像优秀的人类开发者一样，**先把运行时证据摆上桌，再谈改哪里**。

---

## 调试能力的演进路径

调试能力可以分成五个阶段，每个阶段都比上一个更强大，但操作难度也会变高。

```
                        ┌─────────────────┐
                        │  Phase 5: CDP   │ ← 最强：实时断点、Heap、Profile
                        │  高级调试能力    │
                   ┌────┴─────────────────┴────┐
                   │  Phase 4: CDP 简单交互     │ ← 断点、变量、调用栈
                   │  (MVP)                     │
              ┌────┴───────────────────────────┴────┐
              │     Phase 3: 动态日志埋点            │ ← 按需：假设驱动、精准收集
              │     (核心能力)                       │
         ┌────┴─────────────────────────────────────┴────┐
         │           Phase 2: 预埋日志                    │ ← 开发阶段预置、关键链路覆盖
         │           (基础保障)                           │
    ┌────┴──────────────────────────────────────────────────┴────┐
    │                  Phase 1: 纯静态分析                        │ ← 看代码、看报错、梳链路
    │                  (入门起点)                                  │
    └────────────────────────────────────────────────────────────┘
```

能力可以想成一座五层塔：底层是**纯静态分析**，直接看代码和报错猜问题，简单但天花板低；往上是**预埋日志**，开发时把关键链路钉住，出事有据可查；再往上是**动态日志**，按假设补埋点，把信号收细；第四层是 **CDP 简单调试**，让 Agent 像人一样操作调试器，设断点、看变量、查调用栈；塔尖是 **CDP 高级能力**，条件断点、Heap 分析、性能 Profile 都在这里。下面按层往下拆。

---

## Phase 1: 纯静态分析

这是最基础的调试方式，也是大多数人和 Agent 打交道时的默认方式。最粗糙的场景是你跟 Agent 说「点击保存按钮没反应」，它只能顺着代码结构猜，完全不知道运行时发生了什么。好一点的做法，是把终端或控制台的报错贴过去，例如：

```
TypeError: Cannot read property 'map' of undefined
    at UserList.render (UserList.tsx:42)
```

堆栈一上来，定位会准很多。再往上，你可以帮它把调用链路讲清楚：用户点了什么、依次经过哪些模块、你怀疑卡在第几步；也可以让它先画链路，你来补洞。即便如此，静态分析能覆盖的仍主要是语法、类型和浅层调用关系；一旦涉及运行时状态、异步时序、跨进程交互，它就很难单独扛住。

---

## Phase 2: 预埋日志

预埋日志是在**开发阶段**就决定好的：每个 if 都打日志会脏，完全不打又会在出事时两眼一抹黑。常见落点包括 API 入口与返回、状态变更、外部依赖、关键分支和异常捕获；更实用的问法是「如果这里出问题，我最需要知道哪几条信息」。

实践中我会先让 Agent 把链路梳理下，然后让它自己在关键出埋上日志，最后再补充下我自己的要求。比如登录流程，它往往能列出表单提交、API、Token、路由跳转这些节点，日志就挂在转折点上。预埋的核心价值在于：出问题时不需要重新构建现场，日志本身就是你留给未来自己的证据链。

---

## Phase 3: 动态日志调试

核心理念可以压成一句话：**用运行时证据说话**，先把现象钉在数据上，再讨论改法。预埋是开发时埋下的底，动态日志是出了问题再按假设补的那层。下面这套时「Debug Agent」的工作流程， 先假设、再取证、再动手：

```
┌──────────────────────────────────────────────────────────┐
│  1. 用户描述 Bug                                          │
│     ↓                                                    │
│  2. Agent 分析代码，生成 3-5 个假设                         │
│     "H1: 可能是状态同步问题"                               │
│     "H2: 可能是 API 超时"                                 │
│     "H3: 可能是边界条件"                                  │
│     ↓                                                    │
│  3. Agent 在代码中插入日志埋点                             │
│     每个埋点关联一个假设（H1, H2...）                      │
│     ↓                                                    │
│  4. 用户复现问题                                          │
│     ↓                                                    │
│  5. Agent 读取日志，分析每个假设                          │
│     H1: ❌ REJECTED（日志显示状态一致）                    │
│     H2: ✅ CONFIRMED（日志显示请求耗时 5200ms）            │
│     H3: ⚠️ INCONCLUSIVE（未触发该路径）                   │
│     ↓                                                    │
│  6. 基于确认的假设进行修复                                │
│     ↓                                                    │
│  7. 用户验证修复                                          │
│     ↓                                                    │
│  8. 成功后清理所有调试埋点                                │
└──────────────────────────────────────────────────────────┘
```

用户描述完 bug，Agent 先列出几条可检验的假设，再给每条假设配上埋点；用户复现一次，日志回来，Agent 逐条标注证实、否定或证据不足，只在有支撑的假设上改代码。约束写死也很简单：**没有日志指向，就不动刀**；假设被否定的改动，该回滚就回滚。

**日志怎么落盘**：浏览器侧通常走一个小 HTTP 服务把 NDJSON 对接到本地文件；Node/Python 等后端可以直接写文件。

```
浏览器代码                    Log Server              日志文件
    │                            │                       │
    │  fetch POST (JSON)         │                       │
    │ ─────────────────────────► │                       │
    │                            │   append to file      │
    │                            │ ────────────────────► │
    │                            │                       │
                                 │  ~/.zero2agent/       │
                                 │  debug.log            │
```

格式上推荐 NDJSON，一行一条 JSON，后面好 grep、好对齐。字段上至少要有时间戳、位置标识和运行变量等上下文，这样 Debug Agent 才能看出来这条日志是在验哪条假设。

---

## Phase 4: 真断点调试

> 本节内容为未来展望，Zero2Agent 将实现一个最小可行版本。

日志再好用，也只能照亮你埋过点的路径；问题如果出在没想到的分支，光加日志会越加越散。例如对于 Node.js 程序可以使用 CDP（其他语言栈也有自己的 Debugger）。CDP（Chrome DevTools Protocol）给的是另一条路：让 Agent 像人一样操作调试器。Node 侧用 `--inspect` 把调试端口露出来，Agent 作为 CDP 客户端连上去，就能下断点、暂停、读变量、拉调用栈，相当于把「程序内部此刻长什么样」摊开来看。

MVP 里四个能力就够撑起一轮闭环：下断点、暂停与继续、读当前作用域、取调用栈。流程可以收成下面这张框图：

```
┌─────────────────────────────────────────────────────────┐
│  1. Agent 分析代码，确定断点位置                          │
│     ↓                                                   │
│  2. 设置断点                                             │
│     ↓                                                   │
│  3. 用户触发操作 → 程序在断点处暂停                       │
│     ↓                                                   │
│  4. Agent 读取当前作用域的变量值                          │
│     ↓                                                   │
│  5. Agent 读取调用栈                                     │
│     ↓                                                   │
│  6. 分析是否找到问题原因                                 │
│     ├─ 是 → 结束调试，提出修复方案                       │
│     └─ 否 → Resume，设置下一个断点，回到步骤 3           │
└─────────────────────────────────────────────────────────┘
```

一轮下来，就是「猜断点 → 下断点 → 用户触发 → 读现场 → 判断要不要换断点」的循环。

和日志相比，CDP 强在不用预先知道该往哪插桩，弱在依赖 `--inspect`、线上几乎不可用；所以线上仍要靠预埋日志兜住，CDP 更适合本地啃硬骨头。

---

## Phase 5: 高级调试能力

> 本节内容为更远的未来方向。

CDP 还有很多高级能力：条件断点（只在满足特定条件时暂停）、Heap 分析（定位内存泄漏）、Profile（分析性能瓶颈）。这些能力对于特定类型的问题非常有用。

---

## 实践中的思考

我自己用 Agent 修 bug 时，会刻意养成「先看日志、再改代码」的顺序：哪怕有些问题它扫一眼代码也能蒙对，我也尽量让它先把日志跑一遍。好处很实在，证据链养成了，浅层 bug 不容易盖住深层问题，事后复盘也有据可查。

分层上，我的习惯是先看预埋日志能不能兜住；兜不住再梳链路、补动态埋点、拉复现。当然本地遇到特别妖的，也可以考虑开 CDP，不过一般动态日志成功率就很高了。线上没有 inspect，只能靠开发阶段把预埋日志下扎实。本地理论上五层都能走，按问题复杂度选工具即可。

---

## 小结

调试能力是 Agent 完整闭环里承上启下的一环：纯静态打底，预埋日志在开发期把关键链路钉住，动态日志按假设补细节，CDP 在本地把现场摊开。五层叠在一起，像接力：能走多远，取决于你在每一层愿意把信号铺多细。

把这些方法练熟，你自己用 Agent 写代码会省很多时间；未来连调试能力也会非常重要。毕竟都接不住的 Agent，很难谈得上可靠。
