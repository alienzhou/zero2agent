# 重试一次请求，不等于业务只发生一次

[课程](../README.md) | [边界](../details/04-backlog.md)

客户端没有收到完整回复，至少有两种可能：服务端还没处理请求，或者服务端已经处理了、回复在路上丢失了。客户端看到的连接错误不能区分它们。重发能提高获得回复的机会，却无法凭此保证远端只计算、只计费一次。

## 先确定恢复对象

本课只把 SDK 传输放进 RequestExecutor。模型请求失败时，重发已有发送视图；write_file、terminal、权限批准和 Checkpoint 捕获都不放进这层重试函数。这条边界能让本地已结算工具不因传输恢复而重放。

它也有实际限制。第一次请求在完整回复之前断掉，本地没有执行半截 tool_use，因此没有对应本地效果。第一次工具已经执行，下一请求断掉，历史保留工具结果，恢复从后面的模型请求开始。如果模型在完整的后续回复中再次提出写入，那是新的调用，仍需授权与保护，并非执行器偷偷重放。

| 看见的证据 | 可以做什么 | 不能推断什么 |
| --- | --- | --- |
| 缺少 message_stop | 草稿作废，按传输策略有限恢复 | 远端没有计算过 |
| 有完整 tool_use 和配对结果 | 向模型保留这一事实 | 整轮失败等于工具没发生 |
| 有 exitCode=7 | 报告真实工具错误 | 命令没有写文件或没有发出外部请求 |
| 崩溃后只剩缺失终态的日志 | 先核对实际状态 | 自动重放缺失回执的操作一定安全 |

## 身份帮助追查，不自动产生幂等性

logicalRequestId 关联一次逻辑发送；requestId 与 attempt 关联每次实际尝试。它们回答“是哪一次尝试失败了”，没有让服务端按这个身份去重。本课没有假定供应商支持幂等键，也没有实现外部系统的去重协议。

若未来要对支付、发信或远端提交增加幂等性，需要把业务操作身份传给明确支持该契约的接收方，保存结果，并定义身份复用、冲突与过期的行为。仅在客户端生成 UUID，再把操作包进 retry，并不能获得这些保证。

## 用量缺失也是一种需要保留的事实

失败尝试可能拿不到 usage。日志应保留尝试与错误类别，让人知道证据没有闭环；不能补一个 0 token，也不能按固定价格猜费用。恢复预算控制请求数量与等待时间，费用结算仍以服务实际证据为准。

离线实验用确定性响应验证边界，真实服务实验让模型提出一次真正的写入，再在写入后的请求上注入503。前者证明分支可控，后者证明与当前服务集成；两者都不证明所有供应商或所有任务具有一次效果保证。跨进程未知效果的核对与安全继续，留给 E04-S004。
