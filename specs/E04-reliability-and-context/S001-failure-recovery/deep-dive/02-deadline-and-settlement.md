# 时间预算到了，为什么还要等工具结束

[课程](../README.md) | [边界](../details/04-backlog.md)

Promise.race 能让等待方先返回，不能把另一个 Promise 正在做的写入撤销。如果工具忽略 signal，超时返回后它仍可能改文件。这时立刻开放下一轮，会让新任务与旧写入竞争，也会让保存的历史错误地声称工具尚未发生。

## 请求与工具有不同的取消契约

SDK 传输接受 AbortSignal。请求执行器的时限覆盖连接和整个 SSE，并把同一个 signal 交给真实传输，所以结束等待时也要求连接关闭。局部等待只适用于这个可取消接口；测试核对的是服务看到连接关闭，而不只是界面停止转圈。

工具执行器则直接 await execute。整轮时间到达后取消 signal，停止启动下一项，但仍等待已经开始的工具真实结算；把结果与原调用配对，再结束 run。原生终端继续使用已有进程控制接口，自定义 JS 需要自己遵守 signal。本课没有为任意代码建立硬隔离。

## 时间上限定义的是哪件事

| 限制 | 本课保证 | 本课不能保证 |
| --- | --- | --- |
| 单次请求时限 | 终止支持取消的传输，不接受过期草稿 | 远端立刻停止计算 |
| 整轮时间预算 | 不再启动新的请求和工具，发出取消 | 任意 JS 在指定毫秒内硬退出 |
| 同类失败阈值 | 结算当前结果后停止重复执行 | 当前错误操作没有副作用 |
| 宿主输入忙状态 | 前一 run 结算前拒绝新的 run | 可以安全地并发修改同一文件 |

## 更强的硬终止需要更多协议

如果以后把不可信工具放到 Worker 或子进程，终止执行会更直接，但“杀掉进程”仍不能说明外部效果没有发生。效果前后的持久记录、恢复时的核对、权限边界和文件冲突还需要独立设计；多文件写入也不能因此被叫作原子事务。

因此本课把两个状态分别处理：停止新工作，以及当前工具结算。课程的晚到写入测试故意忽略 signal，证明在预算错误之后文件确实可能改变；宿主等待到这条结果留下，再接受下一条请求。这个约束让恢复证据与现实一致，代价是工具不配合时，整轮可能继续等待。

生产集成自定义工具时，应让它周期性检查 signal、关闭自己的资源并返回可解释结果。若工具会无限挂住，需要另外设计隔离和人工恢复入口，不能通过丢弃 Promise 来制造“已停止”的表象。
