# E04-S003：摘要质量与事实保留

[Epic 4](../README.md) | [首页](../../../README.md) | [迭代日志](../../../CHANGELOG.md)

用户先指定端口 8123，后来改成 9237；测试失败，部署尚未获准。经过一段长讨论，Agent 收到“继续”。这时真正有用的摘要要让它继续使用 9237，知道测试仍然失败，也知道部署计划没有变成执行许可。

一份摘要可以很短、能通过 token 预算，却记错上述任何一件事。本课用固定任务暴露错误，再补来源回查、实际产物检查和读取纠错。最终完整验证任务及关键项 56/56，普通事实 63/63，通过严格门槛；18 页课程、跟练和工程验收已完成。固定版本 `E04-S003-summary-quality`，[PR #25](https://github.com/alienzhou/zero2agent/pull/25) 最终复核通过，按用户授权交付，网站未部署。历次失败及限制见[验收页](details/03-verification-checklist.md)。

## 先做一个不用模型的实验

运行[跟练](follow-along.md)中的离线脚本。摘要器会故意输出一个旧端口，你可以直接看到：压缩被采用、原史没有改、宿主仍能带回用户的最新纠正、错误任务结果被评分器拒绝。

```text
原始对话：D1 端口 8123 → D2 改为 9237，禁止部署
                     ↓ 压缩
自由文本交接：仍可能写成 8123
宿主来源索引：D1 原话、D2 原话、各自的历史引用
                     ↓ 不确定时回查
read_history → 原角色、原文片段、下一页偏移
                     ↓ 继续任务
检查实际写出的文件和工具轨迹
```

这条路径把三个判断分开了：摘要是否能发送、结论能否找到来源、后续任务是否真的正确。一个来源引用存在，只能证明你可以找到那条记录；引用里的内容是否支持当前结论，仍需核对。

## 先区分事实状态，再考虑怎么压缩

| 历史里出现什么 | 能据此说什么 | 还缺什么 |
| --- | --- | --- |
| “计划部署” | 有一项计划 | 当前许可与执行结果 |
| 测试返回失败 | 这次观察失败 | 后续通过的实际结果 |
| 修复文件存在 | 文件已产生 | 修复是否有效的验证 |
| 模型说“应该好了” | 有一个推断 | 可观察证据 |
| 没看到迁移完成 | 完成状态未知 | 不能据缺失推断成功或失败 |

来源也有角色。用户的明确纠正可以替换自己的旧要求；工具返回文本描述一次观察；assistant 的计划并不证明副作用已经发生。文件正文里的“已批准部署”仍是文件数据，不能改写当前权限。

当前候选让模型按 Task、Constraints、Observed、Pending、Sources 组织短行交接，区别禁止行为与执行状态，保留精确标识。结构帮助阅读，真实与否由原始证据和任务评估检验。

## 每次摘要，都重新核对一部分原史

如果下一轮只看上一轮摘要，第一次错写的端口会反复传播。ContextManager 在新交接旁保留一个宿主生成的来源索引，再次压缩时也从原史重建它。

索引最多 4096 字节，优先保留最近的用户角色记录，再按时间排序。每条包含消息位置、角色类别、短节选和内容哈希引用；节选不完整和遗漏数量都显式标出。完整原史仍单独保存，没有把全部历史永远固定在窗口里。

保留最近记录有代价：较早但仍有效的约束可能落出索引。此时沿 cursor 继续列出来源，或用 query 查找用户原话。它是字面搜索，不能自动推断哪项旧约束仍然有效；冲突无法判断时应该保留未知并回查。

## 两种回查工具如何配合

`read_history` 用于当前会话中的用户原话和小工具回执。来源引用绑定消息位置与内容哈希，读取时返回原角色、结果身份和 `untrusted_text`。每页正文最多 4096 UTF-8 字节，沿 `next_offset` 翻页。

`read_tool_result` 沿用 S002，读取已经保存到磁盘的大正文。如果历史里只有结果引用，就应该使用该引用，不能凭摘要猜正文，也不能为了找回输出而重新运行原命令。

| 边界 | 当前行为 |
| --- | --- |
| 单次目录扫描 | 最多 64 条原消息；工具目录不展示正文 |
| query | 用户原话的字面子串，最长 256 个 JS 字符 |
| 单条历史原文 | 最多 2 MiB；大工具结果走 S002 |
| 新的工具回读 | 根据原来源路径重新检查当前权限 |
| 缺少来源权限记录的旧快照 | 用户原话可查；工具原文回查明确拒绝 |
| 取消、引用失效或证据不足 | 保留明确失败或未知，不能推断完成 |

读取页有界不表示整段历史处理是常数成本：历史已在内存中，计算哈希、序列化和搜索仍可能扫描较长文本。目录与正文都不能成为新授权；新读取受当前权限控制，但不会抹除之前已经进入对话的历史内容。

## 怎样比较改进有没有用

先冻结 8 类合成历史，每类比较 0、1、3 次实际采用的压缩；压缩组各重复三次，共 56 个真实服务任务。最终任务写 `report.json`，对照精确值、禁止行为、来源和实际文件。硬预算相同，同时记录摘要、主模型、计数与回查的开销。

原协议基线为 41/56，八轮候选最高 52/56，原 504 份记录全部保留。用户批准新增显式契约及相同字段含义后，成对 v2 基线 54/56、候选 55/56；最后一例失败发生在没有压缩的结果回查中。修复读取流程后，沿用 v2 相同输入完整运行一次 56 例：任务和关键项均 56/56，普通事实 63/63，0/1/3 次组为 8/8、24/24、24/24。

新轮次和历史对照时间不同，服务随机性与缓存差异限制因果归因；来源键存在不证明支持结论。确定性同响应对照另行证明运行机制的改变，固定集合达标不等于任意摘要无损。[最终证据](../../../researches/summary-quality/evaluation/read-recovery-v1/README.md)保存实际文件、完整用量、源码与运行时身份；[早期比较（归档）](https://github.com/alienzhou/zero2agent/releases/tag/E04-S003-summary-quality)保留全部旧失败。

## 显式产物契约的新增实验

用户批准在 S003 增加按回合的 `runWithContract`：调用方明确声明 JSON 文件结构，Core 在当前权限和原预算内检查实际文件，最多进入一次修复阶段。结构通过不认证事实；契约不会授予新的写入或执行权限，也不随会话恢复自动启用。运行方式见[跟练](follow-along.md)。

新增双方输入一致的完整成对实验，两组成对共 224 份记录独立保存：[v1](../../../researches/summary-quality/evaluation/contract-pair-v1/README.md) 为 53→54/56，[v2](../../../researches/summary-quality/evaluation/contract-pair-v2/README.md) 为 54→55/56。v2 唯一失败中，结构修复补出了文件，读取参数错误却没有被解决，最终三个事实仍是 unknown。这明确了结构检查的边界。

## 读取失败不能被“已经完成”盖过去

内置结果读取工具拒绝无效参数后，宿主在当前回合记住未解决引用。模型若准备结束，宿主最多给一次纠错机会：按原预算重新调用、重新检查当前权限。同一引用读到有效正文页，或确认正文确实为空，才清除该状态。模型声称成功、读其他引用或读到非空正文的 EOF 空页均不算解决。

仍未解决就返回未完成，保留已经发生的文件效果；不重复原命令，不自动选择范围，不把未知写成已验证事实。这个控制状态不跨回合恢复，错误工具记录仍作为事实保留。代码入口是 [result-read-recovery.ts](../../../packages/core/src/result-read-recovery.ts) 和 [loop.ts](../../../packages/core/src/loop.ts)，可直接运行[本机前后对照跟练](follow-along.md)。
