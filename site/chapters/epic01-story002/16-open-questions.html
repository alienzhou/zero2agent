关于 Grep：
留给实际产品的三个开放问题
在这一课的拆解中，我们看到了 Grep 搜索的基本设计方案，以及多种突破路线。
但篇幅有限，有几个也很重要的问题无法展开了，它们都需要在工程上权衡，这里也留给大家讨论。
Q1：动态上下文截断——到底给 Agent 多少才恰好？
搜索返回结果有体积，会消耗 Agent 的上下文。结果极少时，是否应自动附带更厚的上下文？命中极多时，该返回更多候选路径，还是只给几条但附带更长代码段？不同样的上下文容量，是否该有不同策略？
RAG 真的死了吗？
Q2：走出封闭域后，搜索的规则会彻底改写
代码仓库是结构收敛的"封闭域"——大多说超不过几万文件。但 Agent 走出 IDE 去查官方文档、搜 GitHub Issues、找设计参考时，就坠入无序的"广域"。封闭域杀手锏——正则、本地索引、AST——在广域中可能全部失效。RAG 等其他方案，很可能不得不重夺主导权。
Q3：索引加速是用内存换时间——有平衡点么？
Cursor 的 Sparse N-gram 索引、ast-grep 的语法树解析，都在用本地资源换取检索速度。在企业级的开发场景里，当多个编辑器窗口、多个项目同时跑着，这块是否是个需要考虑的问题。
