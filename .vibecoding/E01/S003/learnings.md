# E01-S003 经验总结

---

## 协作模式

1. **多会话并行是效率倍增器**：S003 跑了 5 个对话会话，各有分工——主讨论、benchmark 设计、benchmark 实现、review + deep-dive、模板规范。主线讨论不被 benchmark 的实现细节阻塞，benchmark 又能拿到完整的设计决策作为输入。关键是通过 `@` 引用 transcript 让各会话共享上下文。

2. **"充分准备 + 一键委托"**：benchmark 实现是最典型的案例——用户只给了一条指令，AI 自主完成了全部代码编写、调试、验证。这能成立的前提是讨论阶段产出了足够详尽的 D02 文档（包含精确的命令模板和每个 wrapper 的完整代码）。准备越充分，委托越放心。

3. **Skill 附件切换 AI 角色**：同一个 AI，附 `discuss-for-specs` 变成讨论者，附 `repo-research` 变成调研员，不附 Skill 就是实现者。Skill 相当于给 AI 装了一套"工作流模板"，省去每次手动描述期望行为的成本。

---

## 讨论策略

1. **方法论复用 > 从零设计**：S002 建立的五维评估框架在 S003 直接复用，用户一句话引导（"你看一下之前 grep search 的 DeepDive"）就够了。好的方法论是有复合利息的——投入一次，后续迭代持续受益。

2. **简短反馈推动迭代**：用户的反馈从不啰嗦——"研究浅了"推动调研从扫表面到追调用链，"代码太多了"推动 Spec 删掉 10+ 个代码块，"模板不要太严苛"推动区分骨架和可选。不需要逐行指出问题，让 AI 自己对照标准做判断。

3. **用户发现 AI 看不到的问题**：ToolContext cwd 的需求是用户主动提出的——这是一个跨工具的一致性问题（read_file / grep_search / list_directory / find_files 都依赖相对路径）。AI 在单个工具的上下文里不容易看到这种全局问题，用户的全局视野在这种时候特别有价值。

4. **明确"沉淀"指令**：讨论完成后明确说"沉淀一下决策"，确保结论从对话流转化为文档。没有这一步，好的讨论结论可能就消散在对话历史里了。

---

## 技术选型

1. **Benchmark 验证直觉而非推翻直觉**：D01 定性分析的结论（rg 最优）被 benchmark 完全验证了。Benchmark 的价值不在于"推翻"，而在于(a) 用数据量化差距（rg 比 npm glob 快 5 倍），(b) 发现定性分析没注意到的细节（`fs.glob` 深度限制、npm glob 在 macOS case-insensitive 文件系统上的字符类问题）。

2. **公平性是 benchmark 的灵魂**：用户反复强调"控制变量、不引入胶水代码"。最终方案：CLI 工具零 wrapper 直接调用，Node API 用最小化 .mjs 包装（3-15 行）。公平性不是 AI 自然会想到的——它倾向于"统一接口"（给所有工具套 wrapper），但这恰好破坏了公平性。

3. **平台兼容性比想象中重要**：benchmark 实现阶段遇到的 5 个 bug 中有 4 个是 macOS 平台特有的（bash 3.2 无关联数组、BSD grep 无 PCRE、全角逗号干扰 bash 变量解析）。教训：shell 脚本要格外注意跨平台兼容。

---

## 规范建设

1. **规范随项目演进长出来**：写 S003 Spec 时发现 `.authoring/` 缺 `details/` 模板，顺手补全了 5 个。这不是"设计不充分"——规范最好是在实践中发现缺口再补，而不是一开始就试图设计完整。

2. **模板的分寸——骨架 vs 按需保留**：太死板的模板让人硬凑内容，太松散的模板等于没有模板。每个模板明确区分"骨架"（必须保留的结构）和"按需保留"（有内容才写的部分）。

3. **模板不能被具体 Story 污染**：从 S001/S002 的实际 Spec "反推"出来的模板结构，容易带入 Story 特有的内容（如"按工具/接口组织"只适合做工具的 Story）。模板应该捕捉的是通用骨架和意图，而非某个 Story 碰巧采用的组织方式。

4. **Spec 记录设计意图，不是代码副本**：代码会变，Spec 不会跟着更新。适合放进 Spec 的是设计判断、接口契约、数据流、取舍理由；不适合放的是完整实现、参数列表、类型定义。代码只在"文字说不清楚"时才贴关键几行。
