# 保留的失败与修正

首次诊断测试 1/5 通过：四个实际 Agent/SDK 用例在请求前被上下文预算拒绝，因为夹具使用未知 model 且没有显式 contextWindow；还发现自定义工具夹具把 input_schema 误写为 inputSchema。修正夹具为仓库已知模型与真实 Tool 契约，不降低生产校验。该首次结果不视为实现通过。

首轮新宿主用例 13/14 通过。日志浏览 PTY 用例在模型文字出现后立即按 Enter，此时宿主仍在保存；原有 TUI 正确保留草稿并要求结算后再发送。将夹具等待点改为实际「已完成」状态，不削弱运行中输入保护；查看断言改为屏幕底部真实可见的日志记录。

第一次完整离线回归发现 4 个旧 Core 契约断言失败：未启用诊断时也向 ToolContext 添加了 onResultMetadata，改变了默认上下文形状。修正为仅在诊断观察者或调用者元信息观察者存在时附加回调；--no-log 同时不安装空诊断观察者。保留旧契约断言，不改为宽松匹配。

4. 专用只读查看器引入后，旧 PTY 测试仍直接在查看器里发送 `/help` / 下一轮文本，没有先 Esc 返回；独占焦点正确阻止了它们，首轮 17 项为 16 通过、1 失败。修正测试按产品流程返回列表再返回对话，增加窄屏 Home/End 滚动，再重新运行。未放开查看器的输入拦截。

5. 返回查看器后 `/logs` 会把界面置为空闲；第一次返回流程测试错误地等待“已完成”，实际已正确显示“等待输入”。17 项仍是 16 通过、1 测试等待失败。将断言改为真实空闲状态，同时要求 End 出现非第一页行号、Home 回到第一行，不放宽生产焦点规则。

6. 全套离线第二轮：CDP 1、Core 409 通过；E2E 144 通过 / 1 失败 / 55 跳过。原 Ctrl-X/Ctrl-S 测试收到模型文本后立刻发送下一轮，但文本流结束尚未保证会话保存与日志 flush 已完成。按原草稿协议，忙时 Enter 不发送。保留 `second-offline-summary.json` 与 gzip 输出；用例改为先等待实际“zero2agent · 已完成”，仍检查真实 PID、后台存活及退出清理，不放宽生产执行协议。
