# E03-S006 复盘：成本和恢复保证一起设计

课程分发约束应在内容计划时就明确。用户补充小红书单篇最多 18 页且包含封面后，把重复的状态边界与末页收束分别合并，得到 1 封面 + 17 内容；字号不变，关键机制仍单页讲解。制作模板、AGENTS.md 与构建检查同步限制，避免 18 页正文之外又增加封面。

[课程](../specs/E03-product-foundations/S006-file-checkpoints/README.md) | [失败记录](../.vibecoding/2026-10-07/e03-s006-file-checkpoints/failures.md)

用户明确拒绝第二套 Git 模拟快照后，最重要的工作是重定捕获范围。只处理专用工具声明的路径，避免把目录扫描、依赖和任意 shell 变化偷偷带入承诺；再用内容定义分块复用大文件的小改动。这两层选择分别控制无关工作和历史增长。

首轮高熵数据实验空间收益明显，但生产保护路径更慢。完整校验、fsync、冲突检查和持久恢复意图都要付出时间。把简单基线的 4 ms 和生产方案的 162 ms 并排写成算法优劣会误导读者，因此明确区分存储基线和等保证性能测试。

真实验证找出了纯算法测试看不到的问题：macOS 物理路径别名、成功状态误发 stderr，以及 HOME/cwd 相同导致只读启动被过早存储校验阻断。原契约测试没有被放宽；修正实现后复测。课程布局也出现一次终端行重叠，保留失败报告后修改框高度。

回退必须拥有自己的恢复协议。保存 from/to 意图后，部分完成可以按磁盘状态继续；回退结果本身又能被 undo。代价是更多清单与验证逻辑，收益是中途失败时不用猜“执行到哪一步”。

仍有限制：不隔离任意外部写入者、不捕获 shell、每次工具调用一条记录、没有整轮 rewind，也没有所有元数据恢复。首个版本的内存以有界整文件缓冲为主，后续可在真实工作负载推动下考虑流式与更紧凑清单。人工审查、跨平台验证和上线部署继续单列。

最终自查又发现恢复意图交接的窗口：新意图已持久化、旧 pending 尚未移除。仅“先写意图”还不足够，必须定义两个状态同时存在时如何推进。新增故障注入先复现双 pending 阻塞，再以 sourceId、完整路径和版本校验来安全移交证据，保留对无关 pending 的拒绝。
