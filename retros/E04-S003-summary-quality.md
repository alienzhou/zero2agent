## 先测任务，才能知道要改什么

基线已经能写出简短摘要，也有真实样例能记住纠正。固定 8 类任务后才暴露：端口纠正、长期禁止项、诊断标识、实际状态和输出契约会在不同位置失效。无压缩组也失败，表明“压缩丢事实”不是所有问题的解释。文件和调用轨迹比一句“已完成”提供更多证据。

协议预跑有两次实质问题：并发触发服务限流，无压缩组意外触发后台摘要。先保留原件并修正条件，再冻结正式基线；比较期间不更换剧本、答案和预算。评分器后来漏检额外顶层字段，也必须对所有版本一致补核，不能只修候选的分数。

## 来源帮助纠错，但没有免费保证

宿主从原史生成身份与节选，后续摘要再次看到原话；模型可以回查用户纠正和工具小回执，大正文继续使用 S002。恢复后工具来源按当前权限检查，引用不能成为授权。有限索引会遗漏，字面搜索会找不到，历史文本仍需按原角色理解。

第一候选增加这些机制后，严格成功反而只有 40/56。第二候选把交接缩短，避免复制大段收据，区别“禁止部署”与“是否部署过”，再提示按当前任务继续，才达到 49/56。它同时增加回查和输入成本：主请求 132→169，回查 8→121；不能只展示成功率。

## 保留下来的失败能继续教什么

第二候选仍有不写文件、字段名错误、非法 JSON、半截错误码和摘要采用失败。读到了正确事实不等于按契约完成任务；eof=false 的最后几个字节也可能改变精确标识。一次 ContextBudgetError 没有保存失败摘要响应，当前证据无法细分原因，不该根据三个 end_turn 请求猜测它一定出在哪里。

v2 默认工程测试 657 项通过，证明协议、权限、取消、分页和恢复路径等行为。真实模型对照证明这一组任务的效果；五个 CLI 进程的固定 HTTP/SSE 测试证明跨进程契约。三种证据分别保留，AI 作者审查也不能替代人工审阅。

## 后续决定

用户已确认继续当前模型、保留严格门槛。继续改进应先针对可验证的机制缺口建立复现，避免在同一组失败上无限重复直到偶然全绿；换模型或改为研究成果交付需要明确决定，不能暗中改条件。课程暂以 18 页研究稿展示真实结果和边界，独立未见任务留作后续验证。

## 第三轮暴露的边界

v3 结果 47/56，低于上一轮。减少一次不必要生成有确定性机制收益，但整组任务没有随之提高；不能用局部测试代替总结果。新增分类使一次失败能明确定位到无效历史引用。另有旧等待覆盖新请求、要求用户事实也必须由工具证明的问题。v4 因此明确区分当前请求与历史内容，并按角色解释证据；这仍需相同完整评测确认，不保证一次提示调整就能满足严格门槛。

## 第四轮改善与第五轮机制

v4 达到 52/56，关键项 52/56、普通事实 59/63，仍未达到原线。两次摘要截断直接导致失败；另一次大结果从头逐页读到末尾，累计上下文触发额外压缩。v5 因此增加相同权限和字节上限内的末尾读取，以及截断后最多一次、从原始片段重新生成的逻辑请求。截断文本不被采用，新请求仍占共享预算。

670 项工程回归通过只说明这些机制满足受控契约；v5 完整真实评测尚在运行。当前模型仍可能读到正确事实却输出错字段或状态词，需要以完整证据判断下一步，不能把新增接口等同于模型一定会正确使用。

## 第五轮说明局部恢复不等于整体验收

v5 完整结果回落到 50/56，关键项 50/56、普通事实 59/63。五个遇到截断的任务重新生成后完成，仍不足以弥补错误字段、许可与效果混淆、拒绝旧记录后放弃工作，以及目录 EOF 后继续追读自己的记录。新的 tail 入口也并非每次都被正确使用。

下一轮保留原任务在回查后的位置，并消除接口对继续分页和引用替代的含糊暗示。模型没有执行的回查、已经读到却写错的值和宿主实际拒绝的调用分别记录，不靠提示改动数量宣布质量提升。

## 第六轮不能用一次组全过盖住后续错误

一次压缩组 24/24，但整体仍为 49/56，关键项 52/56、普通事实 58/63。三次组连续把退出码当诊断标识，尽管摘要里两者都在；另有原请求被忽略、字段名错误和权限状态被当作执行未知。来源存在和原话读回都不足以完成精确输出。

v7 只改进当前任务的表达位置和禁止项说明，继续原模型与原线。因为服务返回了完整 end_turn，不能用传输重试自动重复任务，也不能把没写报告当作还没有收到用户要求。所有版本及失败仍用于比较，而不是择优挑一个分组。

## 第七轮：空页、错误字段和未完成请求

v7 全部 56 次：任务 49/56、关键项 51/56、普通事实 57/63，禁止企图 0。任务数与 v6 相同，仍不能说整体更稳。两个状态任务在摘要仍含 checksum-317 时写成退出码 1；另两个首次摘要请求约 60 秒后取消，没有用量可计。输出错误与未完成请求都保留在分母，不能统一归为摘要丢失，也不能从取消诊断断言上游原因。

大结果任务误把 offset=total_bytes 的合法空页当成整个正文为空。v8 增加固定提示，指导明确选择 tail 或较早范围，保持实际范围及权限校验。真正空正文不提示；EOF 同长度篡改仍拒绝。675 项工程回归只证明这些机制，第八轮完整对照仍用当前模型和原门槛，不为通过测试而加入剧本答案或自动改写报告。

## 第八轮完成：普通事实达线，关键项仍有缺口

v8 为 52/56、关键项 53/56、普通事实 60/63（95.2%）。四次失败仍然重要：字段与顶层结构被改写、等待已经发出的任务、把诊断标识写成退出码。无压缩也失败；失败摘要中保留了相关事实，不能把它们一概算成摘要丢失。全部大结果任务通过，但没有一个触发新空页提示，因此不能从本轮分数声称该提示提升语义质量。

从保存状态另做一次真实请求诊断，确认 SDK 发出的两个请求都含完整任务，诊断报告正确。新运行的成功没有替换原失败。更重要的限制是服务 model 字段自报 MiniMax-M3，而配置请求名是 claude-sonnet-4-20250514；此前记录不含响应身份，不能宣称实际模型从始至终相同。后续比较应同时记录请求身份与服务回执身份，服务自报本身也不是权重验证。当前服务、严格门槛及未交付状态保持。

## 把模型身份的不确定性写进运行证据

在 bef6e96 补上可选 responseModel：完整响应才保存服务自报名称，请求名独立保留，缺失不猜测。不是再次改摘要提示，也没有增加模型请求。678 项工程检查及一次独立服务诊断确认落盘路径；真实服务的两个回执均与生产字段一致，单独记录 3753 输入、176 输出 token。

这项改动补足以后排查路由差异的证据，不能修复过去缺失的身份信息，也不能使 v8 的关键项从 53/56 变成全过。后续语义改进仍须针对实际失败机制，在冻结的完整协议下验证；不能只因无副作用的诊断再次成功就覆盖原失败。

## 原句可验证，选择仍可能失败

独立实验让模型只选择历史引用，宿主复制完整记录，避免在交接里新增自然语言断言。v1 只有 6/8 个合法结果：空引用和超预算都被拒绝。v2 保留原内容块、减少转义，明确不提供本身就装不下的巨大记录正文；输入用量下降，但只有 5/8 合法，仍有两次空选择和一次超限。

复制原文只解决“复制了什么”的校验。模型还可能不选择、选择太多、选错来源，后续也可能把正确原句写成错误字段。两版研究没有执行后续 Agent 任务，不能把结构通过计成质量通过；当前不采用这条替换路线，保持生产实现和原严格门槛。完整失败、源码身份和成本见 [v1（归档）](https://github.com/alienzhou/zero2agent/releases/tag/E04-S003-summary-quality)与 [v2（归档）](https://github.com/alienzhou/zero2agent/releases/tag/E04-S003-summary-quality)。

## 自查也会漏检，评分器同样需要反例

单次结束前核对并未可靠修好四个失败：一个报告仍把诊断标识写成退出码，另一个虽然事实正确，却把来源键写成 facts.project。原评分和顶层结构检查误将后者算作通过。对照原始请求，来源映射本来就必须覆盖每个事实键，因此应补查全部版本，而不能只扣本轮分数。

504 份历史记录一致补查后，v5 任务/关键项为 49/56、49/56，v7 为 48/56、50/56；此前段落的 50/56、49/56 是当时仅做顶层结构审计的历史数字，原证据保持。v8 仍为 52/56、关键项 53/56。核对试验实际修复 2/4，四个成功对照无损；没有满足事先约定的集成条件，故不接入生产。完整八例和 17 次请求的费用均保留。

要求键存在、来源标签匹配、引用真正支持事实，是不同层次。新增检查只补上第一层；不能把它叫作来源认证，也不能用模型一句“核对完成”替代后两层。保持当前模型和严格门槛，意味着把这些失败如实算进结果，而不是继续重跑到偶然通过。

## 显式产物检查解决的范围

获批成对 v1 的基线为 53/56、候选 54/56，结构从 53/56 到 56/56；只有一例触发并完成实际修复，零压缩组分差不能全部归因于新机制。两个语义关键失败发生在首次结构检查之前：一个选了存在于证据中的错误概念，一个把历史失败当作新执行未知。增加 JSON 检查不能识别它们。

按回合显式契约避免把任意任务猜成固定报告格式，独立预算/权限/取消保护避免完成检查开启新的无界回合。字段 description 只由调用方解释含义，不从字段名推断事实或注入 oracle；新成对 v2 同时给双方这些说明。所有旧失败与成本保留，不把新输入成绩冒充原条件改善。

## 字段说明仍不能保证正确取证

成对 v2 完整结果为基线 54/56、候选 55/56，关键项同为 55/56。候选一次/三次压缩组各 24/24，但零压缩的大结果回查仍失败：模型把互斥读取参数组合起来，拒绝后没有重读，最终把三个事实写成 unknown。唯一修复补出了文件，未修复事实；56 份结构合法不能算语义全过。

离线重建与原收据哈希一致的合成字节，合法尾页读取可以取得事实；这是协议诊断，不是重跑或给真实失败补分。所有 728 份正式记录及各轮成本分开保留。下一步需要针对取证和事实使用的机制证据，不能用重复措辞实验与不断重测代替改进。当前服务、预算和严格要求不改，Story 仍为开发稿。

## 最后的修复为什么要改运行流程

最后一个失败在零压缩组，已经排除了“只有摘要丢失事实”这个解释。先前不断补字段说明和结构检查，只能让模型知道应该写什么、文件长什么样；读取调用被拒绝后，宿主仍允许模型用 unknown 填完并结束，这个流程条件没有改变。

修复先建立同一响应序列的确定性前后对照，再让内置工具的参数错误登记未解决引用。结束前最多一次纠错，仍失败就明确未完成；不能让模型文字或合法 JSON 清除失败。实际读取重走当前权限、仍消耗原预算，已完成副作用不重放。全仓 723 项通过，真实完整固定集 56/56 达标。

最终真实轮次与旧基线是同调用方输入、不同时间的历史比较。一次全过不足以把收益全归给某条提示或状态机；机制收益由确定性前后对照证明，真实结果证明这一固定集本轮达标。所有 784 份正式记录保留。以后遇到类似反复失败，先判断失败属于记忆、取证、工具协议还是完成条件，再针对可观察缺口修复，避免继续靠补文案碰成功。
