# E02-S001-write-file Retrospective

> 迭代：E02-S001（直接改动工作区）· 日期：2026-07 · 关联：[Story README](../specs/E02-act-and-execute/S001-write-file/README.md) · [讨论记录](../.discuss/2026-07-20/e02-s001-write-file/outline.md)

## Summary

给 Agent Harness 装上第一批**写工具** `write_file` 和 `delete`，让它第一次跨过 Epic 1 的「只读」边界，能创建 / 覆盖 / 删除工作区文件。核心产出：`write-file.ts`、`delete.ts`、共享边界校验 `path-guard.ts`（`resolveInsideCwd`），以及 25 个针对写路径的单测。安全底线是「cwd 之外一律硬拒绝」。

这是 Agent Harness 从「只读观察者」变成「能改变世界状态」的行动者的第一步，也是 Epic 2「行动力」主轴的起点。

## What Went Well

- **竞品调研先行，得到一个反常识结论**：opencode / codex / pi-mono / gemini-cli / aider 五家里**没有一家做独立 delete 工具**（都交给 shell / 补丁 / git）。zero2agent 坚持独立 `delete` 是**有意的教学向偏离**，且把「偏离理由」写成了可辩护的对比表，而不是无脑跟风或凭感觉。
- **单一职责的工具拆分**：`write_file` 只做全量写、`delete` 只做批量删，各司其职、语义清晰，延续了本课程「一个工具 = 一种清晰意图」的哲学。
- **物理边界抽成共享 helper**：`resolveInsideCwd` 独立成 `path-guard.ts`，两个写工具共用，一行 `path.relative` 判断同时挡住 `../../etc/hosts` 和 `/etc/hosts` 两类逃逸。复用 + 单点防护，比各自内联更不易漏。
- **批量操作的「部分失败」被显式建模**：`delete` 走方案 B（尽力删 + 逐条汇总），每个路径单独过边界校验，失败不中断、回执如实陈述。这是从「工具能跑」到「工具对 Agent 友好」的关键一步。
- **克制扩展**：明确不扩展 `ToolContext`（维持只有 `cwd`）、不引入 approval 框架，把接口稳定和「后续专章一次性做好」绑定。没有为单个 Story 的便利污染公共契约。

## What Could Be Improved

- **回执语言 doc 与 code 漂移（本次最大疏漏）**：D06 决策、技术设计和 README 里写的回执都是中文（`已创建文件 <path>（写入 N 字节）`、`Error: <path> 超出工作区`），但实现实际落的是英文（`Created ... (N bytes written)`、`is outside the workspace`）。原因是实现时**跟随了 Epic 1 既有工具的实际英文回执习惯**，与 spec 的中文契约相左，且事后没有回头对齐文档。最终 `git` 里的代码是英文，文档是中文——两套契约并存。
- **协作记录与复盘滞后**：`.vibecoding/` 下没有 E02 目录，E02-S001 的 AI 协作对话没有按规范归档（Epic 1 的 S001–S004 都有）；复盘笔记也拖到迭代收尾才补。文档节奏没跟上代码节奏。
- **安全纵深只有单点**：本 Story 的防线是「cwd 硬拒绝」这一条。软链真实路径解析、危险路径黑名单、破坏性确认、事后回滚全部进了 backlog，越界的物理防线目前是单薄的单点校验。

## Lessons Learned

1. **写工具的设计重心从「功能多」转移到「边界 + 回执清晰」**：只读工具重复调用无害，写工具会改变磁盘状态、不可逆，所以安全边界和「改了什么、没改什么」的回执比参数丰富度更重要。
2. **竞品调研的价值在于「反共识」**：结论不是「抄谁」，而是「发现主流都不做独立 delete → 我们为什么偏要做 → 理由写清楚」。有意的偏离需要同样有意的论证。
3. **批量操作必须显式定义部分失败语义**：一旦接收数组，「删到一半失败怎么办」就绕不开。方案 B（尽力删 + 逐条汇总）对 Agent 最友好——它拿到的是清晰的成败清单，而不是模糊的整体状态。
4. **回执的语言/措辞要在 spec 里写死并跟随既有代码习惯对齐**：本次 doc/code 漂移的根因，是 spec 用中文描述契约、既有代码用英文实现，两者从未对齐。要么 spec 明确「沿用既有英文回执」，要么实现按 spec 中文落盘，不能两套并存。

## AI Coding Notes

- **竞品调研文档直接喂给模型，能高效产出收敛的决策点**：把 5 家竞品报告作为上下文，模型能自己归纳出「无独立 delete」「write 最小形态收敛」「路径安全两流派」等跨竞品发现，D01–D07 的推导质量因此明显高于凭空设计。
- **模型实现时会「自作主张」对齐既有代码风格**：本次回执语言的漂移，正是模型在实现时看到 Epic 1 工具都返回英文，便主动把英文当成了「代码库既有约定」，而无视了 spec 里的中文契约。教训：**回执措辞这类「契约面」细节，需要在实现后做一次 doc/code 一致性核对**，或在 spec 里显式声明「沿用既有英文回执」以消除歧义。
- **写工具的测试要覆盖「副作用不发生」**：越界拒绝的正确性不能只看返回值，还要断言磁盘上没有产生任何文件（`resolveInsideCwd` 返回 null 后不写不删）。`path-guard.test.ts` + `write-file.test.ts` 的越界用例都验证了这一点。
