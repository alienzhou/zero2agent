# E02-S002-replace-in-file Retrospective

> 迭代：E02-S002（高效修改已有内容）· 日期：2026-08 · 关联：[Story README](../specs/E02-act-and-execute/S002-replace-in-file/README.md) · [讨论记录](../.discuss/2026-08-15/e02-s002-replace-in-file/outline.md)

## Summary

给 Agent Harness 装上局部修改工具 `replace_in_file`，让它在 `write_file` 的「整篇重写」之外，能对已有文件做精确的局部替换。核心产出：`replace-in-file.ts`、14 个单测，以及「唯一性约束 + replace_all 开关」这一组设计。安全边界复用 S001 的 `resolveInsideCwd`，回执统一英文。

这是 Agent 写能力从「能写」到「能改」的关键一步，也是 S001 复盘教训第一次被显式落到下一个迭代的决策里。

## What Went Well

- **doc/code 漂移的教训被前置到决策阶段**：S001 复盘记了「spec 写中文回执、代码落英文」这条教训。S002 的 D06 直接写明「回执统一英文，与既有工具一致」，Spec 与代码从源头对齐，不再两套并存。复盘的价值第一次被真正「用」了起来，而不是停在文档里。
- **把教学重心放在「定位」而非「替换」**：替换这个动作本身太简单，真正的难点是「怎么确保改的是对的那一处」。S002 把唯一性约束（0 次 / 1 次 / ≥2 次三种语义）立为 Story 的灵魂，让读者学到的是「如何防止改错位置」，而不是「怎么调一个替换函数」。
- **复用而非重写**：安全边界直接复用 `path-guard.ts` 的 `resolveInsideCwd`，没有为 replace_in_file 另写一份。这反过来验证了 S001「把边界抽成共享 helper」这个决策的价值——第二个写工具来了，零新增边界代码。
- **replace_all 是一个真实的产品判断**：五家竞品的单文件 edit 都没有全量替换开关，但「批量重命名」是高频场景。默认关、显式开，既守住唯一性安全默认，又覆盖真实需求，成本只有一行 `split().join()`。
- **规避了一个隐蔽实现坑**：用 `split(old_string).join(new_string)` 而非 `String.replace`，躲开了 `$` 在替换串里被当成占位符（`$&`、`$1`）的陷阱，并有单测覆盖。

## What Could Be Improved

- **竞品调研偏「推断」而非「实证」**：本轮 replace-in-file 调研建立在上一轮 write-file 调研的既有矩阵 + 模型先验之上，没有像 S001 那样单独跑一轮针对「edit/replace 机制」的独立实证。「五家竞品都没有 replace_all」这条关键结论，需要实际翻竞品源码/文档才能站得住，否则有「用模型先验冒充调研结论」的风险。
- **端到端行为验证留白**：单测全绿，但真实 LLM 调用 `replace_in_file` 的 e2e 验证因缺 `ANTHROPIC_API_KEY` 没跑。模型在真实语境里是否会正确使用「唯一性约束」和「replace_all」、会不会自己想到「插入用锚点替换」，都没有得到行为层面的确认。
- **插入场景对模型不够显式**：D05 定了「纯插入用锚点替换表达」，但工具 `description` 里没有显式提示模型「要插入就替换一个唯一锚点」。这依赖模型自己领悟，可能成为真实使用中的摩擦点。

## Lessons Learned

1. **复盘要「落地到下一个迭代的决策」，而非停在复盘文档**：S001 的 doc/code 漂移教训，因为被显式写进 S002 的 D06，才真正消失。复盘→决策→实现形成闭环，教训才有效。
2. **局部修改的本质是「定位 + 替换」，定位比替换更难**：唯一性约束解决的是定位问题（逼模型带上下文），它是防止改错位置的关键，也是局部改工具的设计重心。
3. **「复用」是上一个迭代决策正确性的验证**：第二个写工具来了却不新增边界代码，说明 S001 抽 `resolveInsideCwd` 是对的。好的抽象经得起第二个使用者的检验。
4. **调研结论需要实证支撑**：用模型先验补全的调研，要把「这是推断」和「这是实证」分开标注，否则会把未经核实的主张写进 spec。

## AI Coding Notes

- **把「上一轮的教训」显式写进新决策文档，是让 doc/code 一致的最省力手段**：与其每次实现后核对，不如在决策阶段就约定好契约措辞，实现者（含 AI）照着写即可。
- **`String.replace` 的 `$` 占位符陷阱是真实高频坑**：处理「把 A 替换成 B」这类字符串工具时，永远优先 `split().join()`，并加一条含 `$` 的测试用例兜底。
- **竞品调研的每一条断言都应标注证据来源**：模型先验推断和实际翻源码/文档的结论要分开，否则教学项目会把「听起来对」当成「事实」，误导读者。
