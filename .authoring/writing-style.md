# 写作风格规范

> 仅供课程作者参考，不在读者阅读路径上。

---

## 核心原则

### 1. 标题说人话

用直述句，直接回答"这一段讲什么"。

| ✅ 用这种 | ❌ 不用这种 |
|-----------|------------|
| 这个 Epic 做什么 | 这个 Epic 要把我们带到哪里 |
| Story 列表 | 这个 Epic 包含哪些 Story |
| 从哪里开始 | 下一步怎么走 |
| 问题与目标 | 这次我们要解决的问题和目标 |

避免隐喻式表述（"带到起点"、"踏上旅程"）。

### 2. 不重复上游信息

每一层文档只写本层的新信息：

- **Roadmap** 讲全局路线和阶段定位 → Epic 页不重复
- **Epic** 讲本阶段做什么、Story 列表 → Story 页不重复
- **Story** 讲具体问题、实现和代码指引

如果某段话删掉后，读者从上游页面仍能获得同样信息，就删掉。

### 3. 信息密度优先

每段话、每个 section 必须有实质新信息。

- 不做排比堆砌（三个 emoji + 三个并列要点，实际说的是同一件事）
- 不用同义替换撑篇幅
- 如果一个 section 只有一句话的信息量，合并到相邻 section

### 4. 快速进入行动

读完就能开始做事。

- Epic 页读完 → 知道做什么、有哪些 Story、从哪个开始
- Story 页读完 → 知道问题、目标、先看什么代码
- 避免抽象铺垫（"在进入 X 之前，我们先..."）

### 5. 结构为读者服务

section 拆分是为了读者快速定位，不是为了模板看起来完整。

- 用不上的 section 直接省略，不要留空
- 内容少的 section 合并

### 6. 节制使用 emoji

- 不用 emoji 做标题前缀（如 `🎯 目标`、`🗺️ Story 列表`）
- 正文中状态标记可以用（✅ Done、📝 Planned）
- 偶尔用于强调可以，但不要每个要点都加

## Story README 专项

### 1. 先建立认知，再进入技术

Story README 的第一职责是教学。

- 先讲这一篇最重要的理解支点
- 再讲问题、目标、边界
- 最后再进入关键设计和实现入口

不要一上来就宣布"新增了什么工具"、"改了哪些文件"。

### 2. 固定内在结构，稳定阅读体验

后续 Story README 尽量共享同一条阅读路径：

1. 认知建立
2. 任务定义（问题 / 目标 / 边界）
3. 关键实现
4. 做完后的效果
5. 扩展与导航

固定的是章节职责，不是标题字面。

- 可以写"Agent 不是更聪明的聊天"
- 也可以写"只会读文件还不够"
- 只要它承担的是"认知建立"这一职责即可

### 3. README 保留关键技术判断，不做去技术化

适合放进 Story README 的内容：

- 为什么需要这一步能力
- 参数为什么这样设计
- 输出契约为什么这样设计
- 排序、截断、边界为什么这样取舍
- 工具之间为什么是配合关系，而不是替代关系

不适合作为正文前半段重心的内容：

- 注册方式
- 底层依赖细节
- 代码分层的琐碎实现
- 大量边界分支和异常处理细节

原则：README 讲设计判断，`details/` 讲深入实现。

### 4. 每段只回答一个问题

提高信息密度时，优先这样写：

- 一段只解决一个明确问题
- 能用表格就不用三段散文
- 能做对比就不要写空泛过渡句
- 能直接下结论就不要绕路铺垫

低信息量句式尽量少用，例如：

- "从某种意义上说"
- "我们可以看到"
- "这一点其实也很重要"

### 5. 主动预留可视化位置

Story README 不默认全文平铺直叙。

适合用图或表的场景：

- 两种模式或工作流的对比
- 参数设计与职责划分
- 设计决策对照
- 代码阅读路径

图表的职责是降低理解成本，不是装饰页面。

### 6. 链接少而准

正文里的链接只放读者下一步最可能需要的材料：

- 需要深入实现细节时，链接 `details/`
- 某个设计判断有复用价值时，可链接 `.discuss/` 决策文档

不要把 README 写成链接目录。

## Deep Dive 与三层学习

每个 Story 尽量让读者带走三类收获（层次不必在文中贴标签，但作者心里要有数）：

1. **功能实现**：这一版在仓库里真实落地了什么（代码、工具、行为变化）。
2. **思维方法**：这一篇特有的设计视角（例如「如何从零设计一个 Agent 工具」、工作流拆分方式）。
3. **Deep Dive**：当前实现之外仍值得想下去的题目；**可以不实现先写清**，供自学与后续迭代。

Deep Dive 的常见来源：

- 讨论中明确**推迟到扩展阅读**的边界（截断、超时、校验、降级等）。
- **设计取舍**的对照（参数多少、路径策略、排序语义等）。
- **业界方案**与当前简版差异（不要求本迭代跟进行业全文）。

### `details/`、`04-backlog`、`deep-dive/` 怎么分

| 载体 | 职责 |
|------|------|
| `details/00–03` | 本迭代要做什么、怎么做、怎么验收 |
| `details/04-backlog.md` | 「不做清单」+ **话题池**（短列表，可链接到 Deep Dive） |
| `deep-dive/*.md` | 把话题池里高杠杆问题写成长文（方法、对比、延伸） |

原则：**README 保主线判断**；**details 保交付**；**deep-dive 保纵深**。同一句话不要在 README 和某篇 Deep Dive 里完整复制两遍——README 给结论与动机，Deep Dive 给推导与外延。

### Story README 里怎么挂 Deep Dive

- 在主线章节之后增加 **「深入了解」**（或同等含义的章节名），用有序列表 + **每一条下有一两句导读**，说明读完能回答什么问题。
- 列表顺序与 `deep-dive/` 文件名编号一致，避免读者迷路。
- 没有合适题目的 Story 可以整节省略；不要为了凑目录硬写空文。

### Deep Dive 正文写法

- 默认读者已读过本 Story README，**不重复**问题/目标/边界的整段定义。
- 允许写「本版未实现」「若以后要做」，与 backlog 互链，避免读者误以为代码已覆盖。
- 标题与分段仍遵守「标题说人话、一段一事、表格优于散文堆砌」。

### 目录名：`deep-dive/`

- **统一使用 `deep-dive/`** 作为 Story 延伸长文目录名（Epic 1 的 S001/S002 均已如此）。
- 同一 Story 内不要混用其他目录名存放同角色内容。

## 语气

- 对读者用"你"，不用"我们"（除非确实是共同操作）
- 技术描述直接了当，不加情感修饰（"很棒的"、"令人兴奋的"）
- 可以口语化，但不能含糊
