# Story README 自检清单

> 写完一篇 Story README 后，用这份清单快速过一遍。

## 定位

- [ ] 这篇 README 是在教读者理解问题和设计，不是在记实现流水账
- [ ] 开头先建立了这一篇最重要的认知支点，而不是直接宣布“新增了什么”

## 结构

- [ ] 章节职责清楚，整体阅读路径基本符合：认知建立 → 任务定义 → 关键实现 → 做完后的效果 → 扩展与导航
- [ ] `问题 / 目标 / 边界` 讲清楚了，而且没有混在一起
- [ ] `做完后的效果` 写的是读者可观察到的变化，而不是重复前文目标

## 技术深度

- [ ] README 保留了关键设计判断，而不是只给代码入口
- [ ] 参数、输出契约、排序、边界等内容，讲的是“为什么这样设计”
- [ ] 过深的实现细节已经下沉到 `details/`，没有挤占正文主线

## 表达

- [ ] 每一段都在回答一个明确问题，没有低信息量铺垫
- [ ] 能用表格、对比或流程表达的地方，没有硬写成长段散文
- [ ] 标题说人话，读者扫一眼就知道这一段讲什么
- [ ] 对读者使用“你”，避免空泛的“我们可以看到”

## 导航

- [ ] 顶部面包屑正确
- [ ] `details/` 入口齐全且必要
- [ ] 若有 `deep-dive/`，README 中「深入了解」（或同等章节）已逐条链到文章，且每条有导读句
- [ ] `details/04-backlog.md` 中的话题池与 Deep Dive 文章无脱节（列表项与长文互链或使用同一编号体系）
- [ ] 只放了少量高价值链接，没有把 README 写成链接目录
- [ ] 上一篇 / 下一篇跳转已补齐

## Deep Dive（若有）

- [ ] 每篇 Deep Dive 假设读者已读 Story README，不重复 Epic/Story 总述
- [ ] 写清了与当前实现的关系（已实现 / 未做 / 未来方向），避免误导
- [ ] 正文是「讲透一个问题」，不是任务清单或验收列表（那些应在 `details/`）

## 可视化

- [ ] 适合配图、对比表、ASCII 图的位置已经预留
- [ ] 图表服务于理解，而不是装饰页面
