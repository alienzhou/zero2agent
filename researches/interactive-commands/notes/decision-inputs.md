# 把调研转成 S004 的讨论选项和验收问题

[调研总览](../README.md) | [基线核对](./zero2agent-baseline.md) | [实验](../experiments/README.md)

> 本页是决策输入，不是定稿 spec。没有以竞品多数票替用户确定 API、PTY、会话数或超时值。

## 一、先确定真实需求，再确定通道

建议用下面的定义重新评审 D01：

> 当后续输入取决于已运行程序的输出、不能在启动前一次性决定时，让模型观察结果，再向同一进程继续输入；输入必须仍在用户授权范围内。

“不能一次性决定”是场景筛选原则，不是要求数学上证明绝无脚本可替代。目标是找到清晰的教学增量，避免为了使用新工具把原本简单的脚本拆成大量轮询。

| 候选故事 | 新增价值 | 首要约束 | 本轮证据 |
|---|---|---|---|
| 运行中保留状态的 Python/Node 探索，按中间结果继续求值 | 同进程状态与按结果调整 | 正确 -i 模式、输出刷新、异常后继续 | 真实 REPL 两轮已验证；LLM 任务未验证 |
| 命令按运行结果显示选项，模型据上下文选择下一步 | 选择依赖动态输出 | 提示可靠、确认权限、不把危险 y/N 自动同意 | 自编两轮协议夹具通过；真实 CLI 待选 |
| 需要 TTY 的菜单或行编辑程序 | 终端兼容性 | PTY、窗口尺寸、ANSI、raw/canonical | 机制验证；产品菜单未验证 |
| 人提供模型不应持有的秘密/交互认证 | 人机协作 | 专用输入、互斥、脱敏、权限和输出反射 | 本轮仅识别风险，未提供秘密通道 |
| dev server、watch 构建 | 后台运行和观察 | 启停、日志、资源归属 | 主要已属 S003，不应重新扩大 S004 |
| 已知输入的 -y、配置文件、here-doc | 无需运行中决策 | 参数正确、不改变原意 | 优先保留现有非交互路径 |

## 二、D01–D05 的候选方案

### D01：输入者和权限是两条轴

不要把 REPL、y/N 都笼统归为“模型能答所以可以写”。至少检查：答案是否可由任务上下文确定；输入是否代表新授权或不可逆动作；是否含秘密；用户是否仍想参与。

本章可以只做模型输入，不做人工接管；但理由应是可控教学范围，而不是“自主 Agent 不能有人在环”。Codex、Gemini、Aider、DeepSeek 的不同组合说明二者不是互斥产品阵营。

### D02：四种就绪策略

| 策略 | 能可靠说明什么 | 成本/风险 | 参照 |
|---|---|---|---|
| 固定有限 yield 窗口 | 本次等待结束，进程可能仍活着 | 空轮询、延迟、模型 token 开销 | Codex |
| 输出静默后 yield，另有绝对上限 | 最近没有被观察到的新输出 | 缓冲/计算/IO 都可静默；持续输出不能无限占住调用 | DeepSeek 的 inferred_idle 部分 |
| 程序提示协议/marker | 受控 shell 到达已定义提示边界 | 需要 shell 注入、转义/伪造/竞态处理 | DeepSeek、IDE shell integration |
| OS 特定的 stdin 等待检查 | 支持平台与权限下的局部证据 | Linux /proc、架构 syscall 表、多线程和前台组；其他平台缺失 | DeepSeek Linux inspector |

教学主线采用第一种是可讨论的简化方案；“暂不采用系统调用检测”不应再写成“操作系统根本没有这种信息”。任何方案都要避免静默时返回假 exitCode=0。

### D03：创建入口和会话操作独立选择

| 形状 | 优点 | 代价 |
|---|---|---|
| terminal 增声明参数 + 独立续写工具 | 保持工具数量小，旧调用可兼容 | terminal 回执新增 running 状态，不能声称契约没变 |
| 独立 open/exec + write/read/close | 一次性与会话职责显式 | 模型工具选择更多，重复参数/命名需控制 |
| 一个会话工具 + action | 集中状态操作 | action 联合校验复杂，误参数更难解释 |
| read 与 write 合并，空输入代表 poll | 类似 Codex，调用面小 | 空串必须不等于 EOF；并发消费语义需明确 |
| 独立 read/wait 与 write | 观察与副作用容易分开 | 工具更多；未必值得为本章一次实现全部 |

不要把工具数量当成设计质量。先写出一段真实“创建→观察→输入→终结”的 transcript，再检查模型能否判断下一步以及用户能否取消。

无论选哪种，session ID 应是应用句柄且绑定 owner；它不能单靠随机性代替授权。重试还需要回答：请求是否可能重复写入？未知/已结束的 ID 是报错、返回终态还是可读 tombstone？

### D04：pipe 与 PTY 的选项

| 方案 | 适用条件 | 明示放弃/新增成本 | 当前判断 |
|---|---|---|---|
| 只保留非交互命令 | 本章找不到必须跨轮的真实任务 | 不交付运行中续写 | 可作为反事实基线，不满足原定核心愿望 |
| pipe-only 会话 | 真实用例可用显式交互/flush 模式运行 | 不提供 TTY 行规程、全屏体验和任意认证 | 已证明部分 REPL 可行；范围仍需讨论 |
| pipe + 可选 PTY | 大部分简单，少量程序要求 TTY | 两套控制字符/EOF/降级语义，原生依赖部署 | 灵活但测试面扩大，不能只留一个空接口当完成 |
| PTY-first | 主要目标就是终端型程序 | 编译/预构建、ConPTY、尺寸、ANSI、回显/背压、终端模式 | 新样本可参考，尚未证明对课程收益大于成本 |
| 人工继承/接管终端 | 必須有用户现场操作 | headless 不成立；控制权交接/恢复与秘密政策 | 是独立需求，不当作模型续写的替代实现 |

S003 不需要原生依赖，并不逻辑上禁止 S004 引入；是否继续零依赖应比较这一次新增需求的收益和维护成本。反过来，也不能因为其他产品用了 PTY 就默认课程必须跟进。

### D05：寿命与资源政策

| 决策点 | 选项 | 必须写出的外部行为 |
|---|---|---|
| 所有者 | 当前 turn／当前 Agent 会话／宿主服务 | 哪些边界结束后 ID 还可用 |
| 停止等待 | 仅返回／中断前台／关闭整个会话 | 用户按取消后究竟什么仍在跑 |
| 空闲 | 不自动回收／有 lease／确认后回收 | 谁的活动重置时钟，推理时间算不算 |
| 达到上限 | 拒绝新建／先清理已结束／淘汰活项 | 是否可能结束用户未完成工作 |
| 进程退出 | 等输出 EOF／有限 drain | 尾部丢失如何标记、何时可删记录 |
| 输入结束 | 显式 close-input／不提供／程序专用退出命令 | EOF 可能处理缓存，不是撤销 |
| 宿主退出 | 关闭所有 owned／允许明确后台存活 | headless、崩溃、SIGKILL 的保证边界 |
| 资源预算 | 活会话、内存、输入长度、磁盘、读输出预算 | 这些限额分别控制什么、超限会怎样 |

小型硬上限拒绝新建是值得讨论的教学方案，但不在本页拍板“8 个”。如果选择 LRU，必须承认 Codex 可以淘汰活项，保护正在操作不等于永不误伤业务。

## 三、建议先写出的回执语义

以下是字段职责示例，不是必须采用的 schema：

- `session_id`：owner 范围内稳定句柄；不能只保存 PID。
- `status`：至少区分 running、exited、closed/failed；waiting 只有确证时才使用。
- `output`：本次观察到的文本，并说明是 delta、窗口还是完整日志片段。
- `next_cursor`／实际输出范围：若采用可重复读取协议，要定义单位与截断后的缺口。
- `exit_code`／`signal`：只在真实终态获得时出现，不用 0 填补未知。
- `input_state`：至少能明确不支持、可写、已关闭；写失败不能伪装成功。
- `truncated`／`incomplete`：分别表明预算裁剪和输出还未完整收集，二者不能混为一谈。

即使最终仍返回字符串，也要让这些语义清晰。TypeScript 的 `Promise<string>` 无需因状态增加而改变，但面向模型的契约确实扩展了。

## 四、验收应覆盖的状态组合

| 类别 | 最小应验场景 | 当前证据/后续 |
|---|---|---|
| 基本回路 | 至少两轮按输出决定输入，同一进程状态保留 | 机制+真实REPL通过；S004端到端待实现 |
| 早返回 | 慢命令、持续输出、等 stdin 均在窗口内归还控制权 | 方案未实现；不能拿 S003 10s 提示替代 |
| 输入 | 空 poll、不自动补换行/明确 submit、UTF-8、关闭后写、未知 ID | 部分机制通过；会话协议待测 |
| 终端差异 | pipe/PTY、canonical/raw、ECHO、无控制终端 | 机制通过；目标平台仍需验收 |
| 输出 | 无换行、跨块字符、截断、溢出、结束尾部、重复读 | 部分机制通过；压力与丢失标记待测 |
| 并发 | 两会话互不串输出；同会话双写/读写竞争；取消与写同时发生 | 源码参考，不等于本项目已通过 |
| 寿命 | 任务完成、turn取消、长推理无输入、配额满、宿主退出 | 方案及各触发语义待定 |
| 异常 | spawn失败、write EPIPE、信号无效、子进程exit但fd未关 | E10验证机制；runtime恢复待测 |
| 安全 | owner错配、陈旧ID、提示注入、未经授权的y、假秘密传播 | 没有安全保证；不得使用真实凭据验收 |
| 兼容 | headless、非交互CI、Windows、Linux、macOS | 本轮只跑macOS本地机制 |

## 五、建议的后续讨论顺序

1. D01 选 2–3 个真实故事，并删掉“知道答案就有权确认”的前提。
2. D02 确认有限 yield 的基本回路；将 OS 探测作为可选增强，而非必需地基。
3. D03 用一段完整工具 transcript 比较 API 形状，先解决创建与后续操作可达性。
4. D04 根据真实故事选择 pipe/PTY 范围，不预先继承“必须无原生依赖”或“必须追平产品”。
5. D05 明确寿命、取消、EOF、owner 与预算，再决定任何数值。
6. 若选 PTY 或要借鉴输入检测/池化，再补目标平台与 OpenHands 单会话/默认池的定向实测。

到“真实故事明确、关键契约可写出、未覆盖边界可接受”再进入 spec。本文和本轮实验不自动更新 PR #12 的 Confirmed/Rejected 状态。
